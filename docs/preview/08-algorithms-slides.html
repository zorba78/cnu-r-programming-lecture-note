1 · 알고리즘과 비용

알고리즘이라 부르려면

노트

알고리즘(algorithm): 주어진 문제를 해결하기 위해 정해진 일련의 절차를 단계적으로 표현한 것.

  • 명확성 — 각 단계가 모호하지 않다
  • 유일성 — 다음 단계가 하나로 결정된다
  • 입력과 출력 — 정의된 입력을 받아 결과를 낸다
  • 유한성 — 유한한 단계를 거쳐 반드시 종료한다
  • 일반성 — 정의된 입력 전체에 대해 동작한다

실제 구현에서 가장 자주 위반되는 조건은 유한성과 일반성이다.

“특정 예제에서 올바르게 동작한다”와 “정의된 입력 전체에서 올바르게 동작한다”는 전혀 다른 진술이다.

결과가 같은 두 프로그램

프로그램 1 · 사전 할당

prealloc_vec <- function(n) {
  x <- numeric(n)
  for (i in seq_len(n)) {
    x[i] <- i
  }
  x
}

프로그램 2 · 이어 붙이기

grow_vec <- function(n) {
  x <- NULL
  for (i in seq_len(n)) {
    x <- c(x, i)
  }
  x
}
identical(prealloc_vec(1000), as.numeric(grow_vec(1000)))
[1] TRUE

사전 할당 방식은 이미 확보된 메모리에 값을 대입하므로 반복당 비용이 일정하다.

시간 복잡도와 공간 복잡도

노트

시간 복잡도

알고리즘이 종료할 때까지 수행하는 연산의 횟수. 사칙연산·비교연산·반복·함수 호출이 계수의 대상이다.

노트

공간 복잡도

알고리즘이 종료할 때까지 필요한 메모리의 크기. 변수의 개수·자료 구조·스택 프레임이 대상이다.

성능은 최악의 경우를 기준으로 평가한다. 최선은 특정 입력에서만 성립하고, 평균은 입력 분포를 가정해야 계산할 수 있는 반면, 최악은 임의의 입력에 대해 항상 성립하는 상한을 제공하기 때문이다.

빅오 표기법

노트

\(x \geq k\) 인 모든 \(x\) 에 대해 \(|f(x)| \leq C|g(x)|\) 를 만족하는 상수 \(k\) 와 \(C\) 가 존재하면 \(f(x) = \mathcal{O}(g(x))\) 라 한다. 즉 \(g\) 는 \(f\) 의 점근적 상한이다.

코드를 분석할 때 실제로 사용하는 것은 정의 자체보다 다음 세 규칙이다.

규칙 1 · 계수 법칙

계수는 소거된다.

\(\mathcal{O}(5n) = \mathcal{O}(n)\)

규칙 2 · 합의 법칙

증가율이 큰 쪽만 남는다.

\(\mathcal{O}(n) + \mathcal{O}(n^2) = \mathcal{O}(n^2)\)

규칙 3 · 곱의 법칙

중첩되면 곱한다.

\(\mathcal{O}(n) \times \mathcal{O}(n) = \mathcal{O}(n^2)\)

차수가 다르면 무엇이 달라지는가

n O(1) O(log n) O(n) O(n log n) O(n^2) O(2^n)
10 1 3 10 33 100 1,024
100 1 7 100 664 10,000 1.3e+30
1,000 1 10 1,000 9,966 1,000,000 1.1e+301

\(n = 1{,}000\) 에서 \(\mathcal{O}(n)\) 과 \(\mathcal{O}(n^2)\) 의 연산 횟수는 천 배 차이가 난다.

차수가 다르면 하드웨어 성능 향상으로 해결할 수 있는 문제가 아니다.

2 · 재귀

재귀 함수의 구성

재귀 함수(recursive function) 는 자기 자신을 호출하는 함수다. 호출할 때마다 호출 스택(call stack)에 새로운 프레임이 누적되므로, 이를 중단시키는 조건이 없으면 함수는 종료되지 않는다.

  1. 종료 조건(base case)
    분할하지 않고 결과를 직접 반환
  2. 재귀 단계(recursive step)
    문제의 크기를 줄여 자기 자신을 호출
recursive_sum <- function(n) {
  if (n == 1) return(n)     # 종료 조건
  n + recursive_sum(n - 1)  # 재귀 단계
}

recursive_sum(3)
[1] 6

n 이 0이면 n == 1 은 결코 참이 되지 않는다. 인수가 계속 감소하다가 R 의 중첩 한계에 도달해서야 중단된다. 종료 조건은 “n 이 1 이하일 때”로 규정했어야 한다.

결함은 입력이 커질 때만 드러나는 것이 아니라, 정의역의 경계 바로 바깥에서도 드러난다.

recursive_sum2 <- function(n) {
  if (n <= 1) return(n)          # 경계 조건을 포함한다
  n + recursive_sum2(n - 1)
}
c(recursive_sum2(0), recursive_sum2(1), recursive_sum2(100))
[1]    0    1 5050

재귀의 비용

재귀 호출은 호출마다 스택 프레임을 누적하므로 공간 복잡도가 \(\mathcal{O}(n)\) 이다. R 은 중첩 깊이를 options(expressions) 로 제한하며 기본값은 5000이다.

recursive_sum2(1000)                     # 정상적으로 동작한다
[1] 500500
tryCatch(recursive_sum2(5000),           # 중첩 한계
         error = function(e) cat("오류:", conditionMessage(e), "\n"))
오류: evaluation nested too deeply: infinite recursion / options(expressions=)?

재귀는 가독성을 얻는 대신 메모리를 소비한다. 재귀 구조로 문제를 먼저 이해한 뒤, 필요하면 반복문으로 변환하는 순서가 안전하다. 반복문 구현은 공간 복잡도가 \(\mathcal{O}(1)\) 이고 깊이 제한도 없다.

하노이 탑

기둥 세 개와 크기가 다른 원판 \(n\) 개. 한 번에 하나씩만 옮기고, 큰 원판을 작은 원판 위에 올릴 수 없다. 해법의 핵심은 문제를 한 단계 작은 동일 문제로 환원하는 것이다.

move_hanoi <- function(k, from, to, via) {
  if (k == 1) {
    cat(sprintf("원판 1: %s -> %s\n", from, to))
  } else {
    move_hanoi(k - 1, from, via, to)
    cat(sprintf("원판 %d: %s -> %s\n", k, from, to))
    move_hanoi(k - 1, via, to, from)
  }
}
move_hanoi(3, "A", "C", "B")
원판 1: A -> C
원판 2: A -> B
원판 1: C -> B
원판 3: A -> C
원판 1: B -> A
원판 2: B -> C
원판 1: A -> C

이동 횟수는 \(2^n - 1\) 이다. 호출이 매 단계에서 두 개로 분기하기 때문이다. 즉 \(\mathcal{O}(2^n)\) 이다.

전설의 원판 64개는 1초에 한 번씩 옮겨도 5천억 년이 넘게 걸린다.

3 · 탐색 알고리즘

선형 탐색과 이진 탐색

선형 탐색 · \(\mathcal{O}(n)\)

linear_search <- function(target, vec) {
  for (i in seq_along(vec)) {
    if (vec[i] == target) return(i)
  }
  NA_integer_
}

첫 원소부터 순차적으로 비교한다. 정렬되어 있지 않아도 적용할 수 있다.

이진 탐색 · \(\mathcal{O}(\log n)\)

binary_search <- function(target, ovec) {
  lo <- 1L; hi <- length(ovec)
  while (lo <= hi) {
    mid <- (lo + hi) %/% 2L
    if (ovec[mid] == target) return(mid)
    if (ovec[mid] > target) hi <- mid - 1L
    else lo <- mid + 1L
  }
  NA_integer_
}

비교를 한 번 할 때마다 후보가 절반으로 줄어든다. 단, 정렬되어 있어야 한다.

원인은 첫 줄의 if (maxL <= minL) return(NA_integer_) 이다. 탐색 범위가 원소 하나로 좁혀지면 minL == maxL 이 되는데, 이 조건은 남은 원소를 검사하지 않은 채 탐색을 종료한다. 탐색 범위가 실제로 비는 조건은 minL > maxL 이다.

오류 메시지 없이 틀린 코드

rbinary_search2 <- function(target, ovec, lo = 1L, hi = length(ovec)) {

  mid <- (lo + hi) %/% 2L
  if (ovec[mid] == target) mid
  else if (ovec[mid] > target) rbinary_search2(target, ovec, lo, mid - 1L)
  else rbinary_search2(target, ovec, mid + 1L, hi)
}

rbinary_search() 는 문법 오류가 없고, 실행 시 오류 메시지도 출력하지 않으며, 저자가 선택한 예제에서는 정답을 반환한다. 그럼에도 잘못된 구현이다.

이러한 결함은 오류 메시지가 아니라 검증 절차를 통해서만 발견된다.

두 탐색의 비용 비교

실행 시간 대신 연산 횟수를 계수하면 하드웨어 성능과 무관한 값을 얻는다.

n 선형 이진
100 50.5 5.8
1,000 477.0 8.8
10,000 5250.9 12.4

\(n\) 이 100배 증가할 때 선형 탐색은 약 100배 증가하지만, 이진 탐색은 두 배를 조금 넘는 수준에 그친다. \(n = 10^6\) 이면 선형 탐색은 평균 50만 회, 이진 탐색은 약 20회를 수행한다.

정렬되어 있어야 적용할 수 있고, 정렬 자체의 비용이 \(\mathcal{O}(n \log n)\) 이다.

탐색을 한 번만 수행한다면 정렬 후 이진 탐색을 적용하는 것보다 선형 탐색이 오히려 저렴하다. 탐색을 여러 번 반복할 때 비로소 정렬 비용이 상쇄된다.

4 · 정렬 알고리즘

버블 정렬과 병합 정렬

버블 정렬 · \(\mathcal{O}(n^2)\)

bubble_sort <- function(x) {
  n <- length(x)
  if (n < 2) return(x)
  for (i in seq_len(n - 1)) {
    for (j in seq_len(n - i)) {
      if (x[j] > x[j + 1]) {
        temp <- x[j]
        x[j] <- x[j + 1]
        x[j + 1] <- temp
      }
    }
  }
  x
}

병합 정렬 · \(\mathcal{O}(n \log n)\)

smerge <- function(left, right) {
  temp <- numeric(length(left) + length(right))
  l <- r <- 1L
  for (i in seq_along(temp)) {
    if (r > length(right) ||
        (l <= length(left) && left[l] <= right[r])) {
      temp[i] <- left[l]; l <- l + 1L
    } else {
      temp[i] <- right[r]; r <- r + 1L
    }
  }
  temp
}
merge_sort <- function(x) {
  n <- length(x)
  if (n <= 1) return(x)
  mid <- n %/% 2L
  smerge(merge_sort(x[1:mid]), merge_sort(x[(mid + 1):n]))
}

예측해 보자

원소 수를 두 배로 늘리면 각 정렬의 비교 횟수는 몇 배가 되겠는가?

A 둘 다 두 배

B 버블 네 배 · 병합 두 배 남짓

C 둘 다 네 배

실행 시간은 하드웨어와 부하에 따라 변동하고, 빠른 쪽은 0초로 측정되어 증가율을 계산할 수 없다. 비교 횟수는 입력이 동일하면 항상 같은 값을 갖는다.

비교 횟수는 이론값과 일치한다

n 버블 n(n-1)/2 병합 n log2(n)
500 124,750 124,750 4,488 4,483
1,000 499,500 499,500 9,976 9,966
2,000 1,999,000 1,999,000 21,952 21,932

\(n\) 이 두 배가 될 때 버블 정렬은 정확히 네 배, 병합 정렬은 두 배를 조금 넘는 수준으로 증가한다. 버블 정렬의 비교 횟수는 \(n(n-1)/2\) 와 정확히 일치하고, 병합 정렬은 \(n\log_2 n\) 에 근접한다.

이론적으로 분석한 복잡도가 실제 연산 횟수와 일치하는지 확인하는 것 역시 검증이다.

5 · 뉴턴-랩슨 알고리즘

원리와 점화식

\(f(x) = 0\) 을 만족하는 \(x\) 를 반복 계산으로 구한다. 통계학에서 최대가능도추정량을 구할 때 사용하는 방법이 바로 이것이다.

  1. 초기값 \(x_0\) 을 설정한다
  2. \(x_n\) 에서 접선을 구한다
  3. 접선이 \(x\) 축과 만나는 점을 \(x_{n+1}\) 로 정한다
  4. 종료 조건까지 2~3을 반복한다

\[x_{n+1} = x_n - \frac{f(x_n)}{f'(x_n)}\]

종료 조건 — 다음 세 가지를 함께 사용한다.

  • 최대 반복 횟수를 초과한 경우
  • \(x\) 의 갱신 폭이 충분히 작아진 경우
  • \(|f(x)|\) 가 허용 오차 이내로 0에 근접한 경우

구현과 검증

f <- function(x) 5 * x^3 - 7 * x^2 - 40 * x + 100
sol <- newton_raphson(f, x0 = 1, range = c(-10, 10))
unlist(sol)
     solution     iteration         value

주의

뉴턴-랩슨 알고리즘은 수렴 속도가 빠르지만 초기값에 민감하다. 기울기가 0에 가까운 지점에서 출발하면 다음 근사값이 크게 벗어나고, \(f'(x) = 0\) 이면 점화식을 계산할 수 없다.

결과를 얻은 뒤에는 그 값이 실제로 해인지, 그리고 의도한 해가 맞는지를 반드시 확인해야 한다.

6 · AI와 함께: 생성 코드의 검증

프롬프트는 곧 요구사항이다

중요

작업 요구사항

오름차순으로 정렬된 수치형 벡터 vec 과 값 target 을 받아, target 이 있으면 그 위치를, 없으면 NA 를 반환하는 재귀 이진 탐색 함수를 R 로 작성하라.

# 생성: Claude Opus 5, 2026-09-11. 수정 없이 그대로 수록.
binary_search_rec <- function(vec, target, lo = 1, hi = length(vec)) {
  if (lo > hi) return(NA_integer_)
  mid <- (lo + hi) %/% 2
  if (vec[mid] == target) return(mid)
  else if (vec[mid] > target) binary_search_rec(vec, target, lo, mid - 1)
  else binary_search_rec(vec, target, mid + 1, hi)
}

앞 절에서 수정한 구현과 동일한 구조다. 그럼에도 검증 절차를 수행한다.

세 가지 검증

v <- seq(1, 40, by = 3)

# 1. 전수 검사
c1 <- all(vapply(seq_along(v), function(i) as.integer(binary_search_rec(v, v[i])),
                 integer(1)) == seq_along(v))

# 2. 경계 사례 — 빈 벡터, 길이 1인 벡터, 존재하지 않는 값
c2 <- all(is.na(c(binary_search_rec(numeric(0), 5), binary_search_rec(7, 9))))

# 3. 무작위 대조 — 정답이 알려진 which() 와 500회 대조
set.seed(20260911)
c3 <- all(replicate(500, {
  w <- sort(sample(1:200, sample(1:60, 1)))
  k <- sample(1:200, 1)
  got <- binary_search_rec(w, k); want <- which(w == k)
  if (length(want) == 0) is.na(got) else (!is.na(got) && got %in% want)
}))

c(전수검사 = c1, 경계사례 = c2, 무작위대조 = c3)
  전수검사   경계사례 무작위대조 
      TRUE       TRUE       TRUE

세 가지 검증을 모두 통과했다. 요구사항의 범위 안에서는 이 코드가 옳다.

요구사항이 규정하지 않은 부분

d <- c(1, 3, 3, 3, 5, 7)
c(이_구현 = binary_search_rec(d, 3), R의_match = match(3, d))   # 중복값
  이_구현 R의_match 
        3         2 
u <- c(19, 7, 2, 15, 10)                                        # 정렬 안 된 입력
c(반환 = binary_search_rec(u, 19), 실제_위치 = which(u == 19))
     반환 실제_위치 
       NA         1

정렬되지 않은 입력에 대해 오류나 경고 없이 값이 존재하지 않는다고 반환한다.

오류 없이 잘못된 결과를 반환하는 편이 명시적으로 실패하는 편보다 훨씬 위험하다.

AI 생성 코드에서 자주 나타나는 오류

주의

  • 경계 조건 — < 와 <=, mid 와 mid - 1 을 혼동한다. 이 수업의 rbinary_search() 가 정확히 이 유형이며, 사람이 작성한 코드에서도 동일하게 나타난다.
  • 전제 미검사 — “정렬되어 있다”, “NA 가 없다”와 같은 전제를 확인하지 않는다.
  • 빈 입력 — 길이가 0인 벡터에서 인덱스 1을 참조한다.
  • 요구사항의 공백 — 중복값이나 동점 처리처럼 규정되지 않은 부분을 임의로 결정하고, 그 선택을 명시하지 않는다.

공통점은 오류 메시지가 출력되지 않는다는 점이다. 따라서 실행해 보는 것만으로는 부족하며 별도의 검증 절차가 필요하다.

정리

비용

  • 같은 결과를 내는 코드도 비용의 증가율이 다르다
  • 성능은 최악의 경우를 기준으로 평가한다
  • 차수가 다르면 하드웨어로 해결되지 않는다

재귀

  • 종료 조건과 재귀 단계, 두 부분으로 이루어진다
  • 가독성을 얻는 대신 스택 프레임을 소비한다

검증

  • 예제 몇 개를 통과하는 것은 정확성의 근거가 아니다
  • 전수 검사 · 경계 사례 · 정답이 알려진 기준과의 대조
  • 오류 메시지가 없는 결함은 절차로만 발견된다
