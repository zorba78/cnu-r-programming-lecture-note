학습 목표

  • 일상의 절차를 알고리즘의 다섯 조건(명확성·유일성·입력과 출력·유한성·일반성)에 맞추어 기술하고, 조건을 어기는 부분을 찾아낼 수 있다.
  • 동일한 결과를 산출하는 두 코드가 요구하는 수행 시간과 메모리의 차이를 설명하고, 어느 쪽이 왜 효율적인지 근거를 제시할 수 있다.
  • 반복문의 시간 복잡도를 빅오 표기법(\(\mathcal{O}\))으로 표현하고, 코드로부터 복잡도의 차수를 판별할 수 있다.
  • 재귀 함수의 종료 조건을 정확히 규정하고, 그 조건이 성립하지 않는 입력을 스스로 구성해 확인할 수 있다.
  • 탐색·정렬 알고리즘을 구현하고, 구현의 정확성을 전수 검사와 경계 사례로 검증할 수 있다.
  • 정렬 알고리즘 네 가지(버블·삽입·병합·퀵)의 비교 횟수를 직접 세어, 같은 알고리즘이라도 입력의 상태에 따라 비용이 달라짐을 설명할 수 있다.
  • 회귀계수 추정을 최적화 문제로 보고 뉴턴-랩슨 알고리즘으로 계수를 구한 뒤 lm()·glm() 과 대조할 수 있으며, 경사하강법과의 차이를 비용의 관점에서 설명할 수 있다.
  • 사람이 작성한 코드와 AI 가 생성한 코드 모두에서, 타당해 보이는 구현의 잘못된 경계 처리를 찾아낼 수 있다.

이 장의 목적은 알고리즘을 암기하는 데 있지 않고, 어떤 코드가 왜 더 많은 수행 시간과 메모리를 요구하는지 판단하는 능력을 기르는 데 있다. 알고리즘을 직접 구현할 일은 점차 줄어들지만, 주어진 코드가 입력 규모가 커진 상황에서도 유효한지 판단할 일은 오히려 늘어난다. 이 장에서는 그 판단에 필요한 최소한의 도구를 다룬다.

1 알고리즘과 계산 비용

1.1 일상의 절차에서 알고리즘으로

알고리즘(algorithm)이라는 말은 낯설게 들리지만, 우리는 매일 알고리즘을 실행한다. 라면을 끓이는 순서, 처음 가는 건물에서 강의실을 찾아가는 방법, 사전에서 단어를 찾는 방법이 모두 문제를 해결하기 위해 정해 둔 일련의 절차다. 컴퓨터 과학에서 말하는 알고리즘도 다르지 않다. 다른 점은 그 절차를 누가 실행해도 같은 결과가 나오도록 약속해 둔다는 데 있다. 이 소절에서는 두 가지 일상의 예로 그 약속이 무엇인지 살펴본다.

예 1: 전화번호부에서 이름 찾기

스마트폰이 없던 시절에는 집마다 두꺼운 전화번호부가 있었다. 이름이 가나다순으로 인쇄된 1,000쪽짜리 전화번호부에서 ’이아무개’의 번호를 찾는다고 하자. 두 가지 방법을 생각할 수 있다.

방법 A: 한 쪽씩 넘기기 방법 B: 가운데 펼치기
1단계 첫 쪽을 편다. 남은 부분의 가운데 쪽을 편다.
2단계 찾는 이름이 있으면 멈춘다. 찾는 이름이 있으면 멈춘다.
3단계 없으면 다음 쪽으로 넘기고 2단계로 간다. 펼친 쪽의 이름이 ’이’보다 앞이면 뒤쪽 절반만, 뒤면 앞쪽 절반만 남기고 1단계로 간다.
1,000쪽일 때 최악의 경우 1,000쪽을 모두 확인한다. 최대 10번 펼치면 끝난다.

두 방법은 모두 ‘이아무개’를 찾아낸다. 결과는 같지만 드는 수고가 다르다. 이 절의 나머지 부분은 이 ’수고’, 즉 알고리즘의 비용을 재고 비교하는 방법을 다룬다.

방법 B 에는 전제가 하나 있다. 이름이 가나다순으로 정렬되어 있어야 한다. 동아리 가입 순서대로 적은 명단이라면 가운데를 펼쳐도 찾는 이름이 앞에 있는지 뒤에 있는지 알 수 없으므로 방법 B 를 쓸 수 없다. 이 전제는 섹션 3.2 의 이진 탐색에서 그대로 다시 등장한다.

힌트

예측해 보자: 전화번호부가 10,000쪽이라면 방법 B 로는 최대 몇 번 펼쳐야 하는가? 1,000쪽일 때 10번이었다. 실행하기 전에 답을 적어 보자.

한 번 펼칠 때마다 남은 쪽수가 절반으로 줄어드는 과정을 그대로 코드로 옮기면 다음과 같다.

# 방법 B: 남은 쪽의 가운데를 펼쳐 절반을 버리는 일을 한 쪽이 남을 때까지 반복한다
half_count <- function(pages) {
  count <- 0
  while (pages > 1) {
    pages <- ceiling(pages / 2)   # 찾는 이름이 없는 쪽 절반을 버린다
    count <- count + 1
  }
  count
}

sizes <- c(1000, 10000, 1000000)
data.frame(
  쪽수 = format(sizes, big.mark = ",", scientific = FALSE),
  방법A_최악 = format(sizes, big.mark = ",", scientific = FALSE),
  방법B_최대 = sapply(sizes, half_count)
)

쪽수가 10배로 늘어도 방법 B 로 펼치는 횟수는 4번밖에 늘지 않는다. 100만 쪽이라도 20번이면 충분하다. 반면 방법 A 의 수고는 쪽수에 정비례해 늘어난다. 이 차이가 섹션 1.4 에서 다루는 \(\mathcal{O}(n)\) 과 \(\mathcal{O}(\log n)\) 의 차이다.

노트

실제로 전화번호부를 펼칠 때 우리는 정확히 가운데를 펴지 않는다. ‘ㅇ’ 은 가나다순에서 뒤쪽에 있으므로 3분의 2 지점쯤을 짐작해 편다. 값의 분포를 이용해 펼칠 위치를 정하는 이 방법에도 이름이 있다. 보간 탐색(interpolation search)이다. 사람은 경험으로 절차를 다듬어 왔고, 그렇게 다듬어 약속한 절차가 곧 알고리즘이다.

예 2: 청소 로봇에게 청소 시키기

사람에게는 “방을 깨끗이 청소해”라는 한마디면 충분하다. 그러나 청소 로봇에게 이 말은 절차가 아니다. 어디서 시작하는가? 깨끗이는 어떤 상태인가? 언제 멈추는가? 사람은 이런 빈칸을 상식으로 채우지만 로봇은 채우지 못한다. 로봇에게는 빈칸 없이 약속된 절차가 필요하다.

  1. 방을 같은 크기의 칸으로 나누고, 왼쪽 위 칸에서 시작한다.
  2. 한 줄을 끝까지 이동하며 지나는 칸을 청소한다.
  3. 줄 끝에 닿으면 아래로 한 칸 내려가고, 이동 방향을 반대로 바꾼다.
  4. 마지막 줄의 끝 칸을 청소하면 멈춘다.

이 절차는 R 로 그대로 옮길 수 있다. 칸마다 몇 번째로 청소되는지를 행렬에 기록해 보자.

힌트

예측해 보자: 4행 6열의 방에서 2행 1열 칸은 몇 번째로 청소되는가? 실행하기 전에 답을 적어 보자.

clean_room <- function(n_row, n_col) {
  visit <- matrix(0L, nrow = n_row, ncol = n_col)   # 칸마다 청소한 순서를 기록
  step <- 0L
  for (i in seq_len(n_row)) {           # 1. 위에서부터 한 줄씩
    cols <- seq_len(n_col)
    if (i %% 2 == 0) cols <- rev(cols)  # 3. 짝수 번째 줄은 반대 방향
    for (j in cols) {                   # 2. 줄 끝까지 한 칸씩 이동
      step <- step + 1L
      visit[i, j] <- step
    }
  }
  visit                                 # 4. 마지막 칸을 지나면 종료
}

2행 1열은 12번째다. 둘째 줄은 오른쪽 끝(7번째)에서 출발해 왼쪽으로 이동하기 때문이다.

이 절차는 크기가 다른 방, 예컨대 clean_room(3, 10) 에도 그대로 적용된다. 그런데 방 한가운데 가구가 놓여 있다면 어떻게 될까? 이 함수에는 가구를 표현할 입력이 없다. 로봇은 가구 자리를 청소하려다 부딪히거나 그 자리에서 멈출 것이다. 가구가 놓인 방은 이 절차를 만든 사람이 떠올리지 못한 입력이다. 한편 “깨끗해질 때까지 청소하라”는 식으로 종료 조건을 정하면, 먼지 센서가 끝내 0을 가리키지 않는 한 로봇은 멈추지 않는다.

알고리즘의 조건

두 예를 바탕으로 알고리즘을 정의하면 다음과 같다.

노트

알고리즘(algorithm): 주어진 문제를 해결하기 위해 약속된 일련의 절차를 단계적으로 표현한 것. 여기서 ’약속’이란 사람이든 로봇이든 컴퓨터든, 누가 실행해도 같은 결과가 나오도록 각 단계를 미리 정해 둔다는 뜻이다.

알고리즘이라 부르려면 다음 다섯 조건을 만족해야 한다. 오른쪽 열은 앞의 청소 로봇 절차에서 각 조건이 무엇에 해당하는지를 보인다.

조건 뜻 청소 로봇에서
명확성 각 단계가 모호하지 않게 기술된다. “깨끗이”가 아니라 “모든 칸을 한 번씩 지난다”
유일성 각 단계의 다음 단계가 하나로 결정된다. 줄 끝에 닿으면 “아래로 한 칸, 방향 반대로” 하나뿐이다
입력과 출력 정의된 입력을 받아 결과를 산출한다. 방의 가로·세로 칸 수를 받아 칸별 청소 순서를 낸다
유한성 유한한 수의 단계를 거쳐 반드시 종료한다. 가로 × 세로 번 이동하면 끝난다
일반성 정의된 입력 전체에 대해 동작한다. 크기가 다른 방에서는 동작하지만, 가구가 놓인 방은 정의된 입력에 없다

이 가운데 실제 구현에서 가장 자주 위반되는 조건은 유한성과 일반성이다. “특정 예제에서 올바르게 동작한다”는 것과 “정의된 입력 전체에서 올바르게 동작한다”는 것은 전혀 다른 진술이며, 이 장에서는 그 차이를 반복해서 다룬다. 청소 로봇에게 가구 놓인 방이 그렇듯, 코드에도 그 코드를 만든 사람이 떠올리지 못한 입력이 들어온다.

1.2 구현에 따른 비용 차이

중요

이 장에서 말하는 비용(cost): 알고리즘이 요구하는 수행 시간과 메모리, 두 가지를 합쳐 부르는 말이다. 수행 시간은 시계로 잰 초가 아니라 연산 횟수로, 메모리는 동시에 확보해야 하는 공간의 크기로 잰다. “비용이 크다”고 할 때는 둘 중 어느 쪽인지 반드시 구분한다. 시간을 줄이기 위해 메모리를 더 쓰는 알고리즘(병합 정렬)이 이 장에 나온다.

아래 두 프로그램은 1부터 n 까지의 값을 담은 벡터를 생성한다. 두 결과는 완전히 동일하다.

힌트

예측해 보자: n 이 5만일 때 두 프로그램의 실행 시간은 얼마나 차이 나겠는가? 비슷한 수준인가, 두 배 정도인가, 그보다 큰가? 실행하기 전에 적어 보자.

# 프로그램 1: 벡터를 미리 할당한 뒤 각 위치에 값을 대입한다
prealloc_vec <- function(n) {
  x <- numeric(n)
  for (i in seq_len(n)) {
    x[i] <- i
  }
  x
}

# 프로그램 2: 반복할 때마다 벡터를 이어 붙여 길이를 늘린다
grow_vec <- function(n) {
  x <- NULL
  for (i in seq_len(n)) {
    x <- c(x, i)
  }
  x
}

# 두 결과가 동일한지 먼저 확인
identical(prealloc_vec(1000), as.numeric(grow_vec(1000)))
[1] TRUE

두 함수의 결과가 동일함을 확인했으므로 이제 비용을 측정한다.

n <- 50000
t1 <- system.time(prealloc_vec(n))[["elapsed"]]
t2 <- system.time(grow_vec(n))[["elapsed"]]

data.frame(
  방식 = c("사전 할당", "이어 붙이기"),
  초 = c(t1, t2)
)

예측과 일치하는가? 두 배 정도의 차이를 예상했다면 실제 결과와 상당한 차이가 있을 것이다. n 을 10배로 늘리면 격차는 다시 크게 벌어진다. x <- c(x, i) 는 반복마다 길이가 1 만큼 늘어난 새 벡터를 할당하고 기존 원소를 전부 복사한다. \(i\) 번째 반복에서 \(i\) 개를 복사하므로 전체 복사량은 \(1 + 2 + \cdots + n = n(n-1)/2\) 에 비례한다. 반면 사전 할당 방식은 이미 확보된 메모리에 값을 대입하므로 반복당 비용이 일정하다.

주의

흔한 오해: 결과가 같으면 두 코드가 동등하다고 판단하는 것. 두 프로그램의 출력은 완전히 동일하지만 비용의 증가율이 다르다. 입력이 작을 때는 이 차이가 드러나지 않다가, 실제 데이터 규모에서 급격히 나타난다.

1.3 시간 복잡도와 공간 복잡도

노트

시간 복잡도(time complexity): 알고리즘이 종료할 때까지 수행하는 연산의 횟수. 사칙연산, 비교연산, 반복, 함수 호출이 계수의 대상이다.

공간 복잡도(space complexity): 알고리즘이 종료할 때까지 필요한 메모리의 크기. 변수의 개수, 자료 구조의 크기, 함수 호출로 누적되는 스택 프레임이 대상이다.

앞 절의 두 프로그램을 이 용어로 기술하면 다음과 같다.

  • 프로그램 1: 반복이 \(n\) 회이므로 수행 시간은 \(n\) 에 비례한다. 벡터를 미리 할당한 뒤 대입만 하므로 추가 메모리는 증가하지 않는다.
  • 프로그램 2: 반복마다 복사가 발생하므로 수행 시간은 \(n^2\) 에 비례한다. 반복마다 새 벡터를 할당하므로 필요한 메모리도 \(n\) 까지 증가한다.

성능은 일반적으로 최악의 경우(worst case) 를 기준으로 평가한다. 최선의 경우는 특정 입력에서만 성립하고, 평균의 경우는 입력 분포를 가정해야 계산할 수 있는 반면, 최악의 경우는 임의의 입력에 대해 항상 성립하는 상한을 제공하기 때문이다.

1.4 빅오 표기법

입력 크기를 \(n\), 연산 횟수를 \(f(n)\) 이라 하자. \(n\) 이 충분히 커지면 \(f(n)\) 의 저차항은 영향력을 잃고 증가율이 가장 큰 항만 남는다. 이러한 점근적 증가율을 나타내는 표기가 빅오 표기법이다.

노트

정의: \(x \geq k\) 인 모든 \(x\) 에 대해 \(|f(x)| \leq C|g(x)|\) 를 만족하는 상수 \(k\) 와 \(C\) 가 존재하면 \(f(x) = \mathcal{O}(g(x))\) 라 하고 “\(f\) 는 \(g\) 의 빅오”라고 읽는다.

즉 \(g\) 는 \(f\) 의 점근적 상한이다. 임의의 입력에 대해 \(f\) 는 \(Cg\) 를 넘지 않는다.

코드를 분석할 때 실제로 사용하는 것은 정의 자체보다 다음 세 규칙이다.

힌트

규칙 1 (계수 법칙): \(C > 0\) 이면 \(C f(n) = \mathcal{O}(g(n))\). \(\rightarrow\) 반복 횟수가 \(5n\) 이든 \(100n\) 이든 모두 \(\mathcal{O}(n)\) 이다.

규칙 2 (합의 법칙): 두 부분이 순차적으로 실행되면 증가율이 큰 쪽만 남는다. \(\rightarrow\) \(\mathcal{O}(n) + \mathcal{O}(n^2) = \mathcal{O}(n^2)\). 단, 입력 변수가 서로 다르면 하나로 합쳐지지 않는다. \(\rightarrow\) \(\mathcal{O}(n + m)\).

규칙 3 (곱의 법칙): 반복문이 중첩되면 각 반복 횟수를 곱한다. \(\rightarrow\) \(\mathcal{O}(n) \times \mathcal{O}(n) = \mathcal{O}(n^2)\).

이 세 규칙을 코드에 적용해 보자.

힌트

예측해 보자: 아래 네 함수의 시간 복잡도를 각각 적어 보자. 코드를 실행할 필요는 없으며, 반복 횟수만 세면 된다.

case1 <- function(n) {           # (가)
  s <- 0
  for (i in seq_len(n)) s <- s + i
  s
}

case2 <- function(n) {           # (나)
  s <- 0
  for (i in seq_len(5 * n)) s <- s + i
  s
}

case3 <- function(n, m) {        # (다)
  s <- 0
  for (i in seq_len(n)) s <- s + i
  for (j in seq_len(m)) s <- s + j
  s

case4 <- function(n) {           # (라)
  s <- 0
  for (i in seq_len(n)) {

2 재귀

재귀 함수(recursive function) 는 자기 자신을 호출하는 함수다. 분할 정복과 같이 원래 문제를 동일한 구조의 더 작은 문제로 환원할 수 있는 경우, 반복문보다 간결하게 표현된다.

일반적인 함수 호출은 호출 지점으로 복귀하는 구조를 갖는다.

재귀 호출 역시 호출 지점으로 복귀하지만, 그 지점이 자기 자신이라는 점이 다르다. 호출할 때마다 호출 스택(call stack)에 새로운 프레임이 누적되므로, 이를 중단시키는 조건이 없으면 함수는 종료되지 않는다.

2.1 재귀 함수의 구성

모든 재귀 함수는 두 부분으로 이루어진다.

  1. 종료 조건(base case): 더 이상 분할하지 않고 결과를 직접 반환하는 경우.
  2. 재귀 단계(recursive step): 문제의 크기를 줄여 자기 자신을 호출하는 경우.

1부터 n 까지의 합을 구하는 함수로 확인해 보자.

recursive_sum <- function(n) {
  if (n == 1) return(n)            # 종료 조건
  n + recursive_sum(n - 1)         # 재귀 단계
}

recursive_sum(3)
[1] 6
  • recursive_sum(3) 은 n 이 1이 아니므로 recursive_sum(2) 를 호출한다.
  • recursive_sum(2) 는 같은 이유로 recursive_sum(1) 을 호출한다.
  • recursive_sum(1) 은 종료 조건을 만족하여 1을 반환한다.
  • 복귀하면서 2 + 1 = 3, 3 + 3 = 6 이 계산되어 최종적으로 6이 반환된다.

2.2 종료 조건의 한계

위 함수는 정상적으로 동작한다. 그렇다면 “정의된 입력 전체”에 대해서도 그러한가?

힌트

예측해 보자: recursive_sum(0) 은 무엇을 반환하겠는가? 0, 1, 오류 중 어느 것인지 실행하기 전에 답을 정해 두자.

# 이 호출은 종료되지 않는다. 발생하는 오류 메시지를 확인한다.
tryCatch(recursive_sum(0),
         error = function(e) cat("오류:", conditionMessage(e), "\n"))
오류: evaluation nested too deeply: infinite recursion / options(expressions=)?

n 이 0이면 n == 1 은 결코 참이 되지 않는다. 인수가 0, -1, -2, \ldots 로 계속 감소하다가 R 의 중첩 한계에 도달해서야 중단된다. 종료 조건은 “n 이 1일 때”가 아니라 “n 이 1 이하일 때”로 규정했어야 한다. 결함은 입력이 커질 때만 드러나는 것이 아니라, 정의역의 경계 바로 바깥에서도 드러난다.

입력 크기에 따른 한계도 확인해 두자.

recursive_sum(1000)          # 정상적으로 동작한다
[1] 500500
tryCatch(recursive_sum(5000),   # 중첩 한계
         error = function(e) cat("오류:", conditionMessage(e), "\n"))
오류: evaluation nested too deeply: infinite recursion / options(expressions=)?

재귀 호출은 호출마다 스택 프레임을 누적하므로 공간 복잡도가 \(\mathcal{O}(n)\) 이다. R 은 중첩 깊이를 options(expressions) 로 제한하며 기본값은 5000이다. 동일한 계산을 반복문으로 구현하면 공간 복잡도는 \(\mathcal{O}(1)\) 이고 깊이 제한도 없다.

두 문제를 함께 해결한 구현은 다음과 같다.

recursive_sum2 <- function(n) {
  if (n <= 1) return(n)            # 경계 조건을 포함한다
  n + recursive_sum2(n - 1)
}

c(recursive_sum2(0), recursive_sum2(1), recursive_sum2(100))
[1]    0    1 5050
# 반복문 구현: 공간 복잡도 O(1), 깊이 제한 없음
iterative_sum <- function(n) {
  s <- 0
  for (i in seq_len(n)) s <- s + i
  s
}

c(iterative_sum(0), iterative_sum(100), iterative_sum(100000))
[1]          0       5050 5000050000
주의

재귀는 가독성을 얻는 대신 메모리를 소비한다. 호출 깊이가 입력 크기에 비례하는 재귀는 R 에서 실무 코드로 사용하기 어렵다. 재귀 구조로 문제를 먼저 이해한 뒤, 필요하면 반복문으로 변환하는 순서가 안전하다.

2.3 계승

계승(factorial)은 재귀적 정의가 그대로 코드로 옮겨지는 대표적인 예다.

\[ n! = \begin{cases} n \times (n-1)!, & n \geq 1 \\ 1, & n = 0 \end{cases} \]

factorial_manual <- function(n) {
  if (n == 0) return(1)
  n * factorial_manual(n - 1)
}

factorial_manual(10)
[1] 3628800
factorial(10)        # R 내장 함수로 대조
[1] 3628800

직접 구현한 함수를 내장 함수와 대조하는 이 한 줄이 곧 검증이다. 구현했으면 반드시 정답이 알려진 기준과 대조한다.

2.4 하노이 탑

하노이 탑은 재귀 없이는 설명하기 어려운 대표적인 문제다. 기둥 세 개(A, B, C)와 크기가 다른 원판 \(n\) 개가 있고, 원판은 A 에 크기순으로 쌓여 있다. 모든 원판을 C 로 옮기되 (1) 한 번에 하나씩만 옮기고 (2) 큰 원판을 작은 원판 위에 올릴 수 없다.

해법의 핵심은 문제를 한 단계 작은 동일 문제로 환원하는 것이다. \(n\) 개를 A 에서 C 로 옮기는 작업은 다음 세 단계로 분해된다.

  1. 위쪽 \(n-1\) 개를 A 에서 B 로 옮긴다 (크기만 하나 작은 동일한 문제).
  2. 가장 큰 원판을 A 에서 C 로 옮긴다.
  3. B 에 있던 \(n-1\) 개를 B 에서 C 로 옮긴다 (역시 동일한 문제).
move_hanoi <- function(k, from, to, via) {
  if (k == 1) {
    cat(sprintf("원판 1: %s -> %s\n", from, to))
  } else {
    move_hanoi(k - 1, from = from, to = via, via = to)
    cat(sprintf("원판 %d: %s -> %s\n", k, from, to))
    move_hanoi(k - 1, from = via, to = to, via = from)
  }
}

move_hanoi(3, "A", "C", "B")
원판 1: A -> C
원판 2: A -> B
원판 1: C -> B
원판 3: A -> C
원판 1: B -> A
원판 2: B -> C
원판 1: A -> C

원판이 \(n\) 개일 때 필요한 이동 횟수는 \(2^n - 1\) 이다. 호출이 매 단계에서 두 개로 분기하기 때문이다. 즉 이 알고리즘의 시간 복잡도는 \(\mathcal{O}(2^n)\) 이며, 앞의 표에서 확인했듯 \(n\) 이 조금만 커져도 계산이 불가능해진다. 전설에 등장하는 원판 64개는 \(2^{64} - 1\) 회의 이동이 필요하며, 1초에 한 번씩 옮겨도 5천억 년이 넘게 걸린다.

count_moves <- function(k) if (k == 1) 1 else 2 * count_moves(k - 1) + 1

3 탐색 알고리즘

정렬된 자료에서 특정 값을 찾는 두 가지 방법을 비교한다. 이 절의 목적은 두 알고리즘을 암기하는 것이 아니라, 복잡도의 차수가 다르다는 사실이 실제로 어떤 차이를 만드는지 수치로 확인하는 것이다.

3.1 선형 탐색

첫 원소부터 순차적으로 비교한다. 가장 단순하며, 자료가 정렬되어 있지 않아도 적용할 수 있다.

linear_search <- function(target, vec) {
  for (i in seq_along(vec)) {
    if (vec[i] == target) return(i)
  }
  NA_integer_
}

set.seed(1)
x <- sort(sample(1:100, 20))

linear_search(target = x[13], vec = x)
[1] 13
linear_search(target = 101, vec = x)

목표값이 마지막 위치에 있거나 존재하지 않으면 \(n\) 회 모두 비교하게 된다. 따라서 최악의 경우 시간 복잡도는 \(\mathcal{O}(n)\) 이다.

3.2 이진 탐색

정렬된 벡터에서는 비교 횟수를 크게 줄일 수 있다. 중앙에 위치한 값과 목표값을 비교하여, 목표값이 더 작으면 오른쪽 절반을, 더 크면 왼쪽 절반을 탐색 범위에서 제외한다. 비교를 한 번 수행할 때마다 후보의 개수가 절반으로 줄어든다.

binary_search <- function(target, ovec) {
  lo <- 1L
  hi <- length(ovec)
  while (lo <= hi) {
    mid <- (lo + hi) %/% 2L
    if (ovec[mid] == target) {
      return(mid)
    } else if (ovec[mid] > target) {
      hi <- mid - 1L          # 오른쪽 절반을 탐색 범위에서 제외
    } else {
      lo <- mid + 1L          # 왼쪽 절반을 탐색 범위에서 제외
    }
  }
  NA_integer_
}

binary_search(target = x[13], ovec = x)
[1] 13
binary_search(target = 101, ovec = x)
[1] NA

비교 횟수에 따라 후보의 개수는 \(n, n/2, n/2^2, \ldots\) 로 감소한다. \(k\) 번째 비교에서 후보가 1개가 되므로 \(n/2^k = 1\) 이고, 양변에 밑이 2인 로그를 취하면 \(k = \log_2 n\) 을 얻는다. 따라서 이진 탐색의 시간 복잡도는 \(\mathcal{O}(\log n)\) 이다.

3.3 구현의 정확성 검증

여기서 한 가지를 짚고 넘어가야 한다. 위 binary_search() 는 과연 올바른 구현인가? 예제 두 개를 통과했다는 사실이 보장하는 것은 그 두 예제에 대한 정확성뿐이다.

검증의 출발점은 전수 검사다. 벡터의 모든 원소를 차례로 목표값으로 입력하고, 반환된 위치가 실제 위치와 일치하는지 확인한다.

checks <- vapply(seq_along(x), function(i) {
  binary_search(target = x[i], ovec = x) == i
}, logical(1))

all(checks)
[1] TRUE
sum(!checks)
[1] 0

모든 원소에 대해 통과했다. 이번에는 동일한 알고리즘을 재귀로 작성한 구현을 살펴본다. 아래 구현에는 결함이 있다. 어느 부분이 잘못되었는지 찾아보자.

힌트

예측해 보자: 아래 rbinary_search() 에 벡터의 모든 원소를 입력하면 몇 개나 정확히 찾아내겠는가? 전부인가, 절반인가, 아니면 하나도 찾지 못하는가?

rbinary_search <- function(target, ovec, minL, maxL) {
  if (maxL <= minL) return(NA_integer_)
  midL <- floor((minL + maxL) / 2)
  if (ovec[midL] > target) {
    rbinary_search(target, ovec, minL = minL, maxL = midL - 1)
  } else if (ovec[midL] < target) {
    rbinary_search(target, ovec, minL = midL + 1, maxL = maxL)
  } else {
    return(midL)
  }
}

절반 가까이가 NA 로 반환되었다. 원인은 첫 줄의 if (maxL <= minL) return(NA_integer_) 이다. 탐색 범위가 원소 하나로 좁혀지면 minL == maxL 이 되는데, 이 조건은 남은 원소를 검사하지 않은 채 탐색을 종료한다. 탐색 범위가 실제로 비는 조건은 minL > maxL 이다.

rbinary_search2 <- function(target, ovec, lo = 1L, hi = length(ovec)) {
  if (lo > hi) return(NA_integer_)          # 탐색 범위가 비었을 때만 종료
  mid <- (lo + hi) %/% 2L
  if (ovec[mid] == target) {
    mid
  } else if (ovec[mid] > target) {
    rbinary_search2(target, ovec, lo, mid - 1L)
  } else {
    rbinary_search2(target, ovec, mid + 1L, hi)
  }
}

3.4 두 탐색의 비용 비교

이제 두 탐색 알고리즘의 비교 횟수를 직접 측정한다. 실행 시간 대신 연산 횟수를 계수하면 하드웨어 성능과 무관한 값을 얻을 수 있다.

count_linear <- function(target, vec) {
  n <- 0L
  for (i in seq_along(vec)) {
    n <- n + 1L
    if (vec[i] == target) return(n)
  }
  n
}

count_binary <- function(target, ovec) {
  lo <- 1L; hi <- length(ovec); n <- 0L
  while (lo <= hi) {
    n <- n + 1L
    mid <- (lo + hi) %/% 2L
    if (ovec[mid] == target) return(n)
    if (ovec[mid] > target) hi <- mid - 1L else lo <- mid + 1L
  }
  n
}

set.seed(1)
sizes <- c(100, 1000, 10000)

  v <- seq_len(n)
  ks <- sample(v, 100)
  c(선형 = mean(sapply(ks, count_linear, vec = v)),
    이진 = mean(sapply(ks, count_binary, ovec = v)),
    log2n = log2(n))

선형 탐색의 평균 비교 횟수는 \(n/2\) 에, 이진 탐색은 \(\log_2 n\) 에 근접한다. \(n\) 이 100에서 10,000으로 100배 증가할 때 선형 탐색은 약 100배 증가하지만, 이진 탐색은 두 배를 조금 넘는 수준에 그친다. \(n = 10^6\) 이면 선형 탐색은 평균 50만 회, 이진 탐색은 약 20회를 수행한다.

주의

이진 탐색이 항상 유리한 것은 아니다. 자료가 정렬되어 있어야 적용할 수 있고, 정렬 자체의 비용이 \(\mathcal{O}(n \log n)\) 이다. 탐색을 한 번만 수행한다면 정렬 후 이진 탐색을 적용하는 것보다 선형 탐색이 오히려 저렴하다. 탐색을 여러 번 반복할 때 비로소 정렬 비용이 상쇄된다.

4 정렬 알고리즘

정렬 알고리즘은 매우 다양하다. 이 장에서는 네 가지를 두 쌍으로 묶어 다룬다.

쌍 시간 복잡도 방식
버블 정렬 · 삽입 정렬 \(\mathcal{O}(n^2)\) 원소를 하나씩 비교하며 자리를 옮긴다
병합 정렬 · 퀵 정렬 평균 \(\mathcal{O}(n \log n)\) 문제를 나누어 재귀로 푸는 분할 정복

쌍과 쌍을 비교하면 차수의 차이가 드러난다. 쌍 안의 두 알고리즘을 비교하면 같은 차수라도 입력의 상태에 따라 비용이 달라진다는 사실이 드러난다. 이 절의 마지막 소절에서 네 알고리즘의 비교 횟수를 직접 세어 두 가지를 모두 확인한다.

노트

안정 정렬(stable sort): 값이 동일한 원소들의 상대적 순서가 정렬 후에도 유지되는 정렬. 데이터 프레임을 여러 열 기준으로 순차 정렬할 때 이 성질이 중요하다.

아래 네 알고리즘은 모두 오름차순 기준으로 설명하며, 입력은 NA 가 없는 수치형 벡터라고 전제한다. 참고로 sort() 는 기본값(na.last = NA)에서 NA 를 제거한 뒤 정렬한다.

4.1 버블 정렬

키 순서로 한 줄을 세우는데, 학생들은 바로 옆 사람과만 키를 비교할 수 있다고 하자. 앞사람이 더 크면 둘이 자리를 바꾼다. 줄의 처음부터 끝까지 한 번 훑으면 키가 가장 큰 학생이 맨 뒤로 밀려난다. 버블 정렬(bubble sort)은 이 방법 그대로다.

인접한 두 원소를 비교하여 순서가 어긋나 있으면 교환한다. 전체를 한 번 순회하면 가장 큰 값이 마지막 위치로 이동한다. 이 과정을 \(n-1\) 회 반복한다.

bubble_sort <- function(x) {
  n <- length(x)
  if (n < 2) return(x)
  for (i in seq_len(n - 1)) {
    for (j in seq_len(n - i)) {
      if (x[j] > x[j + 1]) {
        temp <- x[j]
        x[j] <- x[j + 1]
        x[j + 1] <- temp
      }
    }
  }
  x
}

비교 횟수는 \((n-1) + (n-2) + \cdots + 1 = n(n-1)/2\) 이므로 시간 복잡도는 \(\mathcal{O}(n^2)\) 이다. 이미 정렬된 입력에 대해서도 이 구현은 모든 비교를 수행한다. 구현이 단순하고 벡터 내부에서 교환이 이루어져 추가 공간이 \(\mathcal{O}(1)\) 이라는 장점이 있으나, 시간 복잡도가 치명적인 단점이다.

4.2 삽입 정렬

카드 게임에서 카드를 한 장씩 받아 손에 쥔다고 하자. 새 카드를 받을 때마다 이미 쥐고 있는 카드 사이에서 제자리를 찾아 끼워 넣는다. 손에 쥔 카드는 언제나 정렬된 상태이고, 마지막 카드를 끼워 넣으면 정렬이 끝난다. 삽입 정렬(insertion sort)은 이 방법 그대로다.

벡터의 앞부분 x[1:(i-1)] 이 ’손에 쥔 카드’다. i 번째 값을 key 로 꺼내 두고, 앞부분에서 key 보다 큰 값을 한 칸씩 뒤로 밀어 빈자리를 만든 뒤 그 자리에 key 를 넣는다.

insertion_sort <- function(x) {
  n <- length(x)
  if (n < 2) return(x)
  for (i in 2:n) {
    key <- x[i]                        # 이번에 끼워 넣을 값
    j <- i - 1
    while (j >= 1 && x[j] > key) {     # key 보다 큰 값을 한 칸씩 뒤로 민다
      x[j + 1] <- x[j]
      j <- j - 1
    }
    x[j + 1] <- key                    # 비워 둔 자리에 넣는다
  }
  x
}

while 의 조건 j >= 1 && x[j] > key 에서 앞쪽 검사가 경계를 지킨다. key 가 앞부분의 모든 값보다 작으면 j 가 0 까지 내려가는데, 이때 && 는 왼쪽이 FALSE 이므로 오른쪽 x[0] > key 를 계산하지 않는다. 이를 단락 평가(short-circuit evaluation) 라 한다. 앞쪽 검사를 빼면 어떻게 되는지 확인해 보자.

비교 횟수는 입력의 상태에 따라 크게 달라진다. 이미 정렬된 입력에서는 key 마다 바로 앞의 값과 한 번만 비교하고 멈추므로 모두 \(n-1\) 회로 끝난다. 역순으로 정렬된 입력에서는 key 가 매번 맨 앞까지 이동해야 하므로 \(1 + 2 + \cdots + (n-1) = n(n-1)/2\) 회를 비교한다. 최선의 경우 \(\mathcal{O}(n)\), 최악의 경우 \(\mathcal{O}(n^2)\) 이다. 버블 정렬처럼 벡터 안에서 자리만 옮기므로 추가 공간은 \(\mathcal{O}(1)\) 이다.

같은 \(\mathcal{O}(n^2)\) 이지만 거의 정렬된 자료에서는 삽입 정렬이 버블 정렬보다 훨씬 적게 비교한다. 그래서 실무에서 쓰는 정렬 함수 가운데에는 짧은 구간을 정렬할 때 삽입 정렬로 바꿔 쓰는 것이 많다. 파이썬의 기본 정렬 알고리즘인 팀정렬(Timsort)이 그 예다.

4.3 병합 정렬

두 반의 시험 답안지를 번호순으로 한 묶음으로 합친다고 하자. 두 묶음이 각각 번호순으로 정리되어 있다면 일은 간단하다. 두 묶음의 맨 위 장끼리 비교해 번호가 빠른 쪽을 한 장씩 내려놓으면 된다. 정리되지 않은 큰 묶음은 절반으로 나누어 각각 정리한 뒤 이렇게 합치면 되고, 절반도 크면 다시 절반으로 나눈다. 병합 정렬(merge sort)은 이 방법 그대로다.

분할 정복(divide and conquer) 기법을 사용한다. 벡터를 절반으로 분할하고, 각 부분을 재귀적으로 정렬한 뒤, 정렬된 두 부분을 병합한다. 실제 정렬이 이루어지는 단계는 분할 단계가 아니라 병합 단계다.

병합 함수부터 구현한다. 정렬된 두 벡터의 앞에서부터 작은 값을 차례로 선택하면 결과 역시 정렬된 상태로 채워진다.

smerge <- function(left, right) {
  temp <- numeric(length(left) + length(right))
  l <- r <- 1L
  for (i in seq_along(temp)) {
    # 오른쪽이 소진되었거나, 왼쪽이 남아 있고 그 값이 더 작거나 같으면 왼쪽을 선택한다
    if (r > length(right) ||
        (l <= length(left) && left[l] <= right[r])) {
      temp[i] <- left[l]
      l <- l + 1L
    } else {
      temp[i] <- right[r]
      r <- r + 1L
    }
  }
  temp
}

smerge(c(1, 4, 9), c(2, 3, 10))
[1]  1  2  3  4  9 10

left[l] <= right[r] 에서 <= 를 사용한 것이 안정성을 보장한다. 값이 동일한 경우 왼쪽, 즉 원래 앞에 있던 원소를 먼저 선택하기 때문이다.

분할 단계는 재귀로 구현한다.

merge_sort <- function(x) {
  n <- length(x)
  if (n <= 1) return(x)            # 종료 조건: 길이가 1 이하이면 이미 정렬된 상태다
  mid <- n %/% 2L
  smerge(merge_sort(x[1:mid]), merge_sort(x[(mid + 1):n]))
}

분할을 절반씩 반복하므로 재귀 깊이는 \(\log_2 n\) 이고, 각 깊이에서 원소 전체를 한 번씩 순회하므로 \(n\) 회의 연산이 필요하다. 따라서 시간 복잡도는 \(\mathcal{O}(n \log n)\) 이다. 다만 병합 결과를 담을 임시 벡터가 필요하므로 공간 복잡도는 \(\mathcal{O}(n)\) 이다. 시간과 공간을 맞바꾼 구조다.

4.4 퀵 정렬

체육 시간에 학생들을 키 순서로 세운다고 하자. 선생님이 먼저 한 학생을 기준으로 세우고, 그보다 작은 학생은 왼쪽, 큰 학생은 오른쪽으로 보낸다. 기준 학생은 이것으로 제자리에 선 셈이다. 이제 왼쪽 무리와 오른쪽 무리 안에서 각각 같은 일을 반복하고, 무리가 한 명 이하가 되면 멈춘다. 퀵 정렬(quick sort)은 이 방법 그대로다.

병합 정렬과 같은 분할 정복이지만 일이 일어나는 단계가 반대다. 병합 정렬은 나누는 일이 단순하고 합치는 단계에서 정렬이 일어난다. 퀵 정렬은 나누는 단계에서 정렬이 일어나고, 합치는 일은 작은 무리, 기준, 큰 무리를 차례로 이어 붙이는 것뿐이다. 기준이 되는 값을 기준값(pivot) 이라 한다. 여기서는 벡터의 첫 원소를 기준값으로 삼는다.

quick_sort <- function(x) {
  if (length(x) <= 1) return(x)      # 종료 조건: 원소가 하나 이하이면 이미 정렬된 상태다
  pivot <- x[1]                      # 첫 원소를 기준값으로 삼는다
  c(quick_sort(x[x < pivot]),        # 기준값보다 작은 무리를 정렬해 왼쪽에
    x[x == pivot],                   # 기준값(과 같은 값)을 가운데에
    quick_sort(x[x > pivot]))        # 기준값보다 큰 무리를 정렬해 오른쪽에
}

나누는 과정을 출력해 보자. 아래 quick_trace() 는 quick_sort() 와 같은 일을 하면서 호출마다 [작은 무리] 기준값 [큰 무리] 를 한 줄씩 출력한다. 들여쓰기가 재귀의 깊이다.

quick_trace <- function(x, depth = 0) {
  if (length(x) <= 1) return(x)
  pivot <- x[1]
  small <- x[x < pivot]
  big <- x[x > pivot]
  cat(strrep("  ", depth), "[", paste(small, collapse = " "), "] ", pivot,
      " [", paste(big, collapse = " "), "]\n", sep = "")
  c(quick_trace(small, depth + 1), x[x == pivot], quick_trace(big, depth + 1))
}

한 번 나눌 때마다 무리가 대략 절반씩 작아져 세 단계 만에 끝났다. 무작위 순서의 입력이라면 재귀 깊이는 대략 \(\log_2 n\) 에 비례하고, 각 깊이에서 모든 원소가 기준값과 한 번씩 비교되므로 평균 시간 복잡도는 병합 정렬과 같은 \(\mathcal{O}(n \log n)\) 이다.

첫 원소를 기준값으로 삼으면 정렬된 입력에서는 기준값이 늘 가장 작은 값이 된다. 작은 무리는 늘 비고, 큰 무리는 원소가 하나씩만 줄어든다. 재귀 깊이는 \(n - 1\) 이 되고, 비교 횟수는 \((n-1) + (n-2) + \cdots + 1 = n(n-1)/2\) 로 버블 정렬과 같아진다. 평균은 \(\mathcal{O}(n \log n)\) 이지만 최악은 \(\mathcal{O}(n^2)\) 이며, 그 최악이 하필 이미 정렬된 입력이다.

재귀 깊이가 \(n\) 에 비례하면 섹션 2.2 에서 본 중첩 한계에도 걸린다.

메모리도 따져 보자. 이 구현은 나눌 때마다 x[x < pivot] 과 x[x > pivot] 으로 새 벡터를 만들고, 호출이 끝날 때까지 각 깊이의 벡터가 동시에 메모리에 남는다. 무작위 입력에서는 깊이마다 벡터가 대략 절반씩 작아지므로 추가 공간이 \(\mathcal{O}(n)\) 이지만, 정렬된 입력에서는 \(n + (n-1) + \cdots\) 가 쌓여 \(\mathcal{O}(n^2)\) 까지 늘어난다. 읽기 쉬운 대신 메모리를 쓰는 구현이다. 교과서의 퀵 정렬은 대개 벡터 안에서 자리만 바꾸는 제자리(in-place) 방식으로 구현해 추가 공간을 재귀 호출에 필요한 만큼으로 줄인다. 대신 코드가 길고 경계 처리가 까다롭다.

노트

기준값을 고르는 규칙이 최악의 입력을 정한다. 가운데 원소를 기준값으로 삼으면 정렬된 입력은 최선의 경우가 되지만, 그 규칙에 불리한 다른 입력이 여전히 존재한다. 기준값을 무작위로 고르면 특정 입력이 늘 최악이 되는 일은 없어지는 대신, 같은 입력이라도 실행할 때마다 비교 횟수가 달라진다.

4.5 네 정렬의 비용 비교

힌트

예측해 보자: 원소 수를 두 배로 늘리면 네 정렬의 비교 횟수는 각각 몇 배가 되겠는가? 또 이미 정렬된 입력에서는 네 정렬 가운데 어느 것이 가장 적게, 어느 것이 가장 많이 비교하겠는가? 표를 보기 전에 적어 보자.

실행 시간 대신 비교 횟수를 측정한다. 실행 시간은 하드웨어 성능과 측정 시점의 부하에 따라 변동하며, 빠른 쪽은 0초로 측정되어 증가율을 계산할 수 없다. 반면 비교 횟수는 입력이 동일하면 항상 같은 값을 갖는다.

아래 네 함수는 각 정렬 함수에서 두 값을 비교하는 곳마다 1을 더하도록 고친 것이다. 퀵 정렬은 한 번 나눌 때 기준값과 나머지 원소를 한 번씩 비교한다고 보고 (원소 수 \(-\,1\)) 회로 센다.

비교 횟수를 세는 함수 네 개 (펼쳐 보기) 
bubble_count <- function(x) {
  n <- length(x)
  cnt <- 0
  for (i in seq_len(n - 1)) {
    for (j in seq_len(n - i)) {
      cnt <- cnt + 1
      if (x[j] > x[j + 1]) {
        temp <- x[j]; x[j] <- x[j + 1]; x[j + 1] <- temp
      }
    }
  }
  cnt
}

insertion_count <- function(x) {
  n <- length(x)
  cnt <- 0
  if (n < 2) return(cnt)
  for (i in 2:n) {
    key <- x[i]
    j <- i - 1
    while (j >= 1) {
      cnt <- cnt + 1                   # x[j] 와 key 를 비교한다
      if (x[j] <= key) break
      x[j + 1] <- x[j]
      j <- j - 1
    }
    x[j + 1] <- key
  }
  cnt
}

# 병합 단계의 비교 횟수는 두 부분을 정렬한 결과에 달려 있으므로
# 정렬 결과와 비교 횟수를 함께 돌려주는 내부 함수를 둔다
merge_count <- function(x) {
  sort_count <- function(x) {
    n <- length(x)
    if (n <= 1) return(list(x = x, cnt = 0))
    mid <- n %/% 2L
    a <- sort_count(x[1:mid])
    b <- sort_count(x[(mid + 1):n])
    left <- a$x
    right <- b$x
    out <- numeric(n)
    l <- r <- 1L
    cnt <- a$cnt + b$cnt
    for (i in seq_len(n)) {
      both <- l <= length(left) && r <= length(right)
      if (both) cnt <- cnt + 1         # 양쪽이 모두 남아 있을 때만 비교한다
      if ((both && left[l] <= right[r]) || r > length(right)) {
        out[i] <- left[l]; l <- l + 1L
      } else {
        out[i] <- right[r]; r <- r + 1L
      }
    }
    list(x = out, cnt = cnt)
  }
  sort_count(x)$cnt
}

quick_count <- function(x) {
  if (length(x) <= 1) return(0)
  pivot <- x[1]
  (length(x) - 1) + quick_count(x[x < pivot]) + quick_count(x[x > pivot])
}

R 의 sort() 는 무엇을 쓰는가: 기본값 method = "auto" 는 길이가 \(2^{31}\) 보다 짧은 수치·정수·논리 벡터와 요인에는 기수 정렬(radix sort) 을, 그 밖의 경우(문자 벡터 등)에는 셸 정렬(Shellsort)을 쓴다(?sort). 기수 정렬은 원소끼리 비교하는 대신 값을 자릿수(바이트) 단위로 나누어 배치하는 방식이며, 도움말에 따르면 \(\mathcal{O}(n)\) 으로 동작한다. sort(x, method = "quick") 로 퀵 정렬을 지정할 수도 있다.

5 뉴턴-랩슨 알고리즘

앞의 절들이 자료를 처리하는 알고리즘을 다루었다면, 이 절에서는 수치 계산 알고리즘을 다룬다. \(f(x) = 0\) 을 만족하는 \(x\) 를 반복 계산으로 구하는 방법이다.

통계학에서 이 알고리즘이 중요한 이유는 추정이 곧 최적화(optimization) 문제이기 때문이다. 회귀계수의 최소제곱추정은 잔차제곱합을 최소로 만드는 값을, 최대가능도추정은 가능도를 최대로 만드는 값을 찾는다. 함수가 최소나 최대가 되는 지점에서는 도함수가 0 이므로, 결국 “도함수 \(= 0\)” 이라는 방정식을 푸는 문제가 된다. 이 절의 앞부분(섹션 5.1 부터 섹션 5.3 까지)에서 방정식의 해를 구하는 원리를 익히고, 뒷부분(섹션 5.4 부터 섹션 5.6 까지)에서 회귀모형과 로지스틱 회귀모형의 계수를 이 방법으로 구한다. 마지막으로 같은 문제를 푸는 또 다른 방법인 경사하강법을 간단히 소개한다(섹션 5.7).

적용 조건은 두 가지다. 탐색 구간에 해가 존재해야 하고, \(f\) 가 미분 가능해야 한다.

5.1 원리와 점화식

알고리즘의 진행은 다음 네 단계로 이루어진다.

  1. 초기값 \(x_0\) 을 설정한다.
  2. \(x_n\) 에서 접선을 구한다. 접선의 기울기는 \(f'(x_n)\) 이다.
  3. 접선이 \(x\) 축과 만나는 점을 다음 근사값 \(x_{n+1}\) 로 정한다.
  4. 종료 조건을 만족할 때까지 2~3을 반복한다.

\((x_n, f(x_n))\) 을 지나는 접선의 식은 \(y = f'(x_n)(x - x_n) + f(x_n)\) 이고, \(y = 0\) 인 \(x\) 를 풀면 다음 점화식을 얻는다.

\[ x_{n+1} = x_n - \frac{f(x_n)}{f'(x_n)} \]

이 점화식에 따르면 함수값이 0에서 멀수록 갱신 폭이 커지고, 기울기의 절대값이 클수록 갱신 폭이 작아진다. 종료 조건은 일반적으로 다음 세 가지를 함께 사용한다.

  • 최대 반복 횟수를 초과한 경우
  • \(x\) 의 갱신 폭이 충분히 작아진 경우
  • \(|f(x)|\) 가 허용 오차(tol) 이내로 0에 근접한 경우

5.2 구현

앞의 종료 조건 세 가지를 그대로 인수로 받는다. 도함수는 deriv() 로 함수 본문에서 직접 유도하며, 해가 존재하는 구간을 range 로 제한해 발산을 막는다.

newton_raphson <- function(FUN, x0 = 1, max_iters = 5000,
                           tol = 1e-9, range = c(-Inf, Inf)) {
  grads <- deriv(as.expression(body(FUN)), "x", function.arg = TRUE)
  iters <- 1L
  gap <- Inf

  while (iters < max_iters && abs(gap) > tol) {
    slope <- attr(grads(x0), "gradient")
    if (slope == 0) stop("미분계수가 0이므로 다음 근사값을 계산할 수 없다.")
    x_new <- x0 - FUN(x0) / slope
    if (x_new <= range[1]) x_new <- range[1]
    if (x_new >= range[2]) x_new <- range[2]
    gap <- FUN(x_new)
    iters <- iters + 1L
    x0 <- x_new
  }

  list(solution = x_new, iteration = iters, value = FUN(x_new))
}

5.4 최적화: 극값은 도함수의 근이다

미분 가능한 함수 \(f\) 가 어떤 점에서 극값을 가지면 그 점의 접선은 수평이다. 즉 도함수가 0 이다. 따라서 극값을 찾는 문제는 도함수 \(f'\) 의 근을 찾는 문제가 되고, 앞의 점화식에서 \(f\) 자리에 \(f'\) 을, \(f'\) 자리에 \(f''\) 을 넣으면 된다.

\[ x_{n+1} = x_n - \frac{f'(x_n)}{f''(x_n)} \]

앞에서 쓴 \(f(x) = 5x^3 - 7x^2 - 40x + 100\) 의 극값을 구해 보자. 도함수는 \(f'(x) = 15x^2 - 14x - 40\) 이다. 손으로 구한 도함수는 R 의 기호 미분 함수 D() 로 대조한다.

fp <- function(x) 15 * x^2 - 14 * x - 40     # 손으로 구한 f'(x)

D(body(f), "x")                               # R 이 기호 미분한 결과
5 * (3 * x^2) - 7 * (2 * x) - 40

출력된 식을 정리하면 손으로 구한 식과 같다. 이제 newton_raphson() 에 f 대신 fp 를 넣는다. 함수를 새로 만들 필요는 없다. newton_raphson() 이 안에서 fp 를 한 번 더 미분해 \(f''\) 을 얻는다.

모수가 두 개 이상이면 점화식의 각 자리가 벡터와 행렬로 바뀐다. 이어지는 두 소절에서 이 형태를 쓴다.

노트

모수가 여러 개일 때의 뉴턴-랩슨

\[ \boldsymbol{\theta}_{n+1} = \boldsymbol{\theta}_n - \mathbf{H}^{-1} \nabla f(\boldsymbol{\theta}_n) \]

  • \(\nabla f\) : 기울기 벡터(gradient). 각 모수로 편미분한 값을 모은 벡터이며, \(f'\) 의 자리다.
  • \(\mathbf{H}\) : 헤세 행렬(Hessian matrix). 2계 편미분을 모은 행렬이며, \(f''\) 의 자리다.
  • 나눗셈은 역행렬을 곱하는 것으로 바뀐다. R 에서는 역행렬을 직접 구하지 않고 solve(H, g) 로 연립방정식 \(\mathbf{H}\mathbf{d} = \nabla f\) 를 풀어 갱신량 \(\mathbf{d}\) 를 얻는다.

5.5 회귀모형: 정규방정식은 뉴턴-랩슨의 한 걸음이다

mtcars 의 연비(mpg)를 무게(wt)로 설명하는 단순선형회귀모형 \(y_i = \beta_0 + \beta_1 x_i + \varepsilon_i\) 를 생각하자. 최소제곱추정은 잔차제곱합

\[ S(\boldsymbol\beta) = \sum_{i=1}^{n} (y_i - \beta_0 - \beta_1 x_i)^2 = (\mathbf{y} - \mathbf{X}\boldsymbol\beta)^\top (\mathbf{y} - \mathbf{X}\boldsymbol\beta) \]

을 최소로 만드는 \(\boldsymbol\beta = (\beta_0, \beta_1)^\top\) 를 찾는다. \(\mathbf{X}\) 는 첫 열이 모두 1(절편)이고 둘째 열이 \(x_i\) 인 \(n \times 2\) 행렬이다. 기울기 벡터와 헤세 행렬은 다음과 같다.

\[ \nabla S = -2\mathbf{X}^\top(\mathbf{y} - \mathbf{X}\boldsymbol\beta), \qquad \mathbf{H} = 2\mathbf{X}^\top\mathbf{X} \]

힌트

예측해 보자: 초기값 \((0, 0)\) 에서 출발하면 뉴턴-랩슨 알고리즘은 몇 번 반복해야 수렴하겠는가? 초기값을 \((100, -50)\) 으로 바꾸면 어떻게 되겠는가?

\[ \boldsymbol\beta_1 = \boldsymbol\beta_0 + (\mathbf{X}^\top\mathbf{X})^{-1}\mathbf{X}^\top(\mathbf{y} - \mathbf{X}\boldsymbol\beta_0) = (\mathbf{X}^\top\mathbf{X})^{-1}\mathbf{X}^\top\mathbf{y} \]

5.6 로지스틱 회귀모형: 반복이 필요한 경우

반응변수가 0 또는 1 인 자료가 있다. 합격·불합격, 발병·비발병처럼 결과가 두 가지인 경우다. mtcars 의 am 은 변속기가 자동이면 0, 수동이면 1 이다. 무게가 변속기 종류와 관련이 있는지 보려면, 수동일 확률 \(p_i\) 를 무게 \(x_i\) 로 설명하는 로지스틱 회귀모형(logistic regression model) 을 쓴다.

\[ p_i = P(y_i = 1) = \frac{1}{1 + e^{-(\beta_0 + \beta_1 x_i)}} \]

계수는 로그가능도

\[ \ell(\boldsymbol\beta) = \sum_{i=1}^{n} \bigl\{ y_i \log p_i + (1 - y_i) \log (1 - p_i) \bigr\} \]

를 최대로 만드는 값으로 추정한다. 기울기 벡터와 헤세 행렬은 다음과 같다.

\[ \nabla \ell = \mathbf{X}^\top(\mathbf{y} - \mathbf{p}), \qquad \mathbf{H} = -\mathbf{X}^\top\mathbf{W}\mathbf{X}, \quad \mathbf{W} = \mathrm{diag}\{p_i(1 - p_i)\} \]

회귀모형과 달리 \(\mathbf{H}\) 안에 \(p_i\), 곧 \(\boldsymbol\beta\) 가 들어 있다. 걸음마다 헤세 행렬이 달라지므로 한 걸음에 끝나지 않고, \(\nabla \ell = \mathbf{0}\) 의 해를 손으로 구할 수도 없다. 반복 계산이 필요한 전형적인 경우다.

# 로그가능도: 반복마다 값이 커지는지 확인하는 데 쓴다
loglik <- function(beta, X, y) {
  p <- as.vector(1 / (1 + exp(-X %*% beta)))
  sum(y * log(p) + (1 - y) * log(1 - p))
}

logistic_nr <- function(X, y, beta = rep(0, ncol(X)),
                        tol = 1e-8, max_iters = 50) {
  history <- NULL
  for (iter in seq_len(max_iters)) {
    p <- as.vector(1 / (1 + exp(-X %*% beta)))   # 현재 계수에서 구한 확률
    g <- t(X) %*% (y - p)                         # 기울기 벡터
    H <- -t(X) %*% (X * (p * (1 - p)))            # 헤세 행렬: X 의 각 행에 p(1-p) 를 곱함
    step <- as.vector(solve(H, g))
    beta <- beta - step
    b <- setNames(beta, paste0("b", seq_along(beta) - 1))
    history <- rbind(history, c(반복 = iter, b, 로그가능도 = loglik(beta, X, y),
                                갱신폭 = max(abs(step))))
    if (max(abs(step)) < tol) break               # 계수가 더 움직이지 않으면 멈춘다
  }
  list(beta = beta, history = history)
}

5.7 경사하강법 맛보기

짙은 안개가 낀 산에서 골짜기로 내려가야 한다고 하자. 멀리는 보이지 않고 발밑의 경사만 느낄 수 있다. 가장 가파르게 내려가는 방향으로 한 걸음 옮기고, 그 자리에서 다시 경사를 느끼고 한 걸음 옮기는 일을 반복하면 언젠가 골짜기에 닿는다. 이것이 경사하강법(gradient descent) 이다.

\[ \boldsymbol\theta_{n+1} = \boldsymbol\theta_n - \eta \, \nabla f(\boldsymbol\theta_n) \]

기울기의 반대 방향으로 기울기의 \(\eta\) 배만큼 이동한다. \(\eta\) 를 학습률(learning rate) 이라 한다. 뉴턴-랩슨과 비교하면 헤세 행렬의 역행렬 \(\mathbf{H}^{-1}\) 자리에 상수 \(\eta\) 가 들어간 형태다. 곡률을 이용해 보폭을 정하는 대신 보폭을 사람이 정한다.

섹션 5.5 의 회귀계수를 경사하강법으로 구해 보자. 목적함수는 잔차제곱합을 \(n\) 으로 나눈 평균제곱오차로 둔다. 최소점은 같고 기울기의 크기만 작아진다.

힌트

예측해 보자: 뉴턴-랩슨은 이 문제를 한 걸음에 풀었다. 경사하강법은 몇 걸음이 필요하겠는가? 10걸음 안쪽, 100걸음 안쪽, 1,000걸음 이상 가운데 골라 보자.

gd_ls <- function(X, y, eta, beta = c(0, 0), tol = 1e-6, max_iters = 1e5) {
  n <- nrow(X)
  for (iter in seq_len(max_iters)) {
    g <- as.vector(-2 / n * t(X) %*% (y - X %*% beta))   # 평균제곱오차의 기울기
    if (sqrt(sum(g^2)) < tol) break        # 기울기가 거의 0 이면 도착
    beta <- beta - eta * g                 # 기울기 반대 방향으로 eta 배만큼
    if (max(abs(beta)) > 1e6) {            # 값이 끝없이 커지면 발산
      return(c(학습률 = eta, 반복 = iter, b0 = NA, b1 = NA))
    }
  }
  c(학습률 = eta, 반복 = iter, b0 = beta[1], b1 = beta[2])
}

학습률이 알맞으면 lm() 과 같은 값에 도착하지만 1,000걸음이 넘게 걸린다. 학습률을 줄이면 걸음이 더 늘고, 조금만 키워도(0.09) 골짜기를 넘나들며 점점 멀어져 발산한다. 알맞은 학습률의 범위는 문제마다 다르므로 대개 여러 값을 시험해 정한다.

걸음이 이렇게 많은데도 경사하강법을 쓰는 이유는 한 걸음의 비용에 있다.

모수가 1,000만 개라면 헤세 행렬의 원소는 \(10^{14}\) 개로, 저장하는 것조차 불가능하다. 대규모 언어 모형(LLM)을 비롯한 딥러닝 모형은 수십억 개가 넘는 모수를 가지며, 경사하강법을 변형한 방법(확률적 경사하강법, Adam 등)으로 학습한다. 걸음 수가 적은 알고리즘과 한 걸음이 싼 알고리즘 가운데 어느 쪽이 나은지는 문제의 크기가 정한다. 이 장 첫 절에서 말한 비용, 곧 수행 시간과 메모리를 함께 따지는 판단이다.

노트

이 소절은 경사하강법이라는 방법이 있다는 것과 뉴턴-랩슨과의 차이를 소개하는 데 그친다. 학습률을 자동으로 조정하는 방법, 자료의 일부만으로 기울기를 계산하는 확률적 경사하강법 등은 기계학습을 다루는 과목에서 배운다. R 에서 일반적인 최적화 문제는 optim() 으로 풀 수 있으며, method 인수로 헤세 행렬을 근사해 쓰는 준뉴턴법("BFGS")이나 기울기만 쓰는 켤레기울기법("CG") 등을 고를 수 있다.

6 AI와 함께: 생성 코드의 검증

중요

이 절의 목표: LLM 에 재귀 이진 탐색 함수의 생성을 요청하고, 생성된 코드를 전수 검사와 경계 사례로 검증한다. 섹션 3.3 에서 사람이 작성한 코드에 적용한 절차를 동일하게 AI 생성 코드에 적용한다.

6.1 작업 요구사항

프롬프트는 곧 요구사항이다. 요구사항이 불완전하면 그 부분은 구현자의 임의 판단으로 채워진다. 아래는 의도적으로 통상적인 수준으로만 작성한 요구사항이다.

오름차순으로 정렬된 수치형 벡터 vec 과 값 target 을 받아, target 이 있으면 그 위치(인덱스)를, 없으면 NA 를 반환하는 재귀 이진 탐색 함수를 R 로 작성하라.

6.2 AI 가 생성한 코드

아래는 위 요구사항으로 실제 생성된 응답이며 수정 없이 그대로 수록했다.

# 생성: Claude Opus 5, 2026-09-11. 수정 없이 그대로 수록.
binary_search_rec <- function(vec, target, lo = 1, hi = length(vec)) {
  if (lo > hi) return(NA_integer_)
  mid <- (lo + hi) %/% 2
  if (vec[mid] == target) {
    return(mid)
  } else if (vec[mid] > target) {
    binary_search_rec(vec, target, lo, mid - 1)
  } else {
    binary_search_rec(vec, target, mid + 1, hi)
  }
}

앞 절에서 수정한 구현과 동일한 구조이며, 종료 조건도 lo > hi 로 올바르게 지정되어 있다. 그럼에도 검증 절차를 수행한다.

6.3 검증

검증 1. 전수 검사 — 벡터의 모든 원소를 목표값으로 입력한다.

x <- seq(1, 40, by = 3)
found <- vapply(seq_along(x), function(i) {
  as.integer(binary_search_rec(x, x[i]))
}, integer(1))

  길이1적중 = binary_search_rec(7, 7),
  길이1불발 = binary_search_rec(7, 9),

검증 3. 무작위 대조 — 정답이 알려진 which() 와 500회 대조한다.

set.seed(20260911)
n_fail <- 0
for (i in 1:500) {
  n <- sample(1:60, 1)
  v <- sort(sample(1:200, n))
  k <- if (runif(1) < 0.7) sample(v, 1) else sample(1:200, 1)
  got <- binary_search_rec(v, k)

세 가지 검증을 모두 통과했다. 요구사항의 범위 안에서는 이 코드가 옳다. 문제는 요구사항이 규정하지 않은 영역에서 발생한다.

6.4 요구사항이 규정하지 않은 부분

미규정 1. 중복값이 있으면 어느 위치를 반환하는가? 요구사항에 규정되어 있지 않으므로 구현이 임의로 결정한다.

d <- c(1, 3, 3, 3, 5, 7)

binary_search_rec(d, 3)    # 이 구현이 반환한 위치
[1] 3
which(d == 3)              # 3이 존재하는 모든 위치
[1] 2 3 4
match(3, d)                # R 의 관례: 가장 앞
[1] 2

R 의 match() 는 가장 앞의 위치를 반환하지만, 이 구현은 중간 위치를 반환한다. 어느 쪽도 그 자체로 오류는 아니나, 호출하는 쪽이 앞의 위치를 기대했다면 오류가 된다.

미규정 2. 정렬되지 않은 입력이 들어오면 어떻게 되는가? 요구사항은 “정렬된 벡터”를 전제했으나, 그 전제가 성립하지 않을 때의 동작은 규정하지 않았다.

u <- c(19, 7, 2, 15, 10)      # 정렬되어 있지 않은 벡터

binary_search_rec(u, 19)      # 19 는 1번 위치에 존재한다
[1] NA
which(u == 19)
[1] 1

오류나 경고 없이 값이 존재하지 않는다고 반환한다. 오류 없이 잘못된 결과를 반환하는 편이 명시적으로 실패하는 편보다 훨씬 위험하다.

미규정 3. NA 가 포함되어 있으면 어떻게 되는가?

binary_search_rec(c(1, 3, NA, 7), 7)
Error in `if (vec[mid] == target) ...`:
! missing value where TRUE/FALSE needed

이 경우에는 오류가 발생하며 실행이 중단된다. 앞의 두 경우보다 오히려 바람직하다. 결함을 즉시 인지할 수 있기 때문이다.

요구사항의 전제를 강제하도록 방어 코드를 추가하면 다음과 같다.

binary_search_safe <- function(vec, target) {
  stopifnot(is.numeric(vec), length(target) == 1L)
  if (anyNA(vec)) stop("vec 에 NA 가 포함되어 있다.")
  if (is.unsorted(vec)) stop("vec 이 오름차순으로 정렬되어 있지 않다.")
  binary_search_rec(vec, target)
}

binary_search_safe(x, x[5])
[1] 5
binary_search_safe(u, 19)
Error in `binary_search_safe()`:
! vec 이 오름차순으로 정렬되어 있지 않다.
주의

AI 생성 코드에서 자주 나타나는 오류 유형

  • 경계 조건: < 와 <=, mid 와 mid - 1 을 혼동한다. 이 장의 rbinary_search() 가 정확히 이 유형이며, 사람이 작성한 코드에서도 동일하게 나타난다.
  • 전제 미검사: “정렬되어 있다”, “NA 가 없다”와 같은 전제를 확인하지 않는다.
  • 빈 입력: 길이가 0인 벡터에서 인덱스 1을 참조한다.
  • 요구사항의 공백: 중복값이나 동점 처리와 같이 요구사항이 규정하지 않은 부분을 임의로 결정하고, 그 선택을 명시하지 않는다.

이 유형들의 공통점은 오류 메시지가 출력되지 않는다는 점이다. 따라서 실행해 보는 것만으로는 부족하며 별도의 검증 절차가 필요하다.

6.5 연습

  1. 위 요구사항에 “중복값이 있으면 가장 앞 위치를 반환한다”는 조건을 추가하여 다시 요청하고, 생성된 코드가 그 조건을 충족하는지 match() 와 대조해 확인하시오.
  2. 두 사람이 코드를 교환한다. 상대의 binary_search_rec() 에 결함을 하나 삽입해 돌려주고, 서로 전수 검사로 찾아내시오. 몇 번째 검증에서 발견했는지 기록하시오.

- 정렬 알고리즘 네 가지(버블·삽입·병합·퀵)의 비교 횟수를 직접 세어, 같은 알고리즘이라도 **입력의 상태에 따라 비용이 달라짐**을 설명할 수 있다.
- 회귀계수 추정을 **최적화 문제**로 보고 뉴턴-랩슨 알고리즘으로 계수를 구한 뒤 `lm()`·`glm()` 과 대조할 수 있으며, 경사하강법과의 차이를 비용의 관점에서 설명할 수 있다.
- 사람이 작성한 코드와 AI 가 생성한 코드 모두에서, 타당해 보이는 구현의 **잘못된 경계 처리**를 찾아낼 수 있다.

메모리를 요구하는지 판단하는 능력**을 기르는 데 있다. 알고리즘을 직접 구현할 일은 점차 줄어들지만,
주어진 코드가 입력 규모가 커진 상황에서도 유효한지 판단할 일은 오히려 늘어난다.
이 장에서는 그 판단에 필요한 최소한의 도구를 다룬다.


## 알고리즘과 계산 비용 {#sec-algo-cost}


### 일상의 절차에서 알고리즘으로 {#sec-everyday-algorithm}

알고리즘(algorithm)이라는 말은 낯설게 들리지만, 우리는 매일 알고리즘을 실행한다.
라면을 끓이는 순서, 처음 가는 건물에서 강의실을 찾아가는 방법, 사전에서 단어를 찾는 방법이
모두 **문제를 해결하기 위해 정해 둔 일련의 절차**다. 컴퓨터 과학에서 말하는 알고리즘도 다르지 않다.
다른 점은 그 절차를 **누가 실행해도 같은 결과가 나오도록 약속해 둔다**는 데 있다.
이 소절에서는 두 가지 일상의 예로 그 약속이 무엇인지 살펴본다.


#### 예 1: 전화번호부에서 이름 찾기 {.unnumbered}

스마트폰이 없던 시절에는 집마다 두꺼운 전화번호부가 있었다. 이름이 가나다순으로 인쇄된
1,000쪽짜리 전화번호부에서 '이아무개'의 번호를 찾는다고 하자. 두 가지 방법을 생각할 수 있다.

| | 방법 A: 한 쪽씩 넘기기 | 방법 B: 가운데 펼치기 |
|:--|:--|:--|
| 1단계 | 첫 쪽을 편다. | 남은 부분의 가운데 쪽을 편다. |
| 2단계 | 찾는 이름이 있으면 멈춘다. | 찾는 이름이 있으면 멈춘다. |
| 3단계 | 없으면 다음 쪽으로 넘기고 2단계로 간다. | 펼친 쪽의 이름이 '이'보다 앞이면 뒤쪽 절반만, 뒤면 앞쪽 절반만 남기고 1단계로 간다. |
| 1,000쪽일 때 | 최악의 경우 1,000쪽을 모두 확인한다. | 최대 10번 펼치면 끝난다. |

: {tbl-colwidths="[16,36,48]"}

두 방법은 모두 '이아무개'를 찾아낸다. **결과는 같지만 드는 수고가 다르다.**
이 절의 나머지 부분은 이 '수고', 즉 알고리즘의 **비용**을 재고 비교하는 방법을 다룬다.

방법 B 에는 전제가 하나 있다. 이름이 **가나다순으로 정렬**되어 있어야 한다.
동아리 가입 순서대로 적은 명단이라면 가운데를 펼쳐도 찾는 이름이 앞에 있는지 뒤에 있는지
알 수 없으므로 방법 B 를 쓸 수 없다. 이 전제는 @sec-binary-search 의 이진 탐색에서 그대로 다시 등장한다.


::: {.callout-tip}
**예측해 보자**: 전화번호부가 10,000쪽이라면 방법 B 로는 최대 몇 번 펼쳐야 하는가?
1,000쪽일 때 10번이었다. 실행하기 전에 답을 적어 보자.

:::


한 번 펼칠 때마다 남은 쪽수가 절반으로 줄어드는 과정을 그대로 코드로 옮기면 다음과 같다.


```{r phonebook-halving}
# 방법 B: 남은 쪽의 가운데를 펼쳐 절반을 버리는 일을 한 쪽이 남을 때까지 반복한다
half_count <- function(pages) {
  count <- 0
  while (pages > 1) {
    pages <- ceiling(pages / 2)   # 찾는 이름이 없는 쪽 절반을 버린다
    count <- count + 1
  }
  count
}

sizes <- c(1000, 10000, 1000000)
data.frame(
  쪽수 = format(sizes, big.mark = ",", scientific = FALSE),
  방법A_최악 = format(sizes, big.mark = ",", scientific = FALSE),
  방법B_최대 = sapply(sizes, half_count)
)

```


쪽수가 10배로 늘어도 방법 B 로 펼치는 횟수는 4번밖에 늘지 않는다.
100만 쪽이라도 20번이면 충분하다. 반면 방법 A 의 수고는 쪽수에 정비례해 늘어난다.
이 차이가 @sec-big-o 에서 다루는 $\mathcal{O}(n)$ 과 $\mathcal{O}(\log n)$ 의 차이다.


::: {.callout-note}
실제로 전화번호부를 펼칠 때 우리는 정확히 가운데를 펴지 않는다. 'ㅇ' 은 가나다순에서 뒤쪽에
있으므로 3분의 2 지점쯤을 짐작해 편다. 값의 분포를 이용해 펼칠 위치를 정하는 이 방법에도
이름이 있다. **보간 탐색(interpolation search)**이다. 사람은 경험으로 절차를 다듬어 왔고,
그렇게 다듬어 약속한 절차가 곧 알고리즘이다.

:::


#### 예 2: 청소 로봇에게 청소 시키기 {.unnumbered}

사람에게는 "방을 깨끗이 청소해"라는 한마디면 충분하다. 그러나 청소 로봇에게 이 말은 절차가 아니다.
**어디서** 시작하는가? **깨끗이**는 어떤 상태인가? **언제** 멈추는가? 사람은 이런 빈칸을
상식으로 채우지만 로봇은 채우지 못한다. 로봇에게는 빈칸 없이 약속된 절차가 필요하다.

1. 방을 같은 크기의 칸으로 나누고, 왼쪽 위 칸에서 시작한다.
2. 한 줄을 끝까지 이동하며 지나는 칸을 청소한다.
3. 줄 끝에 닿으면 아래로 한 칸 내려가고, 이동 방향을 반대로 바꾼다.
4. 마지막 줄의 끝 칸을 청소하면 멈춘다.

이 절차는 R 로 그대로 옮길 수 있다. 칸마다 몇 번째로 청소되는지를 행렬에 기록해 보자.


::: {.callout-tip}
**예측해 보자**: 4행 6열의 방에서 2행 1열 칸은 몇 번째로 청소되는가? 실행하기 전에 답을 적어 보자.

:::


```{r clean-room}
clean_room <- function(n_row, n_col) {
  visit <- matrix(0L, nrow = n_row, ncol = n_col)   # 칸마다 청소한 순서를 기록
  step <- 0L
  for (i in seq_len(n_row)) {           # 1. 위에서부터 한 줄씩
    cols <- seq_len(n_col)
    if (i %% 2 == 0) cols <- rev(cols)  # 3. 짝수 번째 줄은 반대 방향
    for (j in cols) {                   # 2. 줄 끝까지 한 칸씩 이동
      step <- step + 1L
      visit[i, j] <- step
    }
  }
  visit                                 # 4. 마지막 칸을 지나면 종료
}

clean_room(4, 6)

```


2행 1열은 12번째다. 둘째 줄은 오른쪽 끝(7번째)에서 출발해 왼쪽으로 이동하기 때문이다.

이 절차는 크기가 다른 방, 예컨대 `clean_room(3, 10)` 에도 그대로 적용된다. 그런데 방 한가운데
**가구**가 놓여 있다면 어떻게 될까? 이 함수에는 가구를 표현할 입력이 없다. 로봇은 가구 자리를
청소하려다 부딪히거나 그 자리에서 멈출 것이다. 가구가 놓인 방은 이 절차를 만든 사람이
**떠올리지 못한 입력**이다. 한편 "깨끗해질 때까지 청소하라"는 식으로 종료 조건을 정하면,
먼지 센서가 끝내 0을 가리키지 않는 한 로봇은 멈추지 않는다.


#### 알고리즘의 조건 {.unnumbered}

두 예를 바탕으로 알고리즘을 정의하면 다음과 같다.


::: {.callout-note}
**알고리즘(algorithm)**: 주어진 문제를 해결하기 위해 **약속된 일련의 절차**를 단계적으로
표현한 것. 여기서 '약속'이란 사람이든 로봇이든 컴퓨터든, 누가 실행해도 같은 결과가 나오도록
각 단계를 미리 정해 둔다는 뜻이다.

:::


알고리즘이라 부르려면 다음 다섯 조건을 만족해야 한다. 오른쪽 열은 앞의 청소 로봇 절차에서
각 조건이 무엇에 해당하는지를 보인다.

| 조건 | 뜻 | 청소 로봇에서 |
|:--|:--|:--|
| **명확성** | 각 단계가 모호하지 않게 기술된다. | "깨끗이"가 아니라 "모든 칸을 한 번씩 지난다" |
| **유일성** | 각 단계의 다음 단계가 하나로 결정된다. | 줄 끝에 닿으면 "아래로 한 칸, 방향 반대로" 하나뿐이다 |
| **입력과 출력** | 정의된 입력을 받아 결과를 산출한다. | 방의 가로·세로 칸 수를 받아 칸별 청소 순서를 낸다 |
| **유한성** | 유한한 수의 단계를 거쳐 반드시 종료한다. | 가로 × 세로 번 이동하면 끝난다 |
| **일반성** | 정의된 입력 전체에 대해 동작한다. | 크기가 다른 방에서는 동작하지만, 가구가 놓인 방은 정의된 입력에 없다 |

: {tbl-colwidths="[14,38,48]"}

이 가운데 실제 구현에서 가장 자주 위반되는 조건은 **유한성**과 **일반성**이다.
"특정 예제에서 올바르게 동작한다"는 것과 "정의된 입력 전체에서 올바르게 동작한다"는 것은
전혀 다른 진술이며, 이 장에서는 그 차이를 반복해서 다룬다. 청소 로봇에게 가구 놓인 방이 그렇듯,
코드에도 그 코드를 만든 사람이 떠올리지 못한 입력이 들어온다.


### 구현에 따른 비용 차이 {#sec-cost-difference}

::: {.callout-important}
**이 장에서 말하는 비용(cost)**: 알고리즘이 요구하는 **수행 시간**과 **메모리**, 두 가지를
합쳐 부르는 말이다. 수행 시간은 시계로 잰 초가 아니라 **연산 횟수**로, 메모리는 **동시에
확보해야 하는 공간의 크기**로 잰다. "비용이 크다"고 할 때는 둘 중 어느 쪽인지 반드시
구분한다. 시간을 줄이기 위해 메모리를 더 쓰는 알고리즘(병합 정렬)이 이 장에 나온다.
:::


아래 두 프로그램은 1부터 `n` 까지의 값을 담은 벡터를 생성한다. **두 결과는 완전히 동일하다.**


::: {.callout-tip}
**예측해 보자**: `n` 이 5만일 때 두 프로그램의 실행 시간은 얼마나 차이 나겠는가?
비슷한 수준인가, 두 배 정도인가, 그보다 큰가? 실행하기 전에 적어 보자.

:::


```{r cost-two-programs}
# 프로그램 1: 벡터를 미리 할당한 뒤 각 위치에 값을 대입한다
prealloc_vec <- function(n) {
  x <- numeric(n)
  for (i in seq_len(n)) {
    x[i] <- i
  }
  x
}

# 프로그램 2: 반복할 때마다 벡터를 이어 붙여 길이를 늘린다
grow_vec <- function(n) {
  x <- NULL
  for (i in seq_len(n)) {
    x <- c(x, i)
  }
  x
}

# 두 결과가 동일한지 먼저 확인
identical(prealloc_vec(1000), as.numeric(grow_vec(1000)))

```


두 함수의 결과가 동일함을 확인했으므로 이제 비용을 측정한다.


```{r cost-two-programs-time}
n <- 50000
t1 <- system.time(prealloc_vec(n))[["elapsed"]]
t2 <- system.time(grow_vec(n))[["elapsed"]]

data.frame(
  방식 = c("사전 할당", "이어 붙이기"),
  초 = c(t1, t2)
)

```


예측과 일치하는가? 두 배 정도의 차이를 예상했다면 실제 결과와 상당한 차이가 있을 것이다.
`n` 을 10배로 늘리면 격차는 다시 크게 벌어진다.
`x <- c(x, i)` 는 반복마다 **길이가 1 만큼 늘어난 새 벡터를 할당하고 기존 원소를 전부 복사**한다.
$i$ 번째 반복에서 $i$ 개를 복사하므로 전체 복사량은
$1 + 2 + \cdots + n = n(n-1)/2$ 에 비례한다.
반면 사전 할당 방식은 이미 확보된 메모리에 값을 대입하므로 반복당 비용이 일정하다.


::: {.callout-caution}
**흔한 오해**: 결과가 같으면 두 코드가 동등하다고 판단하는 것.
두 프로그램의 출력은 완전히 동일하지만 비용의 **증가율**이 다르다.
입력이 작을 때는 이 차이가 드러나지 않다가, 실제 데이터 규모에서 급격히 나타난다.

:::


### 시간 복잡도와 공간 복잡도 {#sec-complexity}


::: {.callout-note}
**시간 복잡도(time complexity)**: 알고리즘이 종료할 때까지 수행하는 연산의 횟수.
사칙연산, 비교연산, 반복, 함수 호출이 계수의 대상이다.

**공간 복잡도(space complexity)**: 알고리즘이 종료할 때까지 필요한 메모리의 크기.
변수의 개수, 자료 구조의 크기, 함수 호출로 누적되는 스택 프레임이 대상이다.

:::

앞 절의 두 프로그램을 이 용어로 기술하면 다음과 같다.

- 프로그램 1: 반복이 $n$ 회이므로 수행 시간은 $n$ 에 비례한다. 벡터를 미리 할당한 뒤
대입만 하므로 추가 메모리는 증가하지 않는다.
- 프로그램 2: 반복마다 복사가 발생하므로 수행 시간은 $n^2$ 에 비례한다. 반복마다 새
벡터를 할당하므로 필요한 메모리도 $n$ 까지 증가한다.

성능은 일반적으로 **최악의 경우(worst case)** 를 기준으로 평가한다. 최선의 경우는
특정 입력에서만 성립하고, 평균의 경우는 입력 분포를 가정해야 계산할 수 있는 반면,
최악의 경우는 임의의 입력에 대해 항상 성립하는 상한을 제공하기 때문이다.


### 빅오 표기법 {#sec-big-o}

입력 크기를 $n$, 연산 횟수를 $f(n)$ 이라 하자. $n$ 이 충분히 커지면 $f(n)$ 의
저차항은 영향력을 잃고 **증가율이 가장 큰 항**만 남는다. 이러한 점근적 증가율을
나타내는 표기가 빅오 표기법이다.


::: {.callout-note}
**정의**: $x \geq k$ 인 모든 $x$ 에 대해 $|f(x)| \leq C|g(x)|$ 를 만족하는
상수 $k$ 와 $C$ 가 존재하면 $f(x) = \mathcal{O}(g(x))$ 라 하고
"$f$ 는 $g$ 의 빅오"라고 읽는다.

즉 $g$ 는 $f$ 의 **점근적 상한**이다. 임의의 입력에 대해 $f$ 는 $Cg$ 를 넘지 않는다.

:::


```{r fig-big-o-def-fig, fig.align='center', echo=FALSE, fig.show='hold', out.width='90%', fig.cap="빅오의 정의: 어떤 지점 k 를 넘어서면 Cg(x) 가 f(x) 를 계속 위에서 덮는다 (https://johngrib.github.io/wiki/big-O-notation/ 에서 발췌)"}
options(knitr.graphics.auto_pdf = TRUE)
knitr::include_graphics('figures/big-o-explain.png', dpi = NA)

```


코드를 분석할 때 실제로 사용하는 것은 정의 자체보다 다음 세 규칙이다.


::: {.callout-tip}
**규칙 1 (계수 법칙)**: $C > 0$ 이면 $C f(n) = \mathcal{O}(g(n))$.
$\rightarrow$ 반복 횟수가 $5n$ 이든 $100n$ 이든 모두 $\mathcal{O}(n)$ 이다.

**규칙 2 (합의 법칙)**: 두 부분이 순차적으로 실행되면 증가율이 큰 쪽만 남는다.
$\rightarrow$ $\mathcal{O}(n) + \mathcal{O}(n^2) = \mathcal{O}(n^2)$.
단, 입력 변수가 서로 다르면 하나로 합쳐지지 않는다. $\rightarrow$ $\mathcal{O}(n + m)$.

**규칙 3 (곱의 법칙)**: 반복문이 중첩되면 각 반복 횟수를 곱한다.
$\rightarrow$ $\mathcal{O}(n) \times \mathcal{O}(n) = \mathcal{O}(n^2)$.

:::


이 세 규칙을 코드에 적용해 보자.


::: {.callout-tip}
**예측해 보자**: 아래 네 함수의 시간 복잡도를 각각 적어 보자.
코드를 실행할 필요는 없으며, 반복 횟수만 세면 된다.

:::


```{r big-o-cases, eval=FALSE}
case1 <- function(n) {           # (가)
  s <- 0
  for (i in seq_len(n)) s <- s + i
  s
}

case2 <- function(n) {           # (나)
  s <- 0
  for (i in seq_len(5 * n)) s <- s + i
  s
}

case3 <- function(n, m) {        # (다)
  s <- 0
  for (i in seq_len(n)) s <- s + i
  for (j in seq_len(m)) s <- s + j
  s
}

case4 <- function(n) {           # (라)
  s <- 0
  for (i in seq_len(n)) {
    for (j in seq_len(n)) s <- s + j
  }
  s
}

```


답은 차례로 (가) $\mathcal{O}(n)$, (나) $\mathcal{O}(5n) = \mathcal{O}(n)$,
(다) $\mathcal{O}(n + m)$, (라) $\mathcal{O}(n^2)$ 이다.
(나)에서 계수 5가 소거되는 것이 규칙 1, (다)에서 두 반복이 하나로 합쳐지지 않는 것이
규칙 2의 단서 조항에 해당하며, (라)는 규칙 3의 사례다.

복잡도의 차수가 한 단계 올라갈 때 연산 횟수가 얼마나 벌어지는지 확인해 보자.

분할 정복과 같이 원래 문제를 동일한 구조의 더 작은 문제로 환원할 수 있는 경우,
반복문보다 간결하게 표현된다.

### 재귀 함수의 구성 {#sec-recursion-structure}

모든 재귀 함수는 두 부분으로 이루어진다.

1. **종료 조건(base case)**: 더 이상 분할하지 않고 결과를 직접 반환하는 경우.
2. **재귀 단계(recursive step)**: 문제의 크기를 줄여 자기 자신을 호출하는 경우.

1부터 `n` 까지의 합을 구하는 함수로 확인해 보자.


```{r recursive-sum}
recursive_sum <- function(n) {
  if (n == 1) return(n)            # 종료 조건
  n + recursive_sum(n - 1)         # 재귀 단계
}

recursive_sum(3)

```


```{r fig-rec-sum-fig, echo=FALSE, out.width='85%', fig.align='center', fig.cap="recursive_sum(3) 의 호출과 반환 (http://10bun.tv/beginner/episode-4/ 에서 발췌)"}
knitr::include_graphics('figures/recursive-sum-flows.png')

```


- `recursive_sum(3)` 은 `n` 이 1이 아니므로 `recursive_sum(2)` 를 호출한다.
- `recursive_sum(2)` 는 같은 이유로 `recursive_sum(1)` 을 호출한다.
- `recursive_sum(1)` 은 종료 조건을 만족하여 1을 반환한다.
- 복귀하면서 `2 + 1 = 3`, `3 + 3 = 6` 이 계산되어 최종적으로 6이 반환된다.


### 종료 조건의 한계 {#sec-base-case-limits}

위 함수는 정상적으로 동작한다. 그렇다면 "정의된 입력 전체"에 대해서도 그러한가?


::: {.callout-tip}
**예측해 보자**: `recursive_sum(0)` 은 무엇을 반환하겠는가?
0, 1, 오류 중 어느 것인지 실행하기 전에 답을 정해 두자.

:::


```{r recursive-sum-zero}
# 이 호출은 종료되지 않는다. 발생하는 오류 메시지를 확인한다.
tryCatch(recursive_sum(0),
         error = function(e) cat("오류:", conditionMessage(e), "\n"))

```


`n` 이 0이면 `n == 1` 은 결코 참이 되지 않는다. 인수가 `0, -1, -2, \ldots` 로 계속
감소하다가 R 의 중첩 한계에 도달해서야 중단된다. **종료 조건은 "`n` 이 1일 때"가 아니라
"`n` 이 1 이하일 때"로 규정했어야 한다.** 결함은 입력이 커질 때만 드러나는 것이 아니라,
정의역의 경계 바로 바깥에서도 드러난다.

입력 크기에 따른 한계도 확인해 두자.


```{r recursive-sum-deep}
recursive_sum(1000)          # 정상적으로 동작한다

tryCatch(recursive_sum(5000),   # 중첩 한계
         error = function(e) cat("오류:", conditionMessage(e), "\n"))

```


재귀 호출은 호출마다 스택 프레임을 누적하므로 **공간 복잡도가 $\mathcal{O}(n)$** 이다.
R 은 중첩 깊이를 `options(expressions)` 로 제한하며 기본값은 5000이다.
동일한 계산을 반복문으로 구현하면 공간 복잡도는 $\mathcal{O}(1)$ 이고 깊이 제한도 없다.

두 문제를 함께 해결한 구현은 다음과 같다.


```{r recursive-sum-fixed}
recursive_sum2 <- function(n) {
  if (n <= 1) return(n)            # 경계 조건을 포함한다
  n + recursive_sum2(n - 1)
}

c(recursive_sum2(0), recursive_sum2(1), recursive_sum2(100))

# 반복문 구현: 공간 복잡도 O(1), 깊이 제한 없음
iterative_sum <- function(n) {
  s <- 0
  for (i in seq_len(n)) s <- s + i
  s
}

c(iterative_sum(0), iterative_sum(100), iterative_sum(100000))

```


::: {.callout-caution}
재귀는 **가독성을 얻는 대신 메모리를 소비한다.** 호출 깊이가 입력 크기에 비례하는
재귀는 R 에서 실무 코드로 사용하기 어렵다. 재귀 구조로 문제를 먼저 이해한 뒤, 필요하면
반복문으로 변환하는 순서가 안전하다.

:::


### 계승 {#sec-recursion-factorial}

계승(factorial)은 재귀적 정의가 그대로 코드로 옮겨지는 대표적인 예다.

$$
 n! = \begin{cases}
 n \times (n-1)!, & n \geq 1 \\
 1, & n = 0
 \end{cases}
$$


```{r factorial-manual}
factorial_manual <- function(n) {
  if (n == 0) return(1)
  n * factorial_manual(n - 1)
}

factorial_manual(10)

factorial(10)        # R 내장 함수로 대조

```


직접 구현한 함수를 내장 함수와 대조하는 이 한 줄이 곧 검증이다.
**구현했으면 반드시 정답이 알려진 기준과 대조한다.**

### 하노이 탑 {#sec-recursion-hanoi}

하노이 탑은 재귀 없이는 설명하기 어려운 대표적인 문제다.
기둥 세 개(A, B, C)와 크기가 다른 원판 $n$ 개가 있고, 원판은 A 에 크기순으로 쌓여 있다.
모든 원판을 C 로 옮기되 (1) 한 번에 하나씩만 옮기고 (2) 큰 원판을 작은 원판 위에
올릴 수 없다.


```{r fig-hanoi-problem, out.width='100%', fig.show='hold', fig.cap="하노이 탑 문제", echo=FALSE}
knitr::include_graphics("figures/hanoi-problem.gif")

```


해법의 핵심은 문제를 한 단계 작은 동일 문제로 환원하는 것이다.
$n$ 개를 A 에서 C 로 옮기는 작업은 다음 세 단계로 분해된다.

1. 위쪽 $n-1$ 개를 A 에서 B 로 옮긴다 (크기만 하나 작은 동일한 문제).
2. 가장 큰 원판을 A 에서 C 로 옮긴다.
3. B 에 있던 $n-1$ 개를 B 에서 C 로 옮긴다 (역시 동일한 문제).


```{r fig-hanoi-solution, out.width='100%', fig.show='hold', fig.cap="원판 3개를 옮기는 과정", echo=FALSE}
knitr::include_graphics("figures/hanoi-solution.gif")

```


```{r hanoi-code}
move_hanoi <- function(k, from, to, via) {
  if (k == 1) {
    cat(sprintf("원판 1: %s -> %s\n", from, to))
  } else {
    move_hanoi(k - 1, from = from, to = via, via = to)
    cat(sprintf("원판 %d: %s -> %s\n", k, from, to))
    move_hanoi(k - 1, from = via, to = to, via = from)
  }
}

move_hanoi(3, "A", "C", "B")

```


원판이 $n$ 개일 때 필요한 이동 횟수는 $2^n - 1$ 이다. 호출이 매 단계에서 두 개로
분기하기 때문이다. 즉 이 알고리즘의 시간 복잡도는 $\mathcal{O}(2^n)$ 이며, 앞의 표에서
확인했듯 $n$ 이 조금만 커져도 계산이 불가능해진다. 전설에 등장하는 원판 64개는
$2^{64} - 1$ 회의 이동이 필요하며, 1초에 한 번씩 옮겨도 5천억 년이 넘게 걸린다.


```{r hanoi-count}
count_moves <- function(k) if (k == 1) 1 else 2 * count_moves(k - 1) + 1

data.frame(원판 = 3:6,
           실제_이동 = sapply(3:6, count_moves),

```


## 탐색 알고리즘 {#sec-search}

정렬된 자료에서 특정 값을 찾는 두 가지 방법을 비교한다. 이 절의 목적은 두 알고리즘을
암기하는 것이 아니라, **복잡도의 차수가 다르다는 사실이 실제로 어떤 차이를 만드는지
수치로 확인하는 것**이다.


### 선형 탐색 {#sec-linear-search}

첫 원소부터 순차적으로 비교한다. 가장 단순하며, 자료가 정렬되어 있지 않아도 적용할 수 있다.


```{r linear-search}
linear_search <- function(target, vec) {
  for (i in seq_along(vec)) {
    if (vec[i] == target) return(i)
  }
  NA_integer_
}

set.seed(1)
x <- sort(sample(1:100, 20))
x

linear_search(target = x[13], vec = x)
linear_search(target = 101, vec = x)

```


목표값이 마지막 위치에 있거나 존재하지 않으면 $n$ 회 모두 비교하게 된다.
따라서 최악의 경우 시간 복잡도는 $\mathcal{O}(n)$ 이다.


### 이진 탐색 {#sec-binary-search}

**정렬된** 벡터에서는 비교 횟수를 크게 줄일 수 있다. 중앙에 위치한 값과 목표값을
비교하여, 목표값이 더 작으면 오른쪽 절반을, 더 크면 왼쪽 절반을 탐색 범위에서 제외한다.
비교를 한 번 수행할 때마다 후보의 개수가 절반으로 줄어든다.


```{r fig-binary-search-anim, echo=FALSE, out.width='100%', fig.cap="선형 탐색과 이진 탐색 (https://blog.penjee.com/binary-vs-linear-search-animated-gifs/ 에서 발췌)"}
knitr::include_graphics("https://blog.penjee.com/wp-content/uploads/2015/04/binary-and-linear-search-animations.gif")

```


```{r binary-search}
binary_search <- function(target, ovec) {
  lo <- 1L
  hi <- length(ovec)
  while (lo <= hi) {
    mid <- (lo + hi) %/% 2L
    if (ovec[mid] == target) {
      return(mid)
    } else if (ovec[mid] > target) {
      hi <- mid - 1L          # 오른쪽 절반을 탐색 범위에서 제외
    } else {
      lo <- mid + 1L          # 왼쪽 절반을 탐색 범위에서 제외
    }
  }
  NA_integer_
}

binary_search(target = x[13], ovec = x)
binary_search(target = 101, ovec = x)

```


비교 횟수에 따라 후보의 개수는 $n, n/2, n/2^2, \ldots$ 로 감소한다. $k$ 번째 비교에서
후보가 1개가 되므로 $n/2^k = 1$ 이고, 양변에 밑이 2인 로그를 취하면 $k = \log_2 n$ 을
얻는다. 따라서 이진 탐색의 시간 복잡도는 $\mathcal{O}(\log n)$ 이다.


### 구현의 정확성 검증 {#sec-search-verification}

여기서 한 가지를 짚고 넘어가야 한다. 위 `binary_search()` 는 과연 올바른 구현인가?
예제 두 개를 통과했다는 사실이 보장하는 것은 그 두 예제에 대한 정확성뿐이다.

검증의 출발점은 **전수 검사**다. 벡터의 모든 원소를 차례로 목표값으로 입력하고,
반환된 위치가 실제 위치와 일치하는지 확인한다.


```{r binary-search-exhaustive}
checks <- vapply(seq_along(x), function(i) {
  binary_search(target = x[i], ovec = x) == i
}, logical(1))

all(checks)
sum(!checks)

```


모든 원소에 대해 통과했다. 이번에는 동일한 알고리즘을 재귀로 작성한 구현을 살펴본다.
아래 구현에는 **결함이 있다.** 어느 부분이 잘못되었는지 찾아보자.


::: {.callout-tip}
**예측해 보자**: 아래 `rbinary_search()` 에 벡터의 모든 원소를 입력하면
몇 개나 정확히 찾아내겠는가? 전부인가, 절반인가, 아니면 하나도 찾지 못하는가?

:::


```{r rbinary-search-buggy}
rbinary_search <- function(target, ovec, minL, maxL) {

  }
}

# 본문 예제 하나만 실행하면 정상으로 보인다
set.seed(2)

```


예제 하나는 통과한다. 이제 전수 검사를 수행한다.


```{r rbinary-search-exhaustive}

}, integer(1))

절반 가까이가 `NA` 로 반환되었다. 원인은 첫 줄의
`if (maxL <= minL) return(NA_integer_)` 이다. 탐색 범위가 원소 하나로 좁혀지면
`minL == maxL` 이 되는데, 이 조건은 **남은 원소를 검사하지 않은 채 탐색을 종료한다.**
탐색 범위가 실제로 비는 조건은 `minL > maxL` 이다.


```{r rbinary-search-fixed}
rbinary_search2 <- function(target, ovec, lo = 1L, hi = length(ovec)) {
  if (lo > hi) return(NA_integer_)          # 탐색 범위가 비었을 때만 종료
  mid <- (lo + hi) %/% 2L
  if (ovec[mid] == target) {
    mid
  } else if (ovec[mid] > target) {
    rbinary_search2(target, ovec, lo, mid - 1L)
  } else {
    rbinary_search2(target, ovec, mid + 1L, hi)
  }
}

}, integer(1))

all(found2 == seq_along(x))

```

**이 절의 핵심**: `rbinary_search()` 는 문법 오류가 없고, 실행 시 오류 메시지도
출력하지 않으며, 저자가 선택한 예제에서는 정답을 반환한다. 그럼에도 잘못된 구현이다.

이러한 결함은 **오류 메시지가 아니라 검증 절차를 통해서만** 발견된다.
전수 검사, 경계 사례 검토, 정답이 알려진 기준과의 대조가 그 절차에 해당한다.
이 절차는 2학기 "AI와 함께 프로그래밍하기" 장에서 다시 사용된다.

:::


### 두 탐색의 비용 비교 {#sec-search-cost}

이제 두 탐색 알고리즘의 비교 횟수를 직접 측정한다. 실행 시간 대신
**연산 횟수를 계수하면** 하드웨어 성능과 무관한 값을 얻을 수 있다.


```{r search-cost-count}
count_linear <- function(target, vec) {
  n <- 0L
  for (i in seq_along(vec)) {
    n <- n + 1L
    if (vec[i] == target) return(n)
  }
  n
}

count_binary <- function(target, ovec) {
  lo <- 1L; hi <- length(ovec); n <- 0L
  while (lo <= hi) {
    n <- n + 1L
    mid <- (lo + hi) %/% 2L
    if (ovec[mid] == target) return(n)
    if (ovec[mid] > target) hi <- mid - 1L else lo <- mid + 1L
  }
  n
}

set.seed(1)
sizes <- c(100, 1000, 10000)
cmp <- t(sapply(sizes, function(n) {
  v <- seq_len(n)
  ks <- sample(v, 100)
  c(선형 = mean(sapply(ks, count_linear, vec = v)),
    이진 = mean(sapply(ks, count_binary, ovec = v)),
    log2n = log2(n))
}))

data.frame(n = sizes, round(cmp, 1))

```


선형 탐색의 평균 비교 횟수는 $n/2$ 에, 이진 탐색은 $\log_2 n$ 에 근접한다.
$n$ 이 100에서 10,000으로 100배 증가할 때 선형 탐색은 약 100배 증가하지만, 이진 탐색은
두 배를 조금 넘는 수준에 그친다. $n = 10^6$ 이면 선형 탐색은 평균 50만 회, 이진 탐색은
약 20회를 수행한다.


::: {.callout-caution}
이진 탐색이 항상 유리한 것은 아니다. **자료가 정렬되어 있어야** 적용할 수 있고,
정렬 자체의 비용이 $\mathcal{O}(n \log n)$ 이다. 탐색을 한 번만 수행한다면 정렬 후
이진 탐색을 적용하는 것보다 선형 탐색이 오히려 저렴하다.
탐색을 여러 번 반복할 때 비로소 정렬 비용이 상쇄된다.

:::


## 정렬 알고리즘 {#sec-sorting}

정렬 알고리즘은 매우 다양하다. 이 장에서는 네 가지를 **두 쌍**으로 묶어 다룬다.

| 쌍 | 시간 복잡도 | 방식 |
|:--|:--|:--|
| 버블 정렬 · 삽입 정렬 | $\mathcal{O}(n^2)$ | 원소를 하나씩 비교하며 자리를 옮긴다 |
| 병합 정렬 · 퀵 정렬 | 평균 $\mathcal{O}(n \log n)$ | 문제를 나누어 재귀로 푸는 분할 정복 |

: {tbl-colwidths="[30,24,46]"}

쌍과 쌍을 비교하면 **차수의 차이**가 드러난다. 쌍 안의 두 알고리즘을 비교하면 같은 차수라도
**입력의 상태에 따라** 비용이 달라진다는 사실이 드러난다. 이 절의 마지막 소절에서 네 알고리즘의
비교 횟수를 직접 세어 두 가지를 모두 확인한다.


::: {.callout-note}
**안정 정렬(stable sort)**: 값이 동일한 원소들의 상대적 순서가 정렬 후에도 유지되는
정렬. 데이터 프레임을 여러 열 기준으로 순차 정렬할 때 이 성질이 중요하다.

아래 네 알고리즘은 모두 **오름차순** 기준으로 설명하며, 입력은 **`NA` 가 없는 수치형 벡터**라고
전제한다. 참고로 `sort()` 는 기본값(`na.last = NA`)에서 `NA` 를 제거한 뒤 정렬한다.

:::


### 버블 정렬 {#sec-bubble-sort}

키 순서로 한 줄을 세우는데, 학생들은 **바로 옆 사람과만** 키를 비교할 수 있다고 하자.
앞사람이 더 크면 둘이 자리를 바꾼다. 줄의 처음부터 끝까지 한 번 훑으면 키가 가장 큰 학생이
맨 뒤로 밀려난다. 버블 정렬(bubble sort)은 이 방법 그대로다.

인접한 두 원소를 비교하여 순서가 어긋나 있으면 교환한다. 전체를 한 번 순회하면
가장 큰 값이 마지막 위치로 이동한다. 이 과정을 $n-1$ 회 반복한다.


```{r fig-bubble-anim, echo=FALSE, out.width='55%', fig.align='center', fig.cap="버블 정렬 (위키미디어 공용)"}
knitr::include_graphics("https://upload.wikimedia.org/wikipedia/commons/0/06/Bubble-sort.gif")

```


```{r bubble-sort}
bubble_sort <- function(x) {
  n <- length(x)
  if (n < 2) return(x)
  for (i in seq_len(n - 1)) {
    for (j in seq_len(n - i)) {
      if (x[j] > x[j + 1]) {
        temp <- x[j]
        x[j] <- x[j + 1]
        x[j + 1] <- temp
      }
    }
  }
  x
}

set.seed(1234)
v <- sample(1:100, 15)
v

bubble_sort(v)

identical(bubble_sort(v), sort(v))     # 내장 함수와 대조한다

```


비교 횟수는 $(n-1) + (n-2) + \cdots + 1 = n(n-1)/2$ 이므로 시간 복잡도는
$\mathcal{O}(n^2)$ 이다. 이미 정렬된 입력에 대해서도 이 구현은 모든 비교를 수행한다.
구현이 단순하고 벡터 내부에서 교환이 이루어져 추가 공간이 $\mathcal{O}(1)$ 이라는 장점이
있으나, 시간 복잡도가 치명적인 단점이다.


### 삽입 정렬 {#sec-insertion-sort}

카드 게임에서 카드를 한 장씩 받아 손에 쥔다고 하자. 새 카드를 받을 때마다 이미 쥐고 있는
카드 사이에서 **제자리를 찾아 끼워 넣는다.** 손에 쥔 카드는 언제나 정렬된 상태이고,
마지막 카드를 끼워 넣으면 정렬이 끝난다. 삽입 정렬(insertion sort)은 이 방법 그대로다.


```{r fig-insertion-anim, echo=FALSE, out.width='45%', fig.align='center', fig.cap="삽입 정렬 (위키미디어 공용)"}
knitr::include_graphics("https://upload.wikimedia.org/wikipedia/commons/0/0f/Insertion-sort-example-300px.gif")

```


벡터의 앞부분 `x[1:(i-1)]` 이 '손에 쥔 카드'다. `i` 번째 값을 `key` 로 꺼내 두고,
앞부분에서 `key` 보다 큰 값을 한 칸씩 뒤로 밀어 빈자리를 만든 뒤 그 자리에 `key` 를 넣는다.


```{r insertion-sort}
insertion_sort <- function(x) {
  n <- length(x)
  if (n < 2) return(x)
  for (i in 2:n) {
    key <- x[i]                        # 이번에 끼워 넣을 값
    j <- i - 1
    while (j >= 1 && x[j] > key) {     # key 보다 큰 값을 한 칸씩 뒤로 민다
      x[j + 1] <- x[j]
      j <- j - 1
    }
    x[j + 1] <- key                    # 비워 둔 자리에 넣는다
  }
  x
}

insertion_sort(v)

identical(insertion_sort(v), sort(v))

```


`while` 의 조건 `j >= 1 && x[j] > key` 에서 앞쪽 검사가 경계를 지킨다. `key` 가 앞부분의
모든 값보다 작으면 `j` 가 0 까지 내려가는데, 이때 `&&` 는 왼쪽이 `FALSE` 이므로 오른쪽
`x[0] > key` 를 계산하지 않는다. 이를 **단락 평가(short-circuit evaluation)** 라 한다.
앞쪽 검사를 빼면 어떻게 되는지 확인해 보자.


```{r insertion-sort-nocheck, error=TRUE}
# j >= 1 검사를 뺀 구현
insertion_nocheck <- function(x) {
  for (i in 2:length(x)) {
    key <- x[i]
    j <- i - 1
    while (x[j] > key) {
      x[j + 1] <- x[j]
      j <- j - 1
    }
    x[j + 1] <- key
  }
  x
}

insertion_nocheck(c(3, 1, 2))

cards <- c(3, 1, 2)
cards[0]         # 0번 위치는 오류가 아니라 길이 0 인 벡터를 돌려준다
cards[0] > 1     # 비교 결과도 길이 0 이므로 while 이 참·거짓을 판단하지 못한다

```


R 에서 `x[0]` 은 오류가 아니다. 이 때문에 경계를 벗어난 비교가 곧바로 드러나지 않고,
`while` 에 이르러서야 알아보기 어려운 메시지와 함께 멈춘다.

비교 횟수는 입력의 상태에 따라 크게 달라진다. 이미 정렬된 입력에서는 `key` 마다 바로 앞의
값과 한 번만 비교하고 멈추므로 모두 $n-1$ 회로 끝난다. 역순으로 정렬된 입력에서는 `key` 가
매번 맨 앞까지 이동해야 하므로 $1 + 2 + \cdots + (n-1) = n(n-1)/2$ 회를 비교한다.
최선의 경우 $\mathcal{O}(n)$, 최악의 경우 $\mathcal{O}(n^2)$ 이다. 버블 정렬처럼 벡터 안에서
자리만 옮기므로 추가 공간은 $\mathcal{O}(1)$ 이다.

같은 $\mathcal{O}(n^2)$ 이지만 **거의 정렬된 자료**에서는 삽입 정렬이 버블 정렬보다 훨씬 적게
비교한다. 그래서 실무에서 쓰는 정렬 함수 가운데에는 짧은 구간을 정렬할 때 삽입 정렬로 바꿔
쓰는 것이 많다. 파이썬의 기본 정렬 알고리즘인 팀정렬(Timsort)이 그 예다.


### 병합 정렬 {#sec-merge-sort}

두 반의 시험 답안지를 번호순으로 한 묶음으로 합친다고 하자. 두 묶음이 각각 번호순으로
정리되어 있다면 일은 간단하다. 두 묶음의 맨 위 장끼리 비교해 번호가 빠른 쪽을 한 장씩
내려놓으면 된다. 정리되지 않은 큰 묶음은 절반으로 나누어 각각 정리한 뒤 이렇게 합치면 되고,
절반도 크면 다시 절반으로 나눈다. 병합 정렬(merge sort)은 이 방법 그대로다.

**분할 정복(divide and conquer)** 기법을 사용한다. 벡터를 절반으로 분할하고, 각 부분을
재귀적으로 정렬한 뒤, 정렬된 두 부분을 병합한다.
실제 정렬이 이루어지는 단계는 분할 단계가 아니라 **병합 단계**다.


```{r fig-merge-anim, echo=FALSE, out.width='45%', fig.align='center', fig.cap="병합 정렬 (위키미디어 공용)"}
knitr::include_graphics("https://upload.wikimedia.org/wikipedia/commons/c/cc/Merge-sort-example-300px.gif")

```


병합 함수부터 구현한다. 정렬된 두 벡터의 앞에서부터 작은 값을 차례로 선택하면
결과 역시 정렬된 상태로 채워진다.


```{r smerge}
smerge <- function(left, right) {
  temp <- numeric(length(left) + length(right))
  l <- r <- 1L
  for (i in seq_along(temp)) {
    # 오른쪽이 소진되었거나, 왼쪽이 남아 있고 그 값이 더 작거나 같으면 왼쪽을 선택한다
    if (r > length(right) ||
        (l <= length(left) && left[l] <= right[r])) {
      temp[i] <- left[l]
      l <- l + 1L
    } else {
      temp[i] <- right[r]
      r <- r + 1L
    }
  }
  temp
}

smerge(c(1, 4, 9), c(2, 3, 10))

```


`left[l] <= right[r]` 에서 **`<=`** 를 사용한 것이 안정성을 보장한다.
값이 동일한 경우 왼쪽, 즉 원래 앞에 있던 원소를 먼저 선택하기 때문이다.

분할 단계는 재귀로 구현한다.


```{r merge-sort}
merge_sort <- function(x) {
  n <- length(x)
  if (n <= 1) return(x)            # 종료 조건: 길이가 1 이하이면 이미 정렬된 상태다
  mid <- n %/% 2L
  smerge(merge_sort(x[1:mid]), merge_sort(x[(mid + 1):n]))
}

merge_sort(v)

identical(merge_sort(v), as.numeric(sort(v)))

```


분할을 절반씩 반복하므로 재귀 깊이는 $\log_2 n$ 이고, 각 깊이에서 원소 전체를 한 번씩
순회하므로 $n$ 회의 연산이 필요하다. 따라서 시간 복잡도는 $\mathcal{O}(n \log n)$ 이다.
다만 병합 결과를 담을 임시 벡터가 필요하므로 공간 복잡도는 $\mathcal{O}(n)$ 이다.
**시간과 공간을 맞바꾼 구조다.**


### 퀵 정렬 {#sec-quick-sort}

체육 시간에 학생들을 키 순서로 세운다고 하자. 선생님이 먼저 한 학생을 **기준**으로 세우고,
그보다 작은 학생은 왼쪽, 큰 학생은 오른쪽으로 보낸다. 기준 학생은 이것으로 제자리에 선 셈이다.
이제 왼쪽 무리와 오른쪽 무리 안에서 각각 같은 일을 반복하고, 무리가 한 명 이하가 되면 멈춘다.
퀵 정렬(quick sort)은 이 방법 그대로다.

병합 정렬과 같은 분할 정복이지만 일이 일어나는 단계가 반대다. 병합 정렬은 나누는 일이 단순하고
**합치는 단계**에서 정렬이 일어난다. 퀵 정렬은 **나누는 단계**에서 정렬이 일어나고, 합치는 일은
작은 무리, 기준, 큰 무리를 차례로 이어 붙이는 것뿐이다. 기준이 되는 값을 **기준값(pivot)** 이라
한다. 여기서는 벡터의 첫 원소를 기준값으로 삼는다.


```{r quick-sort}
quick_sort <- function(x) {
  if (length(x) <= 1) return(x)      # 종료 조건: 원소가 하나 이하이면 이미 정렬된 상태다
  pivot <- x[1]                      # 첫 원소를 기준값으로 삼는다
  c(quick_sort(x[x < pivot]),        # 기준값보다 작은 무리를 정렬해 왼쪽에
    x[x == pivot],                   # 기준값(과 같은 값)을 가운데에
    quick_sort(x[x > pivot]))        # 기준값보다 큰 무리를 정렬해 오른쪽에
}

quick_sort(v)

identical(quick_sort(v), sort(v))

```


나누는 과정을 출력해 보자. 아래 `quick_trace()` 는 `quick_sort()` 와 같은 일을 하면서
호출마다 `[작은 무리] 기준값 [큰 무리]` 를 한 줄씩 출력한다. 들여쓰기가 재귀의 깊이다.


```{r quick-trace}
quick_trace <- function(x, depth = 0) {
  if (length(x) <= 1) return(x)
  pivot <- x[1]
  small <- x[x < pivot]
  big <- x[x > pivot]
  cat(strrep("  ", depth), "[", paste(small, collapse = " "), "] ", pivot,
      " [", paste(big, collapse = " "), "]\n", sep = "")
  c(quick_trace(small, depth + 1), x[x == pivot], quick_trace(big, depth + 1))
}

res <- quick_trace(c(5, 3, 8, 1, 9, 2, 7))

```


한 번 나눌 때마다 무리가 대략 절반씩 작아져 세 단계 만에 끝났다. 무작위 순서의 입력이라면
재귀 깊이는 대략 $\log_2 n$ 에 비례하고, 각 깊이에서 모든 원소가 기준값과 한 번씩 비교되므로
평균 시간 복잡도는 병합 정렬과 같은 $\mathcal{O}(n \log n)$ 이다.


::: {.callout-tip}
**예측해 보자**: 이미 정렬된 벡터 `1:6` 을 `quick_trace()` 에 넣으면 출력은 몇 줄이고,
들여쓰기는 어떤 모양이 되겠는가? 실행하기 전에 그려 보자.

:::


```{r quick-trace-sorted}
res <- quick_trace(1:6)

```


첫 원소를 기준값으로 삼으면 정렬된 입력에서는 기준값이 늘 **가장 작은 값**이 된다. 작은 무리는
늘 비고, 큰 무리는 원소가 하나씩만 줄어든다. 재귀 깊이는 $n - 1$ 이 되고, 비교 횟수는
$(n-1) + (n-2) + \cdots + 1 = n(n-1)/2$ 로 버블 정렬과 같아진다. **평균은 $\mathcal{O}(n \log n)$
이지만 최악은 $\mathcal{O}(n^2)$ 이며, 그 최악이 하필 이미 정렬된 입력이다.**

재귀 깊이가 $n$ 에 비례하면 @sec-base-case-limits 에서 본 중첩 한계에도 걸린다.


```{r quick-sort-depth}
set.seed(1)
identical(quick_sort(sample(5000)), 1:5000)   # 무작위 순서 5,000개: 정상

tryCatch(quick_sort(1:5000),                  # 정렬된 5,000개: 재귀 깊이 약 5,000
         error = function(e) cat("오류:", conditionMessage(e), "\n"))

```


같은 5,000개의 값인데 **순서만 다른** 두 입력 가운데 하나는 정상적으로 끝나고 다른 하나는 멈춘다.
이미 정렬된 자료를 다시 정렬하는 일은 드물지 않으므로 이 차이는 실무에서도 문제가 된다.

메모리도 따져 보자. 이 구현은 나눌 때마다 `x[x < pivot]` 과 `x[x > pivot]` 으로 **새 벡터를
만들고**, 호출이 끝날 때까지 각 깊이의 벡터가 동시에 메모리에 남는다. 무작위 입력에서는 깊이마다
벡터가 대략 절반씩 작아지므로 추가 공간이 $\mathcal{O}(n)$ 이지만, 정렬된 입력에서는
$n + (n-1) + \cdots$ 가 쌓여 $\mathcal{O}(n^2)$ 까지 늘어난다. 읽기 쉬운 대신 메모리를 쓰는
구현이다. 교과서의 퀵 정렬은 대개 벡터 안에서 자리만 바꾸는 **제자리(in-place)** 방식으로 구현해
추가 공간을 재귀 호출에 필요한 만큼으로 줄인다. 대신 코드가 길고 경계 처리가 까다롭다.


::: {.callout-note}
**기준값을 고르는 규칙이 최악의 입력을 정한다.** 가운데 원소를 기준값으로 삼으면 정렬된
입력은 최선의 경우가 되지만, 그 규칙에 불리한 다른 입력이 여전히 존재한다. 기준값을 무작위로
고르면 특정 입력이 늘 최악이 되는 일은 없어지는 대신, 같은 입력이라도 실행할 때마다 비교
횟수가 달라진다.

:::


### 네 정렬의 비용 비교 {#sec-sorting-cost}


::: {.callout-tip}
**예측해 보자**: 원소 수를 두 배로 늘리면 네 정렬의 비교 횟수는 각각 몇 배가 되겠는가?
또 **이미 정렬된** 입력에서는 네 정렬 가운데 어느 것이 가장 적게, 어느 것이 가장 많이
비교하겠는가? 표를 보기 전에 적어 보자.

:::


실행 시간 대신 **비교 횟수를 측정한다.** 실행 시간은 하드웨어 성능과 측정 시점의 부하에
따라 변동하며, 빠른 쪽은 0초로 측정되어 증가율을 계산할 수 없다.
반면 비교 횟수는 입력이 동일하면 항상 같은 값을 갖는다.

아래 네 함수는 각 정렬 함수에서 두 값을 비교하는 곳마다 1을 더하도록 고친 것이다. 퀵 정렬은
한 번 나눌 때 기준값과 나머지 원소를 한 번씩 비교한다고 보고 (원소 수 $-\,1$) 회로 센다.


```{r sorting-count}
#| code-fold: true
#| code-summary: "비교 횟수를 세는 함수 네 개 (펼쳐 보기)"
bubble_count <- function(x) {
  n <- length(x)
  cnt <- 0
  for (i in seq_len(n - 1)) {
    for (j in seq_len(n - i)) {
      cnt <- cnt + 1
      if (x[j] > x[j + 1]) {
        temp <- x[j]; x[j] <- x[j + 1]; x[j + 1] <- temp
      }
    }
  }
  cnt
}

insertion_count <- function(x) {
  n <- length(x)
  cnt <- 0
  if (n < 2) return(cnt)
  for (i in 2:n) {
    key <- x[i]
    j <- i - 1
    while (j >= 1) {
      cnt <- cnt + 1                   # x[j] 와 key 를 비교한다
      if (x[j] <= key) break
      x[j + 1] <- x[j]
      j <- j - 1
    }
    x[j + 1] <- key
  }
  cnt
}

# 병합 단계의 비교 횟수는 두 부분을 정렬한 결과에 달려 있으므로
# 정렬 결과와 비교 횟수를 함께 돌려주는 내부 함수를 둔다
merge_count <- function(x) {
  sort_count <- function(x) {
    n <- length(x)
    if (n <= 1) return(list(x = x, cnt = 0))
    mid <- n %/% 2L
    a <- sort_count(x[1:mid])
    b <- sort_count(x[(mid + 1):n])
    left <- a$x
    right <- b$x
    out <- numeric(n)
    l <- r <- 1L
    cnt <- a$cnt + b$cnt
    for (i in seq_len(n)) {
      both <- l <= length(left) && r <= length(right)
      if (both) cnt <- cnt + 1         # 양쪽이 모두 남아 있을 때만 비교한다
      if ((both && left[l] <= right[r]) || r > length(right)) {
        out[i] <- left[l]; l <- l + 1L
      } else {
        out[i] <- right[r]; r <- r + 1L
      }
    }
    list(x = out, cnt = cnt)
  }
  sort_count(x)$cnt
}

quick_count <- function(x) {
  if (length(x) <= 1) return(0)
  pivot <- x[1]
  (length(x) - 1) + quick_count(x[x < pivot]) + quick_count(x[x > pivot])
}

```


먼저 무작위 순서의 입력에서 원소 수를 두 배씩 늘려 가며 센다.


```{r sorting-count-random}
set.seed(1234)
sizes <- c(500, 1000, 2000)

  v <- sample(n)                     # 1 부터 n 까지를 무작위 순서로
  c(버블 = bubble_count(v), 삽입 = insertion_count(v),
    병합 = merge_count(v), 퀵 = quick_count(v))
}))

data.frame(n = sizes, cnt)

# n 이 두 배가 될 때 비교 횟수가 늘어난 배율
ratio <- round(cnt[-1, ] / cnt[-nrow(cnt), ], 2)
rownames(ratio) <- c("1000/500", "2000/1000")
ratio

```


$n$ 이 두 배가 될 때 버블 정렬의 비교 횟수는 **정확히 네 배**, 삽입 정렬은 **네 배 가까이**
증가하고, 병합 정렬과 퀵 정렬은 **두 배를 조금 넘는** 수준(2.2\~2.4배)으로 증가한다.
$n^2$ 과 $n\log n$ 의 증가 양상이 표에 그대로 나타난 것이다.
분석으로 얻은 복잡도가 실제 연산 횟수와 일치하는지 대조해 보자.


```{r sorting-count-theory}
data.frame(n = sizes,
           버블 = cnt[, "버블"], `n(n-1)/2` = sizes * (sizes - 1) / 2,
           삽입 = cnt[, "삽입"], `n^2/4` = sizes^2 / 4,
           병합 = cnt[, "병합"], 퀵 = cnt[, "퀵"],
           `n log2(n)` = round(sizes * log2(sizes)),
           check.names = FALSE)

```


버블 정렬의 비교 횟수는 $n(n-1)/2$ 와 **정확히** 일치한다. 삽입 정렬은 무작위 입력에서 그 절반인
$n^2/4$ 근처를 비교한다. 원소 하나를 끼워 넣을 때 평균적으로 앞부분의 절반쯤을 지나가기
때문이다. 병합 정렬과 퀵 정렬은 $n\log_2 n$ 과 같은 규모이며 앞에 붙는 계수만 조금 다르다.
빅오 표기법이 계수를 무시하는 이유가 여기에 있다(@sec-big-o 의 규칙 1).
**이론적으로 분석한 복잡도가 실제 연산 횟수와 일치하는지 확인하는 것 역시 검증이다.**

다음은 입력의 상태를 바꾸어 센다. 원소 수는 1,000개로 고정하고 무작위 순서, 정렬된 순서,
역순 세 가지를 넣는다.


```{r sorting-count-input}
set.seed(1234)
n <- 1000
inputs <- list(무작위 = sample(n), 정렬됨 = 1:n, 역순 = n:1)

t(sapply(inputs, function(v) {
  c(버블 = bubble_count(v), 삽입 = insertion_count(v),

}))

```


정렬된 입력에서 삽입 정렬은 999회로 네 정렬 가운데 가장 적게 비교하고, 퀵 정렬은 499,500회로
버블 정렬과 같아진다. 역순 입력에서는 삽입 정렬도 최악이 된다. 병합 정렬만 입력의 상태와
관계없이 $n \log_2 n$ 이하를 유지한다. **같은 알고리즘이라도 입력에 따라 비용이 달라지므로,
비용을 말할 때는 어떤 입력에서의 비용인지(최선·평균·최악)를 함께 밝혀야 한다.**

실행 시간도 함께 측정한다. 측정값은 환경에 따라 변동하지만 차수의 차이는 그대로 드러난다.

퀵 정렬이 병합 정렬보다 비교를 더 많이 하는데도 더 빠르게 측정되는 것은, `x[x < pivot]` 과 같은
R 의 벡터 연산이 내부에서 C 로 실행되어 R 의 `for` 반복문보다 훨씬 빠르기 때문이다. 차수가 같을 때는
이런 구현의 차이, 곧 빅오가 무시한 계수가 실제 시간을 좌우한다.

정확성도 함께 확인한다. 속도만 측정하고 결과의 정확성을 확인하지 않는 벤치마크는 의미가 없다.


```{r sorting-correctness}
set.seed(99)
same <- function(a, b) length(a) == length(b) && all(a == b)

checks <- replicate(200, {
  n <- sample(0:50, 1)                     # 길이 0 인 벡터도 포함한다
  v <- sample(1:20, n, replace = TRUE)     # 중복값을 포함시킨다
  s <- sort(v)
  same(bubble_sort(v), s) && same(insertion_sort(v), s) &&
    same(merge_sort(v), s) && same(quick_sort(v), s)
})

all(checks)

```


네 정렬의 성질을 정리하면 다음과 같다. 최선·최악의 경우는 이 장의 구현 기준이다.

| 정렬 | 방식 | 최선 | 평균 | 최악 | 추가 메모리 |
|:--|:--|:--|:--|:--|:--|
| 버블 | 인접한 두 원소를 교환 | $\mathcal{O}(n^2)$ | $\mathcal{O}(n^2)$ | $\mathcal{O}(n^2)$ | $\mathcal{O}(1)$ |
| 삽입 | 앞부분의 제자리에 끼워 넣기 | $\mathcal{O}(n)$ 정렬된 입력 | $\mathcal{O}(n^2)$ | $\mathcal{O}(n^2)$ 역순 입력 | $\mathcal{O}(1)$ |
| 병합 | 절반으로 나누어 정렬한 뒤 병합 | $\mathcal{O}(n \log n)$ | $\mathcal{O}(n \log n)$ | $\mathcal{O}(n \log n)$ | $\mathcal{O}(n)$ |
| 퀵 | 기준값으로 나눈 뒤 이어 붙이기 | $\mathcal{O}(n \log n)$ | $\mathcal{O}(n \log n)$ | $\mathcal{O}(n^2)$ 정렬된 입력 | $\mathcal{O}(n)$, 최악 $\mathcal{O}(n^2)$ |

: {tbl-colwidths="[8,28,15,13,20,16]"}


::: {.callout-note}
**R 의 `sort()` 는 무엇을 쓰는가**: 기본값 `method = "auto"` 는 길이가 $2^{31}$ 보다 짧은
수치·정수·논리 벡터와 요인에는 **기수 정렬(radix sort)** 을, 그 밖의 경우(문자 벡터 등)에는
셸 정렬(Shellsort)을 쓴다(`?sort`). 기수 정렬은 원소끼리 비교하는 대신 값을 자릿수(바이트)
단위로 나누어 배치하는 방식이며, 도움말에 따르면 $\mathcal{O}(n)$ 으로 동작한다.
`sort(x, method = "quick")` 로 퀵 정렬을 지정할 수도 있다.

실무에서는 정렬을 직접 구현하지 않고 `sort()`, `order()` 를 쓴다. 이 절에서 네 정렬을 직접
구현한 목적은 비용이 어디서 생기는지 이해하고, 주어진 구현을 검증하는 능력을 기르는 데 있다.

:::


## 뉴턴-랩슨 알고리즘 {#sec-newton-raphson}

앞의 절들이 자료를 처리하는 알고리즘을 다루었다면, 이 절에서는 **수치 계산** 알고리즘을
다룬다. $f(x) = 0$ 을 만족하는 $x$ 를 반복 계산으로 구하는 방법이다.

통계학에서 이 알고리즘이 중요한 이유는 **추정이 곧 최적화(optimization) 문제**이기 때문이다.
회귀계수의 최소제곱추정은 잔차제곱합을 **최소**로 만드는 값을, 최대가능도추정은 가능도를
**최대**로 만드는 값을 찾는다. 함수가 최소나 최대가 되는 지점에서는 도함수가 0 이므로, 결국
"도함수 $= 0$" 이라는 방정식을 푸는 문제가 된다. 이 절의 앞부분(@sec-nr-principle 부터
@sec-nr-verification 까지)에서 방정식의 해를 구하는 원리를 익히고, 뒷부분(@sec-nr-optimization
부터 @sec-nr-logistic 까지)에서 회귀모형과 로지스틱 회귀모형의 계수를 이 방법으로 구한다.
마지막으로 같은 문제를 푸는 또 다른 방법인 경사하강법을 간단히 소개한다(@sec-gradient-descent).

적용 조건은 두 가지다. 탐색 구간에 해가 존재해야 하고, $f$ 가 미분 가능해야 한다.

### 원리와 점화식 {#sec-nr-principle}

알고리즘의 진행은 다음 네 단계로 이루어진다.

1. 초기값 $x_0$ 을 설정한다.
2. $x_n$ 에서 접선을 구한다. 접선의 기울기는 $f'(x_n)$ 이다.
3. 접선이 $x$ 축과 만나는 점을 다음 근사값 $x_{n+1}$ 로 정한다.
4. 종료 조건을 만족할 때까지 2\~3을 반복한다.

$(x_n, f(x_n))$ 을 지나는 접선의 식은 $y = f'(x_n)(x - x_n) + f(x_n)$ 이고,
$y = 0$ 인 $x$ 를 풀면 다음 점화식을 얻는다.

$$
 x_{n+1} = x_n - \frac{f(x_n)}{f'(x_n)}
$$

이 점화식에 따르면 함수값이 0에서 멀수록 갱신 폭이 커지고, 기울기의 절대값이 클수록
갱신 폭이 작아진다. 종료 조건은 일반적으로 다음 세 가지를 함께 사용한다.

- 최대 반복 횟수를 초과한 경우
- $x$ 의 갱신 폭이 충분히 작아진 경우
- $|f(x)|$ 가 허용 오차(`tol`) 이내로 0에 근접한 경우


### 구현 {#sec-nr-implementation}

앞의 종료 조건 세 가지를 그대로 인수로 받는다. 도함수는 `deriv()` 로 함수 본문에서
직접 유도하며, 해가 존재하는 구간을 `range` 로 제한해 발산을 막는다.


```{r newton-raphson}
newton_raphson <- function(FUN, x0 = 1, max_iters = 5000,
                           tol = 1e-9, range = c(-Inf, Inf)) {
  grads <- deriv(as.expression(body(FUN)), "x", function.arg = TRUE)
  iters <- 1L
  gap <- Inf

  while (iters < max_iters && abs(gap) > tol) {
    slope <- attr(grads(x0), "gradient")
    if (slope == 0) stop("미분계수가 0이므로 다음 근사값을 계산할 수 없다.")
    x_new <- x0 - FUN(x0) / slope
    if (x_new <= range[1]) x_new <- range[1]
    if (x_new >= range[2]) x_new <- range[2]
    gap <- FUN(x_new)
    iters <- iters + 1L
    x0 <- x_new
  }

  list(solution = x_new, iteration = iters, value = FUN(x_new))
}

f <- function(x) 5 * x^3 - 7 * x^2 - 40 * x + 100

sol <- newton_raphson(f, x0 = 1, range = c(-10, 10))
sol

```


### 해의 검증과 초기값 의존성 {#sec-nr-verification}

결과를 검증한다. 3차 다항식이므로 `polyroot()` 로 모든 근을 구해 대조할 수 있다.


```{r newton-raphson-check}
roots <- polyroot(c(100, -40, -7, 5))     # 상수항부터 오름차순 계수
roots

# 허수부가 0인 것만 실근이다
Re(roots)[abs(Im(roots)) < 1e-8]

```


이 함수의 **실근은 하나뿐**이며, 뉴턴-랩슨 알고리즘이 구한 값과 일치한다.
나머지 두 근은 켤레 복소수이므로 실수 축에서는 나타나지 않는다.
그림에서 곡선이 $x$ 축과 한 번만 교차하는 이유가 여기에 있다.

초기값을 달리하면 수렴하는 해는 같으나 수렴에 필요한 반복 횟수가 달라진다.


```{r newton-raphson-x0}
inits <- c(-5, -1, 0, 1, 5)
t(sapply(inits, function(x0) {
  r <- newton_raphson(f, x0 = x0, range = c(-10, 10))
  c(x0 = x0, 해 = r$solution, 반복 = r$iteration)
}))

```


::: {.callout-caution}
뉴턴-랩슨 알고리즘은 수렴 속도가 빠르지만 **초기값에 민감하다.** 기울기가 0에 가까운
지점에서 출발하면 다음 근사값이 크게 벗어나고, $f'(x) = 0$ 이면 점화식을 계산할 수 없다.
해가 여러 개인 함수에서는 어느 해로 수렴하는지를 초기값이 결정한다.
따라서 결과를 얻은 뒤에는 **그 값이 실제로 해인지($f(x) \approx 0$)**, 그리고
**의도한 해가 맞는지**를 반드시 확인해야 한다.

:::


### 최적화: 극값은 도함수의 근이다 {#sec-nr-optimization}

미분 가능한 함수 $f$ 가 어떤 점에서 극값을 가지면 그 점의 접선은 수평이다. 즉 도함수가 0 이다.
따라서 극값을 찾는 문제는 **도함수 $f'$ 의 근을 찾는 문제**가 되고, 앞의 점화식에서 $f$ 자리에
$f'$ 을, $f'$ 자리에 $f''$ 을 넣으면 된다.

$$
 x_{n+1} = x_n - \frac{f'(x_n)}{f''(x_n)}
$$

앞에서 쓴 $f(x) = 5x^3 - 7x^2 - 40x + 100$ 의 극값을 구해 보자. 도함수는
$f'(x) = 15x^2 - 14x - 40$ 이다. 손으로 구한 도함수는 R 의 기호 미분 함수 `D()` 로 대조한다.


```{r nr-opt-deriv}
fp <- function(x) 15 * x^2 - 14 * x - 40     # 손으로 구한 f'(x)

D(body(f), "x")                               # R 이 기호 미분한 결과

```


출력된 식을 정리하면 손으로 구한 식과 같다. 이제 `newton_raphson()` 에 `f` 대신 `fp` 를 넣는다.
함수를 새로 만들 필요는 없다. `newton_raphson()` 이 안에서 `fp` 를 한 번 더 미분해 $f''$ 을 얻는다.


::: {.callout-tip}
**예측해 보자**: 초기값 $-5, -1, 0, 1, 5$ 에서 출발하면 모두 같은 점에 도착하겠는가?
도착한 점은 모두 $f$ 를 가장 작게 만드는 점이겠는가?

:::


```{r nr-opt-run}
inits <- c(-5, -1, 0, 1, 5)
opt <- t(sapply(inits, function(x0) {
  r <- newton_raphson(fp, x0 = x0)
  c(x0 = x0, 해 = r$solution, 반복 = r$iteration)
}))

# 2계 도함수 f''(x) = 30x - 14 의 부호로 극소와 극대를 가린다
d2 <- 30 * opt[, "해"] - 14
data.frame(opt, `f''(해)` = d2, 판정 = ifelse(d2 > 0, "극소", "극대"),
           check.names = FALSE)

```


초기값에 따라 두 점으로 갈라진다. $x \approx 2.165$ 에서는 $f'' > 0$ 이므로 **극소**,
$x \approx -1.232$ 에서는 $f'' < 0$ 이므로 **극대**다. 알고리즘은 $f'(x) = 0$ 인 점을 찾을 뿐,
그 점이 극소인지 극대인지는 가리지 않는다. R 의 1차원 최적화 함수 `optimize()` 와도 대조해 둔다.


```{r nr-opt-check}
optimize(f, interval = c(0, 5))                    # 구간 [0, 5] 에서 최솟값
optimize(f, interval = c(-5, 0), maximum = TRUE)   # 구간 [-5, 0] 에서 최댓값

```


::: {.callout-caution}
$f'(x) = 0$ 은 극값의 **후보**일 뿐이다. 결과를 얻은 뒤에는 (1) 2계 도함수의 부호로 극소인지
극대인지 확인하고, (2) 그 극소가 관심 있는 범위 전체에서의 최소인지 확인해야 한다. 이 $f$ 는
$x$ 가 작아질수록 한없이 작아지므로 $x \approx 2.165$ 는 극소이지만 전체의 최소는 아니다.
로그가능도처럼 봉우리가 여러 개인 함수에서는 초기값에 따라 서로 다른 봉우리에 도착한다.

:::


모수가 두 개 이상이면 점화식의 각 자리가 벡터와 행렬로 바뀐다. 이어지는 두 소절에서 이 형태를 쓴다.


::: {.callout-note}
**모수가 여러 개일 때의 뉴턴-랩슨**

$$
 \boldsymbol{\theta}_{n+1} = \boldsymbol{\theta}_n - \mathbf{H}^{-1} \nabla f(\boldsymbol{\theta}_n)
$$

- $\nabla f$ : **기울기 벡터(gradient)**. 각 모수로 편미분한 값을 모은 벡터이며, $f'$ 의 자리다.
- $\mathbf{H}$ : **헤세 행렬(Hessian matrix)**. 2계 편미분을 모은 행렬이며, $f''$ 의 자리다.
- 나눗셈은 역행렬을 곱하는 것으로 바뀐다. R 에서는 역행렬을 직접 구하지 않고 `solve(H, g)` 로
  연립방정식 $\mathbf{H}\mathbf{d} = \nabla f$ 를 풀어 갱신량 $\mathbf{d}$ 를 얻는다.

:::


### 회귀모형: 정규방정식은 뉴턴-랩슨의 한 걸음이다 {#sec-nr-regression}

`mtcars` 의 연비(`mpg`)를 무게(`wt`)로 설명하는 단순선형회귀모형
$y_i = \beta_0 + \beta_1 x_i + \varepsilon_i$ 를 생각하자. 최소제곱추정은 잔차제곱합

$$
 S(\boldsymbol\beta) = \sum_{i=1}^{n} (y_i - \beta_0 - \beta_1 x_i)^2
 = (\mathbf{y} - \mathbf{X}\boldsymbol\beta)^\top (\mathbf{y} - \mathbf{X}\boldsymbol\beta)
$$

을 최소로 만드는 $\boldsymbol\beta = (\beta_0, \beta_1)^\top$ 를 찾는다. $\mathbf{X}$ 는 첫 열이
모두 1(절편)이고 둘째 열이 $x_i$ 인 $n \times 2$ 행렬이다. 기울기 벡터와 헤세 행렬은 다음과 같다.

$$
 \nabla S = -2\mathbf{X}^\top(\mathbf{y} - \mathbf{X}\boldsymbol\beta), \qquad
 \mathbf{H} = 2\mathbf{X}^\top\mathbf{X}
$$


::: {.callout-tip}
**예측해 보자**: 초기값 $(0, 0)$ 에서 출발하면 뉴턴-랩슨 알고리즘은 몇 번 반복해야 수렴하겠는가?
초기값을 $(100, -50)$ 으로 바꾸면 어떻게 되겠는가?

:::


```{r nr-ls}
X <- cbind(1, mtcars$wt)      # 첫 열은 절편에 곱해지는 1
y <- mtcars$mpg

# 뉴턴-랩슨 한 걸음: beta - H^{-1} g
nr_step_ls <- function(beta, X, y) {
  g <- -2 * t(X) %*% (y - X %*% beta)    # 기울기 벡터
  H <- 2 * t(X) %*% X                    # 헤세 행렬: beta 가 들어 있지 않다
  as.vector(beta - solve(H, g))
}

b1 <- nr_step_ls(c(0, 0), X, y)
b1

nr_step_ls(b1, X, y)                     # 한 걸음 더 가도 제자리다
nr_step_ls(c(100, -50), X, y)            # 출발점을 바꾸어도 한 걸음에 같은 점

```


**한 걸음 만에** 도착하고, 한 걸음 더 가도 움직이지 않는다. 출발점도 결과를 바꾸지 못한다.
점화식에 기울기 벡터와 헤세 행렬을 대입해 보면 이유가 드러난다.

$$
 \boldsymbol\beta_1
 = \boldsymbol\beta_0 + (\mathbf{X}^\top\mathbf{X})^{-1}\mathbf{X}^\top(\mathbf{y} - \mathbf{X}\boldsymbol\beta_0)
 = (\mathbf{X}^\top\mathbf{X})^{-1}\mathbf{X}^\top\mathbf{y}
$$

초기값 $\boldsymbol\beta_0$ 가 소거된다. 뉴턴-랩슨은 매 걸음 목적함수를 2차 함수로 근사한 뒤 그
2차 함수의 최소점으로 이동하는데, 잔차제곱합은 원래 $\boldsymbol\beta$ 의 2차 함수이므로 근사가
곧 정확한 식이 된다. 결과는 **정규방정식(normal equations)**
$\mathbf{X}^\top\mathbf{X}\boldsymbol\beta = \mathbf{X}^\top\mathbf{y}$ 의 해이며, 회귀분석에서
배우는 최소제곱추정량 공식 그 자체다. `lm()` 과 대조한다.


```{r nr-ls-check}
coef(lm(mpg ~ wt, data = mtcars))

all.equal(b1, unname(coef(lm(mpg ~ wt, data = mtcars))))

```


두 결과를 `==` 가 아니라 `all.equal()` 로 비교했다. 같은 식이라도 계산 순서가 다르면 소수점
아래 열다섯째 자리 부근에서 차이가 날 수 있으므로, 실수는 허용 오차 안에서 같은지를 확인한다.


::: {.callout-note}
`lm()` 은 정규방정식을 그대로 풀지 않고 $\mathbf{X}$ 의 **QR 분해**를 이용한다. 설명변수끼리
상관이 매우 높으면 $\mathbf{X}^\top\mathbf{X}$ 로 계산하는 과정이 수치적으로 불안정해지기
때문이다. 수식으로는 같은 답이라도 **계산하는 방법에 따라 정확도가 달라진다.**

:::


### 로지스틱 회귀모형: 반복이 필요한 경우 {#sec-nr-logistic}

반응변수가 0 또는 1 인 자료가 있다. 합격·불합격, 발병·비발병처럼 결과가 두 가지인 경우다.
`mtcars` 의 `am` 은 변속기가 자동이면 0, 수동이면 1 이다. 무게가 변속기 종류와 관련이 있는지
보려면, 수동일 확률 $p_i$ 를 무게 $x_i$ 로 설명하는 **로지스틱 회귀모형(logistic regression
model)** 을 쓴다.

$$
 p_i = P(y_i = 1) = \frac{1}{1 + e^{-(\beta_0 + \beta_1 x_i)}}
$$

계수는 로그가능도

$$
 \ell(\boldsymbol\beta) = \sum_{i=1}^{n} \bigl\{ y_i \log p_i + (1 - y_i) \log (1 - p_i) \bigr\}
$$

를 **최대**로 만드는 값으로 추정한다. 기울기 벡터와 헤세 행렬은 다음과 같다.

$$
 \nabla \ell = \mathbf{X}^\top(\mathbf{y} - \mathbf{p}), \qquad
 \mathbf{H} = -\mathbf{X}^\top\mathbf{W}\mathbf{X}, \quad
 \mathbf{W} = \mathrm{diag}\{p_i(1 - p_i)\}
$$

회귀모형과 달리 $\mathbf{H}$ 안에 $p_i$, 곧 $\boldsymbol\beta$ 가 들어 있다. 걸음마다 헤세 행렬이
달라지므로 한 걸음에 끝나지 않고, $\nabla \ell = \mathbf{0}$ 의 해를 손으로 구할 수도 없다.
반복 계산이 필요한 전형적인 경우다.


```{r nr-logistic}
# 로그가능도: 반복마다 값이 커지는지 확인하는 데 쓴다
loglik <- function(beta, X, y) {
  p <- as.vector(1 / (1 + exp(-X %*% beta)))
  sum(y * log(p) + (1 - y) * log(1 - p))
}

logistic_nr <- function(X, y, beta = rep(0, ncol(X)),
                        tol = 1e-8, max_iters = 50) {
  history <- NULL
  for (iter in seq_len(max_iters)) {
    p <- as.vector(1 / (1 + exp(-X %*% beta)))   # 현재 계수에서 구한 확률
    g <- t(X) %*% (y - p)                         # 기울기 벡터
    H <- -t(X) %*% (X * (p * (1 - p)))            # 헤세 행렬: X 의 각 행에 p(1-p) 를 곱함
    step <- as.vector(solve(H, g))
    beta <- beta - step
    b <- setNames(beta, paste0("b", seq_along(beta) - 1))
    history <- rbind(history, c(반복 = iter, b, 로그가능도 = loglik(beta, X, y),
                                갱신폭 = max(abs(step))))
    if (max(abs(step)) < tol) break               # 계수가 더 움직이지 않으면 멈춘다
  }
  list(beta = beta, history = history)
}

fit_nr <- logistic_nr(X, mtcars$am)
fit_nr$history

```


로그가능도는 반복마다 커지다가 더 커지지 않는 값에서 멈춘다. 갱신폭은 해에 가까워질수록
급격히 줄어든다. 해 근처에서 뉴턴-랩슨은 오차가 대략 제곱으로 줄어드는 **2차 수렴(quadratic
convergence)** 을 보이며, 표에서 갱신폭의 0 이 아닌 첫 자리가 반복마다 두 배쯤씩 뒤로 밀려나는
것이 그 모습이다. `glm()` 과 대조한다.


```{r nr-logistic-glm}
fit_glm <- glm(am ~ wt, family = binomial, data = mtcars)
coef(fit_glm)

all.equal(fit_nr$beta, unname(coef(fit_glm)))

```


`glm()` 의 결과와 일치한다. 무게의 계수가 음수이므로 무거운 차일수록 수동 변속기일 확률이 낮다.


::: {.callout-note}
`glm()` 은 이 계산을 **반복 재가중 최소제곱(IRLS, iteratively reweighted least squares)** 이라는
형태로 수행한다. 매 반복에서 가중값 $p_i(1-p_i)$ 를 쓰는 가중 최소제곱 문제를 푸는 방식이며,
로지스틱 회귀모형에서는 뉴턴-랩슨과 같은 계산이다. `summary(fit_glm)` 의 마지막 줄
"Number of Fisher Scoring iterations" 가 그 반복 횟수다(이 자료에서 `r fit_glm$iter` 회).
위 구현과 횟수가 다른 것은 종료 조건이 다르기 때문이다. `glm()` 은 계수의 갱신폭이 아니라
이탈도(deviance)의 상대 변화가 $10^{-8}$ 보다 작아지면 멈춘다(`?glm.control`).

:::


### 경사하강법 맛보기 {#sec-gradient-descent}

짙은 안개가 낀 산에서 골짜기로 내려가야 한다고 하자. 멀리는 보이지 않고 발밑의 경사만 느낄 수
있다. 가장 가파르게 내려가는 방향으로 한 걸음 옮기고, 그 자리에서 다시 경사를 느끼고 한 걸음
옮기는 일을 반복하면 언젠가 골짜기에 닿는다. 이것이 **경사하강법(gradient descent)** 이다.

$$
 \boldsymbol\theta_{n+1} = \boldsymbol\theta_n - \eta \, \nabla f(\boldsymbol\theta_n)
$$

기울기의 반대 방향으로 기울기의 $\eta$ 배만큼 이동한다. $\eta$ 를 **학습률(learning rate)** 이라
한다. 뉴턴-랩슨과 비교하면 헤세 행렬의 역행렬 $\mathbf{H}^{-1}$ 자리에 상수 $\eta$ 가 들어간
형태다. 곡률을 이용해 보폭을 정하는 대신 **보폭을 사람이 정한다.**

@sec-nr-regression 의 회귀계수를 경사하강법으로 구해 보자. 목적함수는 잔차제곱합을 $n$ 으로 나눈
평균제곱오차로 둔다. 최소점은 같고 기울기의 크기만 작아진다.


::: {.callout-tip}
**예측해 보자**: 뉴턴-랩슨은 이 문제를 한 걸음에 풀었다. 경사하강법은 몇 걸음이 필요하겠는가?
10걸음 안쪽, 100걸음 안쪽, 1,000걸음 이상 가운데 골라 보자.

:::


```{r gd-ls}
gd_ls <- function(X, y, eta, beta = c(0, 0), tol = 1e-6, max_iters = 1e5) {
  n <- nrow(X)
  for (iter in seq_len(max_iters)) {
    g <- as.vector(-2 / n * t(X) %*% (y - X %*% beta))   # 평균제곱오차의 기울기
    if (sqrt(sum(g^2)) < tol) break        # 기울기가 거의 0 이면 도착
    beta <- beta - eta * g                 # 기울기 반대 방향으로 eta 배만큼
    if (max(abs(beta)) > 1e6) {            # 값이 끝없이 커지면 발산
      return(c(학습률 = eta, 반복 = iter, b0 = NA, b1 = NA))
    }
  }
  c(학습률 = eta, 반복 = iter, b0 = beta[1], b1 = beta[2])
}

t(sapply(c(0.01, 0.05, 0.08, 0.09), function(eta) gd_ls(X, y, eta)))

```


학습률이 알맞으면 `lm()` 과 같은 값에 도착하지만 **1,000걸음이 넘게** 걸린다. 학습률을 줄이면
걸음이 더 늘고, 조금만 키워도(0.09) 골짜기를 넘나들며 점점 멀어져 발산한다. 알맞은 학습률의
범위는 문제마다 다르므로 대개 여러 값을 시험해 정한다.

걸음이 이렇게 많은데도 경사하강법을 쓰는 이유는 **한 걸음의 비용**에 있다.

| | 뉴턴-랩슨 | 경사하강법 |
|:--|:--|:--|
| 쓰는 도함수 | 1계와 2계 (기울기 벡터, 헤세 행렬) | 1계 (기울기 벡터)만 |
| 한 걸음의 비용 | 모수가 $p$ 개이면 $p \times p$ 행렬을 저장하고 연립방정식을 푼다 | 길이 $p$ 인 벡터 하나를 계산한다 |
| 걸음 수 | 적다 (회귀 1회, 로지스틱 8회) | 많다 (위 회귀에서 1,000회 이상) |
| 정해야 할 값 | 초기값 | 초기값, 학습률 |
| 주로 쓰는 곳 | 모수가 적은 통계모형 (`glm()` 등) | 모수가 매우 많은 기계학습·딥러닝 |

: {tbl-colwidths="[18,41,41]"}

모수가 1,000만 개라면 헤세 행렬의 원소는 $10^{14}$ 개로, 저장하는 것조차 불가능하다. 대규모 언어
모형(LLM)을 비롯한 딥러닝 모형은 수십억 개가 넘는 모수를 가지며, 경사하강법을 변형한 방법(확률적
경사하강법, Adam 등)으로 학습한다. **걸음 수가 적은 알고리즘과 한 걸음이 싼 알고리즘 가운데 어느
쪽이 나은지는 문제의 크기가 정한다.** 이 장 첫 절에서 말한 비용, 곧 수행 시간과 메모리를 함께
따지는 판단이다.


::: {.callout-note}
이 소절은 경사하강법이라는 방법이 **있다는 것**과 뉴턴-랩슨과의 차이를 소개하는 데 그친다.
학습률을 자동으로 조정하는 방법, 자료의 일부만으로 기울기를 계산하는 확률적 경사하강법 등은
기계학습을 다루는 과목에서 배운다. R 에서 일반적인 최적화 문제는 `optim()` 으로 풀 수 있으며,
`method` 인수로 헤세 행렬을 근사해 쓰는 준뉴턴법(`"BFGS"`)이나 기울기만 쓰는 켤레기울기법(`"CG"`)
등을 고를 수 있다.

:::


## AI와 함께: 생성 코드의 검증 {#sec-ai-algorithms}


::: {.callout-important}
**이 절의 목표**: LLM 에 재귀 이진 탐색 함수의 생성을 요청하고, 생성된 코드를

### 작업 요구사항 {#sec-ai-algorithms-spec}

프롬프트는 곧 요구사항이다. 요구사항이 불완전하면 그 부분은 구현자의 임의 판단으로
채워진다. 아래는 의도적으로 **통상적인 수준으로만** 작성한 요구사항이다.

> 오름차순으로 정렬된 수치형 벡터 `vec` 과 값 `target` 을 받아,
> `target` 이 있으면 그 위치(인덱스)를, 없으면 `NA` 를 반환하는
> 재귀 이진 탐색 함수를 R 로 작성하라.


### AI 가 생성한 코드 {#sec-ai-algorithms-gen}

아래는 위 요구사항으로 실제 생성된 응답이며 **수정 없이 그대로 수록했다.**


```{r ai-generated}
# 생성: Claude Opus 5, 2026-09-11. 수정 없이 그대로 수록.
binary_search_rec <- function(vec, target, lo = 1, hi = length(vec)) {
  if (lo > hi) return(NA_integer_)
  mid <- (lo + hi) %/% 2
  if (vec[mid] == target) {
    return(mid)
  } else if (vec[mid] > target) {
    binary_search_rec(vec, target, lo, mid - 1)
  } else {
    binary_search_rec(vec, target, mid + 1, hi)
  }
}

```


앞 절에서 수정한 구현과 동일한 구조이며, 종료 조건도 `lo > hi` 로 올바르게 지정되어
있다. 그럼에도 검증 절차를 수행한다.


### 검증 {#sec-ai-algorithms-verify}

**검증 1. 전수 검사** — 벡터의 모든 원소를 목표값으로 입력한다.


```{r ai-verify-exhaustive}
x <- seq(1, 40, by = 3)
found <- vapply(seq_along(x), function(i) {
  as.integer(binary_search_rec(x, x[i]))
}, integer(1))

all(found == seq_along(x))

```


**검증 2. 경계 사례** — 빈 벡터, 길이가 1인 벡터, 존재하지 않는 값.


```{r ai-verify-edge}
c(빈벡터 = binary_search_rec(numeric(0), 5),
  길이1적중 = binary_search_rec(7, 7),
  길이1불발 = binary_search_rec(7, 9),
  없는값 = binary_search_rec(x, 2))

```


**검증 3. 무작위 대조** — 정답이 알려진 `which()` 와 500회 대조한다.


```{r ai-verify-random}
set.seed(20260911)
n_fail <- 0
for (i in 1:500) {
  n <- sample(1:60, 1)
  v <- sort(sample(1:200, n))
  k <- if (runif(1) < 0.7) sample(v, 1) else sample(1:200, 1)
  got <- binary_search_rec(v, k)
  want <- which(v == k)
  ok <- if (length(want) == 0) is.na(got) else (!is.na(got) && got %in% want)
  if (!ok) n_fail <- n_fail + 1
}
n_fail

```


세 가지 검증을 모두 통과했다. **요구사항의 범위 안에서는** 이 코드가 옳다.
문제는 요구사항이 규정하지 않은 영역에서 발생한다.


### 요구사항이 규정하지 않은 부분 {#sec-ai-algorithms-gaps}

**미규정 1. 중복값이 있으면 어느 위치를 반환하는가?**
요구사항에 규정되어 있지 않으므로 구현이 임의로 결정한다.


```{r ai-gap-duplicates}
d <- c(1, 3, 3, 3, 5, 7)

binary_search_rec(d, 3)    # 이 구현이 반환한 위치
which(d == 3)              # 3이 존재하는 모든 위치
match(3, d)                # R 의 관례: 가장 앞

```


R 의 `match()` 는 가장 앞의 위치를 반환하지만, 이 구현은 중간 위치를 반환한다.
어느 쪽도 그 자체로 오류는 아니나, **호출하는 쪽이 앞의 위치를 기대했다면 오류가 된다.**

**미규정 2. 정렬되지 않은 입력이 들어오면 어떻게 되는가?**
요구사항은 "정렬된 벡터"를 전제했으나, 그 전제가 성립하지 않을 때의 동작은 규정하지 않았다.


```{r ai-gap-unsorted}
u <- c(19, 7, 2, 15, 10)      # 정렬되어 있지 않은 벡터

binary_search_rec(u, 19)      # 19 는 1번 위치에 존재한다
which(u == 19)

```


오류나 경고 없이 값이 존재하지 않는다고 반환한다.
**오류 없이 잘못된 결과를 반환하는 편이 명시적으로 실패하는 편보다 훨씬 위험하다.**

**미규정 3. `NA` 가 포함되어 있으면 어떻게 되는가?**


```{r ai-gap-na, error=TRUE}
binary_search_rec(c(1, 3, NA, 7), 7)

```


이 경우에는 오류가 발생하며 실행이 중단된다. 앞의 두 경우보다 오히려 바람직하다.
결함을 즉시 인지할 수 있기 때문이다.

요구사항의 전제를 강제하도록 방어 코드를 추가하면 다음과 같다.


```{r ai-gap-fixed}
binary_search_safe <- function(vec, target) {
  stopifnot(is.numeric(vec), length(target) == 1L)
  if (anyNA(vec)) stop("vec 에 NA 가 포함되어 있다.")
  if (is.unsorted(vec)) stop("vec 이 오름차순으로 정렬되어 있지 않다.")
  binary_search_rec(vec, target)
}

binary_search_safe(x, x[5])

```


```{r ai-gap-fixed-error, error=TRUE}
binary_search_safe(u, 19)

```


::: {.callout-caution}
**AI 생성 코드에서 자주 나타나는 오류 유형**

- **경계 조건**: `<` 와 `<=`, `mid` 와 `mid - 1` 을 혼동한다. 이 장의
`rbinary_search()` 가 정확히 이 유형이며, 사람이 작성한 코드에서도 동일하게 나타난다.
- **전제 미검사**: "정렬되어 있다", "`NA` 가 없다"와 같은 전제를 확인하지 않는다.
- **빈 입력**: 길이가 0인 벡터에서 인덱스 1을 참조한다.
- **요구사항의 공백**: 중복값이나 동점 처리와 같이 요구사항이 규정하지 않은 부분을
임의로 결정하고, 그 선택을 명시하지 않는다.

이 유형들의 공통점은 **오류 메시지가 출력되지 않는다**는 점이다. 따라서 실행해 보는
것만으로는 부족하며 별도의 검증 절차가 필요하다.

:::
