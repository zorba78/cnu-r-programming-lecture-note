오른쪽은 엑셀 파일입니다. 첫 두 바이트가 PK 입니다. ZIP 압축 형식을 만든 필 카츠라는 사람의 머리글자예요. 엑셀 파일은 사실 XML 파일 여러 개를 묶은 압축 파일입니다. 메모장으로 열면 알아볼 수 없는 기호만 나오는 이유이고, 전용 함수가 필요한 이유입니다.

아래 상자를 보세요. 읽기 함수는 바이트를 약속에 따라 해석합니다. 약속이 어긋나면 해석이 틀립니다. 틀린 해석은 오류로 멈추기도 하지만, 오류 없이 행과 열을 갖춘 표를 내놓고 끝나기도 합니다. 뒤의 경우는 오류 메시지가 없어서, 결과를 원문과 대조하기 전에는 틀린 줄 모릅니다.

read_csv 는 첫 줄 기준으로 열 3개를 만들고, 넘치는 조각을 마지막 열에 붙였습니다. 수량 열에 “000원,2” 가 들어갔지요. 대신 문제로 기록해 둡니다. 아래 표가 problems 로 본 기록입니다. 2번째 줄, 3칸이어야 하는데 4칸이다.

셋째 줄은 따옴표 덕분에 4,500원 이 한 값으로 들어갔습니다. 이게 CSV 의 약속입니다. 값 안에 쉼표가 있으면 큰따옴표로 감쌉니다.

오른쪽은 같은 파일을 read.csv 로 읽은 결과입니다. 오류도 경고도 없습니다. 그런데 사과와 배가 행 이름으로 빠지고 값이 한 칸씩 밀렸어요. 데이터 줄이 머리글보다 한 칸 많으면 첫 칸을 행 이름으로 쓰는 규칙 때문입니다.

같은 파일을 두 함수가 다르게 틀립니다. read_csv 는 문제를 기록으로 남기고, read.csv 는 기록 없이 값을 한 칸씩 밀어 넣습니다.

한글 파일에서 흔히 만나는 정답표는 두 가지입니다. UTF-8 은 전 세계 문자를 담는 표준이고 한글 한 글자에 3바이트를 씁니다. CP949 는 한국어 Windows 가 오래 써 온 방식이고 한 글자에 2바이트입니다. 한국어 엑셀에서 CSV 로 저장한 파일이나 공공기관에서 받은 CSV 는 CP949 일 수 있으니 먼저 확인합니다.

해결은 오른쪽입니다. 인코딩을 모르면 guess_encoding 으로 짐작하고, locale 에 인코딩을 알려 줍니다. 그러면 열 이름이 한글로 읽힙니다.

base R 에서는 fileEncoding 인수를 씁니다. read.csv 에는 encoding 이라는 비슷한 이름의 인수도 있는데, 이 인수는 변환을 하지 않습니다.

guess_encoding 이 EUC-KR 이라고 알려 줘도 CP949 를 지정하세요. CP949 가 EUC-KR 을 넓힌 방식이라, 똠이나 펲 같은 글자는 EUC-KR 에 없습니다.

아래 상자. R 4.1 까지는 한국어 Windows 의 R 이 CP949 를 기본으로 써서 CP949 파일이 그냥 읽혔습니다. R 4.2.0 부터 Windows 10 버전 1903 이상에서도 UTF-8 이 기본이 되었습니다. 그래서 인코딩을 안 적은 옛 예제가 이제는 Windows 에서도 깨집니다. 운영체제와 상관없이 인코딩은 늘 명시하세요.

    "도서관 행 수가 원문과 같다" =

4.3 엑셀에서 열 CSV

증상

  • R 에서 UTF-8 로 저장한 CSV 를 한국어 Windows 의 Excel 에서 열면 한글이 깨질 수 있음
  • 아무 표시가 없는 CSV 를 Excel 이 시스템 기본 인코딩(CP949)으로 읽음
readBin(out_excel, "raw", n = 3)
[1] ef bb bf
readBin(out_readr, "raw", n = 3)
[1] eb 8f 84

받는 사람에 맞춰 쓰기

  • Excel 로 열 사람: write_excel_csv(), 맨 앞 세 바이트 BOM(ef bb bf)이 “이 CSV 는 UTF-8” 이라고 알림 (readr 도움말)
  • CP949 만 받는 옛 프로그램: write.csv(…, fileEncoding = “CP949”)
  • R, Python 등으로 읽을 사람: write_csv() 그대로

어느 쪽이든 받은 사람이 열어 본 결과를 한 번은 확인

R 에서 저장한 CSV 를 엑셀로 열면 한글이 깨질 수 있습니다.

R 은 UTF-8 로 저장하는데, 아무 표시가 없는 CSV 를 한국어 Windows 의 엑셀은 시스템 기본 인코딩인 CP949 로 읽기 때문입니다.

오른쪽 첫 줄. 엑셀로 열 사람에게는 write_excel_csv 로 저장합니다. 맨 앞에 BOM 이라는 세 바이트, ef bb bf 를 붙여서 이 CSV 는 UTF-8 이라고 알려 줍니다. 왼쪽 코드에서 두 파일의 첫 세 바이트를 비교했습니다. write_excel_csv 는 ef bb bf, write_csv 는 바로 글자로 시작합니다.

CP949 파일만 받는 옛 프로그램에 줘야 하면 fileEncoding 으로 변환해서 씁니다. R 이나 Python 으로 읽을 사람에게는 write_csv 그대로 주면 됩니다.

어느 쪽이든 받은 사람이 열어 본 결과를 한 번은 확인하세요. 이것도 대조입니다.

na 인수에 9 를 넣는 방법을 떠올릴 수 있지만, na 는 모든 열에 적용됩니다. 9번 응답자의 응답번호까지 NA 가 되었습니다. 결측 코드가 한 열에만 해당하면 그 열에서만 바꿉니다. 그러면 3.9, SPSS 와 같아집니다.

SAS 파일은 read_sas, Stata 파일은 read_dta 로 읽습니다. 셋 다 haven 패키지의 함수이고, 파일 경로를 주어 읽는 사용법은 read_sav 와 같습니다.

6.2 Parquet

학생 명부를 보관하는 두 방법

  • 행 단위: 한 사람당 카드 한 장 (이름, 학번, 키)
  • 열 단위: 이름 목록, 학번 목록, 키 목록을 따로
  • “모든 학생의 키 평균” → 키 목록 한 장만 보면 됨
  • 같은 종류의 값이 이어져 행 단위보다 압축하면 더 작아짐
library(arrow)
pq_file <- file.path(tempdir(), "before.parquet")
write_parquet(before, pq_file)
identical(before,
          as.data.frame(read_parquet(pq_file)))
[1] TRUE
  • Parquet: 열 단위로 저장하는 형식의 하나
  • 요인, 날짜, 앞자리 0 보존
  • R, Python, DuckDB 등 여러 도구가 읽고 씀
  • 읽고 쓰기만 필요하면 설치 크기가 작은 nanoparquet 패키지도 가능

큰 데이터를 다른 도구, 다른 사람과 주고받을 때: Parquet

학생 명부를 보관하는 방법을 두 가지 생각해 봅시다. 한 사람당 카드 한 장에 이름, 학번, 키를 적는 방법. 이게 행 단위입니다. 그리고 이름 목록, 학번 목록, 키 목록을 따로 적는 방법. 이게 열 단위입니다.

모든 학생의 키 평균을 구하려면 열 단위가 빠르지요. 키 목록 한 장만 보면 되니까요. 게다가 같은 종류의 값이 이어져 있으니, 행 단위로 섞어 적을 때보다 압축했을 때 크기가 더 줄어듭니다.

이렇게 열 단위로 저장하는 형식 가운데 하나가 Parquet 입니다. 오른쪽 코드를 보세요. arrow 패키지로 쓰고 읽었더니 identical 이 TRUE 입니다. 요인, 날짜, 앞자리 0 이 모두 보존됩니다.

RDS 와 다른 점은, R 뿐 아니라 Python, DuckDB 같은 여러 도구가 읽고 쓴다는 겁니다. 그래서 큰 데이터를 다른 도구나 다른 사람과 주고받을 때 씁니다. arrow 패키지는 Apache Arrow 의 C++ 라이브러리를 함께 설치하므로 nanoparquet 패키지보다 설치 파일이 큽니다. 이 슬라이드를 만든 리눅스 컴퓨터에서는 126MB 대 23MB 였습니다. 읽고 쓰기만 필요하면 nanoparquet 으로도 됩니다.

7.4 파일 읽기 코드에서 자주 나타나는 오류

사람이 짠 코드와 AI 가 짠 코드 모두

  • 앞부분만 보고 전체를 가정: 합계 행, 주석 행, 뒤쪽에만 있는 결측 표기
  • 경로를 내 컴퓨터에 묶음: setwd(), 절대 경로
  • 인코딩을 기본값에 맡김: encoding 과 fileEncoding 혼동
  • 확인을 사람에게 미룸: tail() 로 보라고만 하고 코드로 남기지 않음
  • 가공한 뒤에 problems(): 파이프 뒤에는 기록이 없음

이번 응답의 코드: 첫째 유형, 파이프 때문에 다섯째 확인도 불가

첫째, 넷째, 다섯째: 오류 메시지 없이 틀린 표, 둘째와 셋째: 다른 컴퓨터에서 실행하거나 출력할 때 오류

AI 에게 물을 때 끝부분 몇 줄도 함께 붙이기

받은 코드를 확인하는 순서: ① 원문의 처음과 끝 보기 ② 실행 직후 problems() ③ 다섯 가지 대조 ④ 검증 함수로 남기기

파일 읽기 코드에서 자주 나타나는 오류를 정리하겠습니다. 사람이 짠 코드든 AI 가 짠 코드든 똑같이 나타납니다.

첫째, 앞부분만 보고 전체를 가정하는 것. 합계 행, 주석 행, 뒤쪽에만 있는 결측 표기를 놓칩니다. 둘째, 경로를 내 컴퓨터에 묶는 것. 셋째, 인코딩을 기본값에 맡기는 것. 넷째, 확인을 사람에게 미루고 코드로 남기지 않는 것. 다섯째, 가공한 뒤에 problems 를 보는 것.

이번 응답의 코드는 첫째 유형이었고, 파이프 때문에 다섯째 확인도 할 수 없게 되어 있었습니다.

첫째, 넷째, 다섯째 유형은 오류 메시지 없이 틀린 표를 남깁니다. 둘째와 셋째 유형도 코드를 쓴 사람의 컴퓨터에서는 오류 없이 돌아가다가, 다른 컴퓨터에서 실행하거나 표를 출력할 때에야 오류가 나기도 합니다.

그래서 오른쪽 아래. AI 에게 물을 때는 파일의 끝부분 몇 줄도 같이 붙이세요. 그리고 받은 코드는 아래 띠의 순서대로 확인합니다. 원문의 처음과 끝 보기, 실행 직후 problems, 다섯 가지 대조, 검증 함수로 남기기.
