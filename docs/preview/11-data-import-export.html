분석은 파일을 읽는 한 줄에서 시작한다. 그 한 줄이 조용히 틀리면 뒤따르는 모든 계산이 틀린다. 평균은 계산되고 그래프도 그려지지만 숫자가 틀려 있다. 파일을 읽는 코드는 AI 가 순식간에 써 주지만, AI 는 여러분의 파일을 보지 못한다. 붙여 넣은 몇 줄만 보고 나머지를 짐작할 뿐이다. 그 코드가 파일을 제대로 읽었는지는 코드를 들여다봐서는 알 수 없고, 파일의 원문과 대조해야 알 수 있다.

이 장은 파일을 읽고 쓰는 방법을 다루되, 중심은 함수 이름이 아니라 읽기 함수가 파일에 대해 세우는 가정에 있다. 어디서 열이 나뉘는지, 어떤 바이트가 어떤 글자인지, 무엇이 결측인지, 각 열이 무슨 유형인지를 함수는 추측한다. 추측이 틀린 곳을 찾아내는 일이 이 장에서 익힐 기술이다. 6장의 대조 습관과 9장의 ’참값을 아는 세계’가 여기서 다시 쓰인다.

이 장의 연습 파일은 강의 저장소의 dataset/ch11/ 폴더에 있다 (GitHub 에서 보기). 모두 교육용 가상 자료이며, 파일마다 일부러 넣어 둔 함정이 있다.

1 파일과 경로

파일을 읽으려면 먼저 파일이 어디에 있는지 R 에게 알려야 한다. 이 절은 경로를 적는 두 가지 방법과, 내 컴퓨터에서만 돌아가는 코드를 피하는 방법을 다룬다.

1.1 주소와 길 안내: 절대 경로와 상대 경로

처음 온 사람에게 학과 사무실의 위치를 알려 주는 방법은 두 가지다.

  • “○○시 ○○구 대학로 99, 자연과학대학 3층 301호” 처럼 주소 전체를 알려 준다. 듣는 사람이 어디에 있든 같은 곳을 가리킨다.
  • “여기서 계단으로 한 층 올라가서 오른쪽 첫 번째 방” 처럼 지금 있는 곳을 기준으로 알려 준다. 짧고 편하지만, 듣는 사람이 다른 건물에 있으면 엉뚱한 방으로 간다.

컴퓨터의 파일 위치도 똑같이 두 가지로 적는다. 주소 전체에 해당하는 것이 절대 경로(absolute path), 지금 있는 곳을 기준으로 적는 것이 상대 경로(relative path) 다.

방식 예 기준
절대 경로 C:/Users/홍길동/Documents/r-lecture/dataset/ch11/library-loans.csv 컴퓨터의 맨 위 폴더
상대 경로 dataset/ch11/library-loans.csv 지금 R 이 서 있는 폴더

상대 경로의 기준, 곧 R 이 지금 서 있는 폴더를 작업 디렉터리(working directory) 라 한다. 이 강의노트는 저장소 폴더를 작업 디렉터리로 두고 렌더한다.

basename(getwd())                                  # 지금 서 있는 폴더의 이름
[1] "cnu-r-programming-lecture-note"
file.exists("dataset/ch11/library-loans.csv")      # 상대 경로로 파일이 보이는가
[1] TRUE
list.files("dataset/ch11")                         # 폴더 안의 파일 목록
[1] "library-loans.csv" "make-ch11-data.R" 
[3] "README.md"         "survey.csv"       
[5] "survey.sav"        "survey.xlsx"      
file.path("dataset", "ch11", "library-loans.csv")  # 폴더 이름을 이어 경로를 만든다
[1] "dataset/ch11/library-loans.csv"

getwd() 는 작업 디렉터리의 절대 경로를 돌려준다. 여기서는 컴퓨터마다 다른 앞부분을 감추려고 마지막 폴더 이름만 보였다.

주의

Windows 에서 복사한 경로를 그대로 붙이면 오류가 난다. 탐색기의 주소는 역슬래시(\)로 폴더를 구분하는데, R 의 문자열에서 역슬래시는 특수 문자를 시작하는 기호다.

x <- "C:\Users\hong\data.csv"
#> Error: '\U' used without hex digits in character string

R 에서는 Windows 에서도 슬래시(/)로 적는다. "C:/Users/hong/data.csv".

1.2 작업 디렉터리와 프로젝트

인터넷 예제나 AI 가 준 코드는 흔히 이런 줄로 시작한다.

setwd("C:/Users/홍길동/Desktop/과제")
data <- read.csv("data.csv")

setwd() 는 작업 디렉터리를 바꾸는 함수다. 이 코드는 홍길동의 컴퓨터에서만 돌아간다. 같은 조의 친구, 채점하는 조교, 한 달 뒤 새 노트북을 산 홍길동 자신의 컴퓨터에는 그 폴더가 없다. 주소 대신 “제 책상 오른쪽 서랍”이라고 적은 길 안내와 같다.

해결책은 프로젝트 폴더다. 분석에 쓰는 코드, 데이터, 결과를 한 폴더에 모으고, 편집기에서 그 폴더를 연다. RStudio 에서는 프로젝트 파일(.Rproj)을 열고, Positron 에서는 폴더 열기(File > Open Folder)로 연다. 어느 쪽이든 R 의 작업 디렉터리가 그 폴더로 정해진다. 그다음부터 모든 경로를 프로젝트 폴더 기준 상대 경로로 적으면, 폴더째 누구에게 건네도 코드가 그대로 돌아간다.

힌트

예측해 보자: 아래 코드는 작업 디렉터리가 어디일 때 성공하겠는가? (가) 저장소 폴더, (나) 저장소 안의 dataset 폴더, (다) 바탕 화면.

read_csv("dataset/ch11/survey.csv")

답은 (가)뿐이다. (나)에서는 dataset 폴더 안에서 다시 dataset/ch11/... 를 찾게 되어 파일이 없다는 오류가 난다. 거꾸로, 저장소 폴더에 서 있으면서 dataset 폴더 안에 있다고 착각하고 경로를 적어도 마찬가지다.

file.exists("ch11/survey.csv")          # dataset 폴더 안에 서 있다고 착각한 경로
[1] FALSE
file.exists("dataset/ch11/survey.csv")  # 저장소 폴더 기준 경로
[1] TRUE

없는 파일을 read_csv() 로 읽으면 'ch11/survey.csv' does not exist in current working directory 라는 오류가 나며, 메시지 끝에 어느 폴더에서 찾았는지가 함께 적힌다. 경로 오류를 만나면 이 부분부터 확인한다.

노트

문서가 하위 폴더에 있을 때: Quarto 문서를 렌더하면 작업 디렉터리가 그 문서가 있는 폴더가 된다. reports/week3.qmd 에서 dataset/ch11/survey.csv 를 읽으면 reports/dataset/... 를 찾게 된다. 이럴 때는 here 패키지의 here() 가 프로젝트 폴더를 찾아 경로를 만들어 준다.

file.exists(here::here("dataset", "ch11", "survey.csv"))
[1] TRUE

1.3 파일은 바이트다

모든 파일은 결국 바이트(byte)의 나열이다. 바이트 하나는 0 부터 255 사이의 수이며, 흔히 두 자리 16진수(00 ~ ff)로 적는다. 읽기 함수는 이 바이트들을 약속에 따라 해석해 글자와 표로 바꾼다.

f_csv <- "dataset/ch11/survey.csv"
file.size(f_csv)                        # 파일의 바이트 수
[1] 308
readLines(f_csv, n = 3)                 # 텍스트 파일은 줄 단위의 글자로 읽힌다
[1] "\"응답번호\",\"성별\",\"학년\",\"참가일\",\"만족도\""
[2] "1,1,2,\"2026-09-01\",4"                              
[3] "2,2,3,\"2026-09-01\",5"                              
readBin(f_csv, what = "raw", n = 8)     # 같은 파일의 앞 8바이트
[1] 22 ec 9d 91 eb 8b b5 eb

survey.csv 의 첫 바이트 22 는 큰따옴표("), 그다음 ec 9d 91 세 바이트가 한글 응 한 글자다. 이처럼 바이트를 글자로 바꾸는 약속만 알면 사람도 읽을 수 있는 파일을 텍스트 파일이라 한다. CSV 가 여기에 속한다.

Excel 파일은 사정이 다르다.

f_xlsx <- "dataset/ch11/survey.xlsx"
readBin(f_xlsx, what = "raw", n = 4)
[1] 50 4b 03 04
rawToChar(readBin(f_xlsx, what = "raw", n = 2))
[1] "PK"
head(unzip(f_xlsx, list = TRUE)$Name, 4)     # 압축 파일로 열어 안의 파일 목록을 본다
[1] "_rels/.rels"         "[Content_Types].xml"
[3] "docProps/app.xml"    "docProps/core.xml"

첫 두 바이트가 PK 다. ZIP 압축 형식을 만든 필 카츠(Phil Katz)의 머리글자로, .xlsx 파일은 여러 XML 파일을 묶은 압축 파일이다. 메모장으로 열면 알아볼 수 없는 기호만 보이는 이유이고, 전용 함수가 필요한 이유다. 이런 파일을 이진 파일(binary file) 이라 한다.

이 장의 나머지는 모두 한 가지 사실에서 나온다. 읽기 함수는 바이트를 약속에 따라 해석하고, 약속이 어긋나면 해석이 틀린다. 틀린 해석은 오류로 멈추기도 하지만, 그럴듯한 표를 내놓고 조용히 끝나기도 한다.

2 텍스트 파일 읽기

데이터 파일 가운데 가장 흔한 것이 CSV(comma-separated values) 파일이다. 한 줄이 한 행이고, 쉼표가 값을 나눈다. 값을 나누는 기호를 구분자(delimiter) 라 하며, 탭을 쓰면 TSV 파일이 된다. 이 절은 base R 의 read.csv() 와 readr 패키지의 read_csv() 로 텍스트 파일을 읽을 때 함수가 세우는 가정을 하나씩 살펴본다.

2.1 구분자, 따옴표, 머리말

동아리 총무가 장 본 내역을 메신저로 보냈다.

품목,가격,수량
사과,3,000원,2

받는 사람은 쉼표에서 끊어 읽는다. 둘째 줄은 사과, 3, 000원, 2 네 조각이 되어 첫 줄의 세 항목과 맞지 않는다. 사람은 문맥으로 바로잡지만 함수는 그러지 못한다. 그래서 CSV 에는 약속이 하나 더 있다. 값 안에 쉼표가 있으면 그 값을 큰따옴표로 감싼다. 배,"4,500원",1 처럼 적으면 따옴표 안의 쉼표는 구분자가 아니다.

힌트

예측해 보자: 아래 파일의 각 줄은 쉼표로 몇 칸으로 나뉘겠는가? read_csv() 는 둘째 줄을 어떻게 읽겠는가?

품목,가격,수량
사과,3,000원,2
배,"4,500원",1

연습용 파일은 프로젝트 폴더에 쌓이지 않도록 임시 폴더(tempdir())에 쓴다. 실제 분석에서는 프로젝트 안에 output 같은 폴더를 두고 거기에 쓴다.

memo_file <- file.path(tempdir(), "memo.csv")
writeLines(c("품목,가격,수량",
             "사과,3,000원,2",
             "배,\"4,500원\",1"), memo_file)

count.fields(memo_file, sep = ",")     # 줄마다 몇 칸으로 나뉘는가
[1] 3 4 3
memo <- read_csv(memo_file)
memo
problems(memo)[, 1:4]                  # readr 가 기록한 문제

count.fields() 는 줄마다 칸 수를 세어 준다. 둘째 줄만 4칸이다. read_csv() 는 첫 줄을 기준으로 3개 열을 만들고, 넘치는 조각을 마지막 열에 붙인 뒤 문제(problem) 로 기록했다. problems() 가 그 목록을 보여 준다. 셋째 줄은 따옴표 덕분에 4,500원 이 한 값으로 들어갔다. base R 의 read.csv() 는 어떨까?

read.csv(memo_file)

오류도 경고도 없다. 그런데 사과 와 배 가 행 이름으로 빠지고, 값이 한 칸씩 밀렸다. 데이터 줄이 머리글보다 한 칸 많으면 첫 칸을 행 이름으로 쓰는 규칙 때문이다. 같은 파일을 두 함수가 다르게 틀린다. 한쪽은 문제를 기록하고, 다른 쪽은 조용히 밀어 넣는다.

파일 맨 위에 제목이나 설명이 붙어 있는 경우도 흔하다. 공공기관이 내려 주는 파일이 특히 그렇다.

titled <- "도서관 대출 현황 (가상 자료)
※ 단위: 권
도서관,대출권수
누리도서관,48215
한빛도서관,61530"

read_csv(I(titled))              # 첫 줄을 열 이름으로 쓴다

I() 로 감싼 문자열은 파일 경로가 아니라 파일의 내용으로 읽힌다. 짧은 예를 파일 없이 시험할 때 쓴다. 첫 줄에 쉼표가 없으니 열이 하나뿐인 표가 되었다. 앞의 두 줄을 건너뛰라고 알려 준다.

read_csv(I(titled), skip = 2)

read.csv() 의 행에서는 시도가 "경기 " 로 남아 "경기" 와 다르다고 판정되었다. 나중에 시도별로 합계를 내면 경기 와 경기 가 서로 다른 지역으로 집계된다. 표의 차이 가운데 어느 것도 오류를 내지 않는다는 점에 주의하자.

이 강의에서는 read_csv() 를 기본으로 쓴다. 결과를 예측하기 쉽고, 문제가 생긴 줄을 기록해 주기 때문이다. 그러나 인터넷 예제와 AI 가 준 코드에는 read.csv() 가 자주 나온다. 그 코드를 받으면 이 표의 차이를 떠올린다.

2.3 열 유형은 추측이다

우편번호 04157 은 사람에게 번호표이지 수가 아니다. 우편번호끼리 더하거나 평균을 내는 일은 없다. 그러나 읽기 함수는 글자만 보고 숫자처럼 생겼으면 숫자로 추측한다. read.csv() 가 04157 을 4157 로 바꾼 것이 그 결과다. read_csv() 는 어떤 기준으로 추측했는지 spec() 으로 확인할 수 있다.

spec(readr_df)
cols(
  도서관 = col_character(),
  시도 = col_character(),
  우편번호 = col_character(),
  개관일 = col_date(format = ""),
  `대출(권)` = col_double(),
  `3월` = col_double()
)

read_csv() 는 앞자리가 0 인 값이 섞인 열을 문자로 추측해 0 을 지켰다. 그렇다면 늘 안전할까?

힌트

예측해 보자: 서울 도서관이 섞인 파일과 대전 도서관만 있는 파일을 각각 read_csv() 로 읽으면 두 파일의 우편번호 열은 같은 유형이 되겠는가?

[1] "character"

[1] "numeric"

같은 형식의 파일인데 우편번호 열이 한쪽은 문자, 한쪽은 숫자가 되었다. 추측은 그 파일에 들어 있는 값을 보고 내리기 때문이다. 대전 파일만 받아 분석 코드를 짜 두었다가 다음 달 서울이 포함된 파일을 받으면 유형이 바뀌어 코드가 멈추거나, 반대의 경우 0 이 사라진다. 계산하지 않을 번호는 문자로 명시한다.

read_csv(I("도서관,우편번호
다온도서관,34126
마루도서관,35233"),
         col_types = cols(우편번호 = col_character()))

cols() 안에 열 이름과 유형을 짝지어 적는다. 적지 않은 열은 계속 추측한다. 자주 쓰는 유형은 col_character()(문자), col_double()(실수), col_integer()(정수), col_number()(쉼표가 섞인 숫자), col_date(format = )(날짜), col_logical()(논리값), col_factor()(요인)이다.

중요

우편번호, 학번, 전화번호, 행정구역 코드처럼 계산하지 않는 번호는 문자로 읽는다. 추측에 맡기지 않고 col_types 로 적어 두면, 파일이 바뀌어도 결과의 유형이 바뀌지 않는다.

2.4 결측값과 숫자 표기

설문지를 걷어 보면 빈칸, “모름”, “해당 없음”, “-” 가 섞여 있다. 사람은 모두 ’값이 없다’로 읽지만 읽기 함수는 빈칸과 NA 만 결측으로 안다. 나머지는 글자다.

가람도서관,\"35,108\",9870"

cols(
  도서관 = col_character(),
  대출권수 = col_character(),
  이용자수 = col_character()

두 열 모두 문자가 되었다. - 가 숫자가 아니기 때문이다. 이 파일에서 - 가 결측을 뜻한다는 사실은 원문과 설명을 읽은 사람만 안다. 그 사실을 na 인수로 알려 준다.

usage_df <- read_csv(I(usage), na = c("", "NA", "-"))
usage_df
spec(usage_df)
cols(
  도서관 = col_character(),
  대출권수 = col_number(),
  이용자수 = col_double()
)

- 를 결측으로 알려 주자 대출권수는 col_number() 로 추측되어 천 단위 쉼표가 빠진 숫자가 되었다. 따옴표 안의 48,215 는 사람에게는 숫자지만 글자로는 쉼표가 섞인 문자열이다. col_number() 와 parse_number() 는 숫자 사이의 쉼표를 지우고 수로 바꾼다.

parse_number(c("48,215", "1,023,456", "12.5%"))
[1]   48215.0 1023456.0      12.5

결측 표기를 알려 주지 않고 유형부터 정하면 어떻게 될까?

[1] 48215    NA 35108

- 는 수로 바꿀 수 없으니 NA 가 되고, 그 사실이 문제로 기록되었다. 결과는 앞과 같아 보이지만 왜 NA 가 되었는지를 아는 사람과 모르는 사람의 차이는 크다. 원래 빈칸이었는지, 휴관을 뜻하는 - 였는지, 오타였는지는 problems() 와 원문으로만 구별된다.

노트

설문 조사 원자료는 무응답을 9, 99, 999 같은 숫자로 적는 경우가 많다. 이런 값은 숫자 열에 그대로 섞여 들어와 평균을 끌어올린다. 무엇이 결측 코드인지는 자료와 함께 배포되는 코드북(codebook) 에 적혀 있다. 섹션 5.3 에서 실제 예를 본다.

2.5 한글과 인코딩

OMR 답안지를 떠올려 보자. 답안지에 칠한 칸은 그대로인데, A형 시험의 답안을 B형 정답표로 채점하면 점수가 엉터리가 된다. 파일도 마찬가지다. 파일의 바이트는 칠한 칸이고, 바이트를 글자로 바꾸는 정답표가 인코딩(encoding) 이다. 같은 바이트도 어떤 정답표로 읽느냐에 따라 전혀 다른 글자가 된다.

한글 파일에서 흔히 만나는 인코딩은 두 가지다.

  • UTF-8: 전 세계 문자를 담는 표준. 한글 한 글자를 3바이트로 적는다. macOS, Linux, 웹, 그리고 최근의 Windows 용 R 이 기본으로 쓴다.
  • CP949: 한국어 Windows 가 오래 써 온 방식. 한글 한 글자를 2바이트로 적는다. 한국어 Windows 의 Excel 에서 CSV 로 저장하거나, 공공기관에서 내려받은 CSV 파일에서 자주 만난다.
charToRaw("한글")                                    # UTF-8
[1] ed 95 9c ea b8 80
charToRaw(iconv("한글", from = "UTF-8", to = "CP949"))  # CP949
[1] c7 d1 b1 db

같은 두 글자가 UTF-8 로는 6바이트, CP949 로는 4바이트다. 이 장의 연습 파일 library-loans.csv 는 CP949 로 저장되어 있다.

힌트

노트

“Windows 에서는 그냥 읽힌다”는 옛이야기다. R 4.1 까지 한국어 Windows 의 R 은 CP949 를 기본으로 써서 CP949 파일이 인코딩 지정 없이 읽혔다. R 4.2.0 부터는 최근 Windows(10 버전 1903 이상)에서도 UTF-8 이 기본이 되었다(R NEWS). 그래서 인코딩을 적지 않은 옛 예제가 이제는 Windows 에서도 깨진다. 운영체제와 관계없이 인코딩을 명시하는 습관이 필요하다.

힌트

새로 만드는 파일은 UTF-8 로 저장한다. 다른 사람이 CP949 파일을 요구할 때만 변환해서 건넨다 (섹션 4.3).

  • 열 이름과 유형: 일곱 열이 모두 있고, 우편번호는 문자, 개관일은 날짜, 수를 담은 열은 숫자다.
  • 결측 수: 원문의 - 는 휴관 중인 여울도서관의 두 칸뿐인데, 여러 열에 NA 가 흩어져 있다.
  • 끝 행: 끝의 두 행이 합계 와 주석이다. 주석 행은 쉼표에서 두 칸으로 나뉘어 도서관 이름과 시도 열에 들어갔고, 나머지 칸은 NA 로 채워졌다. problems() 가 이 줄의 칸 수 문제를 기록해 두었다.

행 수와 끝 행만 확인했어도 문제를 찾았을 것이다. 반대로 head() 로 앞부분만 보았다면 아무 문제도 보이지 않는다.

대조는 여러 가지를 함께 한다. 합계 대조는 행이 빠지거나 겹친 문제를 잡지만, 결측이 0 으로 바뀐 문제는 놓친다. 결측 수 대조는 그 반대다. 하나의 검증으로 모든 결함을 잡을 수 없다는 점은 8장의 전수 검사와 경계 사례를 함께 쓴 이유와 같다.

3.4 검증을 코드로 남기기

대조를 눈으로만 하면 다음 달 파일을 받았을 때 다시 해야 한다. 대조를 코드로 적어 두면 파일을 바꿔 넣고 다시 실행하기만 하면 된다. stopifnot() 은 조건이 하나라도 거짓이면 멈추고, 조건에 붙인 이름을 오류 메시지로 보여 준다.

check_loans <- function(d, raw_lines, total) {
  stopifnot(
    "도서관 행 수가 원문과 같다" = nrow(d) == length(raw_lines) - 5,
    "우편번호는 다섯 자리 문자다" = all(grepl("^[0-9]{5}$", d$우편번호)),
    "대출권수 합이 합계 행과 같다" = sum(d$대출권수, na.rm = TRUE) == total$대출권수,
    "이용자수 합이 합계 행과 같다" = sum(d$이용자수, na.rm = TRUE) == total$이용자수,
    "이용자수 결측 수가 원문의 '-' 줄 수와 같다" =
      sum(is.na(d$이용자수)) == sum(grepl(",-$", raw_lines))
  )
  invisible(TRUE)
}

length(raw_lines) - 5 에는 “제목 2줄, 머리글 1줄, 합계 1줄, 주석 1줄” 이라는 파일 형식에 대한 가정이 들어 있다. 다음 달 파일에 주석이 한 줄 늘면 첫 조건에서 멈춘다. 조용히 틀린 결과를 내는 것보다 멈추는 편이 낫다(6장). 함수로 만든 검증은 6장에서 맛본 testthat 의 expect_equal() 로 옮겨 적을 수도 있다.

4.3 엑셀에서 열 CSV

R 에서 UTF-8 로 저장한 CSV 를 한국어 Windows 의 Excel 에서 두 번 눌러 열면 한글이 깨지는 경우가 많다. 아무 표시가 없는 CSV 를 Excel 이 시스템의 기본 인코딩(CP949)으로 읽기 때문이다. readr 의 write_excel_csv() 는 파일 맨 앞에 BOM(byte order mark) 이라는 세 바이트를 붙인다. readr 도움말에 따르면 이 표시가 Excel 에 “이 CSV 는 UTF-8” 이라고 알려 준다.

[1] ef bb bf
readBin(out_readr, what = "raw", n = 3)     # write_csv() 는 BOM 없이 바로 글자

Excel 에서 열어 볼 사람에게 건넬 파일은 write_excel_csv() 로 쓴다. 옛 프로그램이 CP949 파일만 받는다면 write.csv(small, "파일.csv", row.names = FALSE, fileEncoding = "CP949") 로 변환해 쓴다. 어느 쪽이든 받은 사람이 열어 본 결과를 한 번은 확인한다.

6 저장 형식 고르기

보고서를 보낼 때 한글(hwp) 파일로 보낼지 PDF 로 보낼지 고민해 본 적이 있을 것이다. 받는 사람이 고쳐 써야 하면 원본 파일을, 모양 그대로 보여 주기만 하면 되면 PDF 를 보낸다. 데이터 저장 형식도 받는 사람과 목적에 따라 고른다. 이 절에서는 R 전용 형식과 Parquet 을 살펴보고, 네 가지 방식의 비용을 잰다.

6.1 R 전용 형식: RDS 와 RData

R 객체를 그대로 저장하는 형식이다. 요인의 수준, 날짜 유형, 모든 자릿수가 보존된다.

rds_file <- file.path(tempdir(), "before.rds")
saveRDS(before, rds_file)
identical(before, readRDS(rds_file))
[1] TRUE

identical() 은 한 비트라도 다르면 FALSE 를 돌려주는 가장 엄격한 비교다. 왕복 검사를 완전히 통과했다. saveRDS() 는 객체 하나를 저장하고, 읽을 때 이름을 새로 붙인다. 여러 객체를 한꺼번에 저장하는 save() 와 load() 도 있다.

힌트

예측해 보자: 아래 코드를 실행한 뒤 x 에는 무엇이 들어 있겠는가?

load() 는 저장할 때의 이름 그대로 객체를 되살리면서, 같은 이름의 객체를 아무 경고 없이 덮어쓴다. 오늘 계산한 결과가 지난주 결과로 바뀌었다. 무엇이 되살아나는지는 파일을 열어 보기 전에는 알 수 없다. 반면 readRDS() 는 result <- readRDS(파일) 처럼 이름을 내가 정한다. 이 강의에서는 RDS 를 쓴다.

6.2 Parquet

학생 명부를 보관하는 두 가지 방법을 생각해 보자. 한 사람당 카드 한 장에 이름, 학번, 키를 적는 방법(행 단위)과, 이름 목록, 학번 목록, 키 목록을 따로 적는 방법(열 단위)이다. “모든 학생의 키 평균”을 구할 때는 키 목록 한 장만 보면 되는 열 단위가 빠르다. 같은 종류의 값이 이어져 있어 압축도 잘 된다. 이렇게 열 단위로 저장하는 대표적인 형식이 Parquet 이다. R 뿐 아니라 Python, DuckDB, Spark 같은 여러 도구가 읽고 쓰므로, 다른 사람과 큰 데이터를 주고받을 때 쓴다.

library(arrow)
pq_file <- file.path(tempdir(), "before.parquet")
write_parquet(before, pq_file)
identical(before, as.data.frame(read_parquet(pq_file)))
[1] TRUE

Parquet 도 왕복 검사를 통과했다. 요인, 날짜, 앞자리 0 이 모두 보존된다. arrow 패키지는 기능이 많은 만큼 설치 파일이 크다. Parquet 파일을 읽고 쓰기만 하면 되는 경우에는 가벼운 nanoparquet 패키지로도 같은 일을 할 수 있다.

6.3 형식별 비용 비교

8장에서 비용을 수행 시간과 메모리로 정의했다. 저장 형식의 비용은 파일 크기와 읽고 쓰는 시간이다. 50만 행의 가상 기상 관측 자료로 네 가지 방식을 비교한다.

힌트

예측해 보자: 같은 자료를 네 방식으로 저장하면 어느 파일이 가장 작고, 어느 파일이 가장 크겠는가? (read.csv 용 CSV, read_csv 용 CSV, RDS, Parquet)

set.seed(2026)

  sec(write.csv(weather, path[1], row.names = FALSE)),
  sec(write_csv(weather, path[2])),
  sec(saveRDS(weather, path[3])),
  sec(write_parquet(weather, path[4]))
)
read_sec <- c(
  sec(w1 <- read.csv(path[1])),

)

초 단위 시간은 컴퓨터마다 다르지만 크기와 복원 여부는 어느 컴퓨터에서나 같다. 텍스트 파일인 CSV 는 수 하나하나를 글자로 적으므로 크고, 다시 읽을 때 유형을 추측해야 하므로 그대로 복원되지 않는다. RDS 와 Parquet 은 압축된 이진 파일이라 작고 빠르며 그대로 복원된다. 그러나 메모장으로 열어 볼 수는 없다. 네 방식의 성격을 정리한다.

형식 사람이 열어 보기 다른 프로그램 유형 보존 크기와 속도 알맞은 쓰임
CSV 쉬움 거의 모두 안 됨 크고 느림 사람과 다른 프로그램에 건네기
Excel 쉬움 스프레드시트 일부 보통 사람이 보고 고칠 표
RDS 안 됨 R 만 완전 작고 빠름 내 분석의 중간 결과 저장
Parquet 안 됨 R, Python 등 거의 완전 작고 매우 빠름 큰 데이터를 여러 도구와 공유

표의 ’작고 매우 빠름’은 위와 같이 행이 많은 긴 표에서의 이야기다. 형식의 비용은 자료의 모양에 따라 달라진다. 열이 2만 개인 넓은 표로 같은 비교를 해 보자. dataset/pulse.csv 는 69행, 20,000열이다.

주의

파일 읽기 코드에서 자주 나타나는 오류 유형 (사람이 짠 코드와 AI 가 짠 코드 모두)

  • 앞부분만 보고 전체를 가정한다: 합계 행, 주석 행, 뒤쪽에만 나오는 결측 표기를 놓친다.
  • 경로를 내 컴퓨터에 묶는다: setwd() 나 절대 경로를 쓰거나, 작업 디렉터리를 확인하지 않는다.
  • 인코딩을 기본값에 맡긴다: read.csv() 의 encoding 과 fileEncoding 을 혼동하기도 한다.
  • 확인을 사람에게 미룬다: tail() 로 보라고만 하고, 대조를 코드로 남기지 않는다.
  • 가공한 뒤에 problems() 를 본다: 파이프로 이어 가공하면 문제 기록이 사라진 뒤다.

이번 응답의 코드는 첫째 유형에 해당했고, 파이프 때문에 다섯째 확인도 할 수 없게 되어 있었다. 모든 유형의 공통점은 오류 메시지가 나오지 않는다는 것이다.

- 절대 경로와 상대 경로의 차이를 설명하고, 프로젝트 폴더를 기준으로 파일을 읽고 쓸 수 있다.
- 파일의 원문을 먼저 확인해 구분자, 따옴표, 머리말, 결측 표기, 인코딩을 읽기 함수의 인수로 **명시**할 수 있다.
- `read.csv()` 와 `read_csv()` 가 같은 파일을 다르게 읽는 지점(열 이름, 열 유형, 빈칸, 공백)을 실행하기 전에 예측할 수 있다.
- 읽은 결과를 행 수, 열 유형, 결측 수, 합계 대조로 **검증**하고, 그 검증을 코드로 남길 수 있다.
- 쓰고 다시 읽는 왕복 검사로 저장 형식이 잃는 정보를 찾아내고, 목적에 맞는 형식(CSV, Excel, RDS, Parquet)을 비용과 함께 고를 수 있다.
- AI 가 생성한 파일 읽기 코드를 원문과 대조해 검증하고, AI 가 보지 못한 부분을 찾아낼 수 있다.

:::


분석은 파일을 읽는 한 줄에서 시작한다. 그 한 줄이 조용히 틀리면 뒤따르는 모든 계산이 틀린다.
평균은 계산되고 그래프도 그려지지만 숫자가 틀려 있다. 파일을 읽는 코드는 AI 가 순식간에 써 주지만,
AI 는 **여러분의 파일을 보지 못한다.** 붙여 넣은 몇 줄만 보고 나머지를 짐작할 뿐이다. 그 코드가 파일을
제대로 읽었는지는 코드를 들여다봐서는 알 수 없고, **파일의 원문과 대조해야** 알 수 있다.

이 장은 파일을 읽고 쓰는 방법을 다루되, 중심은 함수 이름이 아니라 **읽기 함수가 파일에 대해 세우는
가정**에 있다. 어디서 열이 나뉘는지, 어떤 바이트가 어떤 글자인지, 무엇이 결측인지, 각 열이 무슨
유형인지를 함수는 추측한다. 추측이 틀린 곳을 찾아내는 일이 이 장에서 익힐 기술이다. 6장의 대조 습관과
9장의 '참값을 아는 세계'가 여기서 다시 쓰인다.

이 장의 연습 파일은 강의 저장소의 `dataset/ch11/` 폴더에 있다
([GitHub 에서 보기](https://github.com/zorba78/cnu-r-programming-lecture-note/tree/master/dataset/ch11)).
모두 교육용 가상 자료이며, 파일마다 일부러 넣어 둔 함정이 있다.


## 파일과 경로 {#sec-files-paths}

파일을 읽으려면 먼저 파일이 **어디에** 있는지 R 에게 알려야 한다. 이 절은 경로를 적는 두 가지 방법과,
내 컴퓨터에서만 돌아가는 코드를 피하는 방법을 다룬다.


### 주소와 길 안내: 절대 경로와 상대 경로 {#sec-paths}

처음 온 사람에게 학과 사무실의 위치를 알려 주는 방법은 두 가지다.

- "○○시 ○○구 대학로 99, 자연과학대학 3층 301호" 처럼 **주소 전체**를 알려 준다. 듣는 사람이 어디에
  있든 같은 곳을 가리킨다.
- "여기서 계단으로 한 층 올라가서 오른쪽 첫 번째 방" 처럼 **지금 있는 곳을 기준으로** 알려 준다. 짧고
  편하지만, 듣는 사람이 다른 건물에 있으면 엉뚱한 방으로 간다.

컴퓨터의 파일 위치도 똑같이 두 가지로 적는다. 주소 전체에 해당하는 것이 **절대 경로(absolute path)**,
지금 있는 곳을 기준으로 적는 것이 **상대 경로(relative path)** 다.

| 방식 | 예 | 기준 |
|:--|:--|:--|
| 절대 경로 | `C:/Users/홍길동/Documents/r-lecture/dataset/ch11/library-loans.csv` | 컴퓨터의 맨 위 폴더 |
| 상대 경로 | `dataset/ch11/library-loans.csv` | 지금 R 이 서 있는 폴더 |

: {tbl-colwidths="[16,60,24]"}

상대 경로의 기준, 곧 R 이 지금 서 있는 폴더를 **작업 디렉터리(working directory)** 라 한다.
이 강의노트는 저장소 폴더를 작업 디렉터리로 두고 렌더한다.


```{r wd-basics}
basename(getwd())                                  # 지금 서 있는 폴더의 이름
file.exists("dataset/ch11/library-loans.csv")      # 상대 경로로 파일이 보이는가
list.files("dataset/ch11")                         # 폴더 안의 파일 목록
file.path("dataset", "ch11", "library-loans.csv")  # 폴더 이름을 이어 경로를 만든다

```


`getwd()` 는 작업 디렉터리의 절대 경로를 돌려준다. 여기서는 컴퓨터마다 다른 앞부분을 감추려고 마지막
폴더 이름만 보였다.


::: {.callout-caution}
**Windows 에서 복사한 경로를 그대로 붙이면** 오류가 난다. 탐색기의 주소는 역슬래시(`\`)로 폴더를
구분하는데, R 의 문자열에서 역슬래시는 특수 문자를 시작하는 기호다.

```r
x <- "C:\Users\hong\data.csv"
#> Error: '\U' used without hex digits in character string
```

R 에서는 Windows 에서도 슬래시(`/`)로 적는다. `"C:/Users/hong/data.csv"`.

:::


### 작업 디렉터리와 프로젝트 {#sec-working-directory}

인터넷 예제나 AI 가 준 코드는 흔히 이런 줄로 시작한다.

```r
setwd("C:/Users/홍길동/Desktop/과제")
data <- read.csv("data.csv")
```

`setwd()` 는 작업 디렉터리를 바꾸는 함수다. 이 코드는 홍길동의 컴퓨터에서만 돌아간다. 같은 조의 친구,
채점하는 조교, 한 달 뒤 새 노트북을 산 홍길동 자신의 컴퓨터에는 그 폴더가 없다. 주소 대신 "제 책상
오른쪽 서랍"이라고 적은 길 안내와 같다.

해결책은 **프로젝트 폴더**다. 분석에 쓰는 코드, 데이터, 결과를 한 폴더에 모으고, 편집기에서 그 폴더를
연다. RStudio 에서는 프로젝트 파일(`.Rproj`)을 열고, Positron 에서는 폴더 열기(File > Open Folder)로 연다.
어느 쪽이든 R 의 작업 디렉터리가 그 폴더로 정해진다. 그다음부터 모든 경로를 **프로젝트 폴더 기준 상대
경로**로 적으면, 폴더째 누구에게 건네도 코드가 그대로 돌아간다.


::: {.callout-tip}
**예측해 보자**: 아래 코드는 작업 디렉터리가 어디일 때 성공하겠는가?
(가) 저장소 폴더, (나) 저장소 안의 `dataset` 폴더, (다) 바탕 화면.

```r
read_csv("dataset/ch11/survey.csv")
```

:::


답은 (가)뿐이다. (나)에서는 `dataset` 폴더 안에서 다시 `dataset/ch11/...` 를 찾게 되어 파일이 없다는 오류가
난다. 거꾸로, 저장소 폴더에 서 있으면서 `dataset` 폴더 안에 있다고 착각하고 경로를 적어도 마찬가지다.


```{r wd-missing}
file.exists("ch11/survey.csv")          # dataset 폴더 안에 서 있다고 착각한 경로
file.exists("dataset/ch11/survey.csv")  # 저장소 폴더 기준 경로

```


없는 파일을 `read_csv()` 로 읽으면 `'ch11/survey.csv' does not exist in current working directory` 라는 오류가
나며, 메시지 끝에 **어느 폴더에서 찾았는지**가 함께 적힌다. 경로 오류를 만나면 이 부분부터 확인한다.


::: {.callout-note}
**문서가 하위 폴더에 있을 때**: Quarto 문서를 렌더하면 작업 디렉터리가 그 문서가 있는 폴더가 된다.
`reports/week3.qmd` 에서 `dataset/ch11/survey.csv` 를 읽으면 `reports/dataset/...` 를 찾게 된다.
이럴 때는 here 패키지의 `here()` 가 프로젝트 폴더를 찾아 경로를 만들어 준다.

```{r here-demo}
file.exists(here::here("dataset", "ch11", "survey.csv"))

```

:::


### 파일은 바이트다 {#sec-bytes}

모든 파일은 결국 **바이트(byte)의 나열**이다. 바이트 하나는 0 부터 255 사이의 수이며, 흔히 두 자리
16진수(`00` ~ `ff`)로 적는다. 읽기 함수는 이 바이트들을 약속에 따라 해석해 글자와 표로 바꾼다.


```{r bytes-text}
f_csv <- "dataset/ch11/survey.csv"
file.size(f_csv)                        # 파일의 바이트 수
readLines(f_csv, n = 3)                 # 텍스트 파일은 줄 단위의 글자로 읽힌다
readBin(f_csv, what = "raw", n = 8)     # 같은 파일의 앞 8바이트

```


`survey.csv` 의 첫 바이트 `22` 는 큰따옴표(`"`), 그다음 `ec 9d 91` 세 바이트가 한글 `응` 한 글자다. 이처럼
바이트를 글자로 바꾸는 약속만 알면 사람도 읽을 수 있는 파일을 **텍스트 파일**이라 한다. CSV 가 여기에
속한다.

Excel 파일은 사정이 다르다.


```{r bytes-xlsx}
f_xlsx <- "dataset/ch11/survey.xlsx"
readBin(f_xlsx, what = "raw", n = 4)
rawToChar(readBin(f_xlsx, what = "raw", n = 2))
head(unzip(f_xlsx, list = TRUE)$Name, 4)     # 압축 파일로 열어 안의 파일 목록을 본다

```


첫 두 바이트가 `PK` 다. ZIP 압축 형식을 만든 필 카츠(Phil Katz)의 머리글자로, **`.xlsx` 파일은 여러 XML
파일을 묶은 압축 파일**이다. 메모장으로 열면 알아볼 수 없는 기호만 보이는 이유이고, 전용 함수가 필요한
이유다. 이런 파일을 **이진 파일(binary file)** 이라 한다.

이 장의 나머지는 모두 한 가지 사실에서 나온다. **읽기 함수는 바이트를 약속에 따라 해석하고, 약속이
어긋나면 해석이 틀린다.** 틀린 해석은 오류로 멈추기도 하지만, 그럴듯한 표를 내놓고 조용히 끝나기도 한다.


## 텍스트 파일 읽기 {#sec-read-text}

데이터 파일 가운데 가장 흔한 것이 CSV(comma-separated values) 파일이다. 한 줄이 한 행이고, 쉼표가 값을
나눈다. 값을 나누는 기호를 **구분자(delimiter)** 라 하며, 탭을 쓰면 TSV 파일이 된다. 이 절은 base R 의
`read.csv()` 와 readr 패키지의 `read_csv()` 로 텍스트 파일을 읽을 때 함수가 세우는 가정을 하나씩 살펴본다.


### 구분자, 따옴표, 머리말 {#sec-delimiter}

동아리 총무가 장 본 내역을 메신저로 보냈다.

```
품목,가격,수량
사과,3,000원,2
```

받는 사람은 쉼표에서 끊어 읽는다. 둘째 줄은 `사과`, `3`, `000원`, `2` 네 조각이 되어 첫 줄의 세 항목과
맞지 않는다. 사람은 문맥으로 바로잡지만 함수는 그러지 못한다. 그래서 CSV 에는 약속이 하나 더 있다.
**값 안에 쉼표가 있으면 그 값을 큰따옴표로 감싼다.** `배,"4,500원",1` 처럼 적으면 따옴표 안의 쉼표는 구분자가
아니다.


::: {.callout-tip}
**예측해 보자**: 아래 파일의 각 줄은 쉼표로 몇 칸으로 나뉘겠는가? `read_csv()` 는 둘째 줄을 어떻게
읽겠는가?

```
품목,가격,수량
사과,3,000원,2
배,"4,500원",1
```

:::


연습용 파일은 프로젝트 폴더에 쌓이지 않도록 **임시 폴더**(`tempdir()`)에 쓴다. 실제 분석에서는 프로젝트
안에 `output` 같은 폴더를 두고 거기에 쓴다.


```{r memo-fields}
memo_file <- file.path(tempdir(), "memo.csv")
writeLines(c("품목,가격,수량",
             "사과,3,000원,2",
             "배,\"4,500원\",1"), memo_file)

count.fields(memo_file, sep = ",")     # 줄마다 몇 칸으로 나뉘는가

```


```{r memo-readr}
memo <- read_csv(memo_file)
memo
problems(memo)[, 1:4]                  # readr 가 기록한 문제

```


`count.fields()` 는 줄마다 칸 수를 세어 준다. 둘째 줄만 4칸이다. `read_csv()` 는 첫 줄을 기준으로 3개 열을
만들고, 넘치는 조각을 마지막 열에 붙인 뒤 **문제(problem)** 로 기록했다. `problems()` 가 그 목록을 보여 준다.
셋째 줄은 따옴표 덕분에 `4,500원` 이 한 값으로 들어갔다. base R 의 `read.csv()` 는 어떨까?


```{r memo-base}
read.csv(memo_file)

```


오류도 경고도 없다. 그런데 `사과` 와 `배` 가 행 이름으로 빠지고, 값이 한 칸씩 밀렸다. 데이터 줄이 머리글보다
한 칸 많으면 첫 칸을 행 이름으로 쓰는 규칙 때문이다. **같은 파일을 두 함수가 다르게 틀린다.** 한쪽은 문제를
기록하고, 다른 쪽은 조용히 밀어 넣는다.

파일 맨 위에 제목이나 설명이 붙어 있는 경우도 흔하다. 공공기관이 내려 주는 파일이 특히 그렇다.


```{r titled}
titled <- "도서관 대출 현황 (가상 자료)
※ 단위: 권
도서관,대출권수
누리도서관,48215
한빛도서관,61530"

read_csv(I(titled))              # 첫 줄을 열 이름으로 쓴다

```


`I()` 로 감싼 문자열은 파일 경로가 아니라 **파일의 내용**으로 읽힌다. 짧은 예를 파일 없이 시험할 때 쓴다.
첫 줄에 쉼표가 없으니 열이 하나뿐인 표가 되었다. 앞의 두 줄을 건너뛰라고 알려 준다.


```{r titled-skip}
read_csv(I(titled), skip = 2)

```


### read.csv() 와 read_csv() {#sec-base-vs-readr}

두 함수는 같은 일을 하지만 기본 가정이 여러 곳에서 다르다. 차이를 한 파일에 모아 보자.


::: {.callout-tip}
**예측해 보자**: 아래 파일을 두 함수로 읽으면 열 이름 `대출(권)` 과 `3월` 은 어떻게 되겠는가? 둘째 행의
시도 `경기 ` (끝에 공백)는 `"경기"` 와 같다고 판정되겠는가?

:::


```{r mini-text}
mini <- "도서관,시도,우편번호,개관일,대출(권),3월
누리도서관,서울,04157,2004-03-15,48215,12
가람도서관,경기 ,16489,2011-06-20,,7
다온도서관,대전,34126,,31002,NA"

```


```{r mini-base}
base_df <- read.csv(text = mini)
str(base_df)

```


```{r mini-readr}
readr_df <- read_csv(I(mini))
readr_df

```


```{r mini-trim}
base_df$시도 == "경기"
readr_df$시도 == "경기"

```


| 항목 | `read.csv()` | `read_csv()` |
|:--|:--|:--|
| 결과의 종류 | 데이터 프레임 | 티블(tibble). 출력이 간결한 데이터 프레임 |
| 열 이름 `대출(권)`, `3월` | `대출.권.`, `X3월` 로 고친다 | 그대로 둔다 |
| 값 끝의 공백 `경기 ` | 그대로 둔다 | 지운다 |
| 문자 열의 빈칸 | 빈 문자열 `""` | 결측 `NA` |
| `2004-03-15` | 문자 | 날짜(`Date`) |
| `04157` | 정수 `4157` (앞자리 0 사라짐) | 문자 `"04157"` |
| 줄마다 칸 수가 다를 때 | 경고 없이 밀리거나 오류 | `problems()` 에 기록 |

: {tbl-colwidths="[26,36,38]"}

`read.csv()` 의 행에서는 시도가 `"경기 "` 로 남아 `"경기"` 와 다르다고 판정되었다. 나중에 시도별로 합계를 내면
`경기` 와 `경기 ` 가 서로 다른 지역으로 집계된다. 표의 차이 가운데 어느 것도 오류를 내지 않는다는 점에
주의하자.

이 강의에서는 `read_csv()` 를 기본으로 쓴다. 결과를 예측하기 쉽고, 문제가 생긴 줄을 기록해 주기 때문이다.
그러나 인터넷 예제와 AI 가 준 코드에는 `read.csv()` 가 자주 나온다. 그 코드를 받으면 이 표의 차이를 떠올린다.


### 열 유형은 추측이다 {#sec-col-types}

우편번호 `04157` 은 사람에게 번호표이지 수가 아니다. 우편번호끼리 더하거나 평균을 내는 일은 없다. 그러나
읽기 함수는 글자만 보고 **숫자처럼 생겼으면 숫자로** 추측한다. `read.csv()` 가 `04157` 을 `4157` 로 바꾼 것이 그
결과다. `read_csv()` 는 어떤 기준으로 추측했는지 `spec()` 으로 확인할 수 있다.


```{r spec-mini}
spec(readr_df)

```


`read_csv()` 는 앞자리가 0 인 값이 섞인 열을 문자로 추측해 0 을 지켰다. 그렇다면 늘 안전할까?


::: {.callout-tip}
**예측해 보자**: 서울 도서관이 섞인 파일과 대전 도서관만 있는 파일을 각각 `read_csv()` 로 읽으면 두
파일의 우편번호 열은 같은 유형이 되겠는가?

:::


```{r guess-two-files}
with_seoul <- read_csv(I("도서관,우편번호
누리도서관,04157
다온도서관,34126"))

daejeon_only <- read_csv(I("도서관,우편번호
다온도서관,34126
마루도서관,35233"))

class(with_seoul$우편번호)
class(daejeon_only$우편번호)

```


같은 형식의 파일인데 우편번호 열이 한쪽은 문자, 한쪽은 숫자가 되었다. 추측은 **그 파일에 들어 있는 값**을
보고 내리기 때문이다. 대전 파일만 받아 분석 코드를 짜 두었다가 다음 달 서울이 포함된 파일을 받으면
유형이 바뀌어 코드가 멈추거나, 반대의 경우 0 이 사라진다. 계산하지 않을 번호는 **문자로 명시**한다.


```{r col-types}
read_csv(I("도서관,우편번호
다온도서관,34126
마루도서관,35233"),
         col_types = cols(우편번호 = col_character()))

```


`cols()` 안에 열 이름과 유형을 짝지어 적는다. 적지 않은 열은 계속 추측한다. 자주 쓰는 유형은
`col_character()`(문자), `col_double()`(실수), `col_integer()`(정수), `col_number()`(쉼표가 섞인 숫자),
`col_date(format = )`(날짜), `col_logical()`(논리값), `col_factor()`(요인)이다.


::: {.callout-important}
우편번호, 학번, 전화번호, 행정구역 코드처럼 **계산하지 않는 번호는 문자로 읽는다.** 추측에 맡기지 않고
`col_types` 로 적어 두면, 파일이 바뀌어도 결과의 유형이 바뀌지 않는다.

:::


### 결측값과 숫자 표기 {#sec-na-numbers}

설문지를 걷어 보면 빈칸, "모름", "해당 없음", "-" 가 섞여 있다. 사람은 모두 '값이 없다'로 읽지만 읽기 함수는
**빈칸과 `NA` 만** 결측으로 안다. 나머지는 글자다.


```{r na-default}
usage <- "도서관,대출권수,이용자수
누리도서관,\"48,215\",12904
여울도서관,-,-
가람도서관,\"35,108\",9870"

read_csv(I(usage)) |> spec()

```


두 열 모두 문자가 되었다. `-` 가 숫자가 아니기 때문이다. 이 파일에서 `-` 가 결측을 뜻한다는 사실은 원문과
설명을 읽은 사람만 안다. 그 사실을 `na` 인수로 알려 준다.


```{r na-declared}
usage_df <- read_csv(I(usage), na = c("", "NA", "-"))
usage_df
spec(usage_df)

```


`-` 를 결측으로 알려 주자 대출권수는 `col_number()` 로 추측되어 천 단위 쉼표가 빠진 숫자가 되었다. 따옴표 안의
`48,215` 는 사람에게는 숫자지만 글자로는 쉼표가 섞인 문자열이다. `col_number()` 와 `parse_number()` 는 숫자
사이의 쉼표를 지우고 수로 바꾼다.


```{r parse-number}
parse_number(c("48,215", "1,023,456", "12.5%"))

```


결측 표기를 알려 주지 않고 유형부터 정하면 어떻게 될까?


```{r na-forced}
forced <- read_csv(I(usage), col_types = cols(대출권수 = col_number()))
forced$대출권수
problems(forced)[, 1:4]

```


`-` 는 수로 바꿀 수 없으니 `NA` 가 되고, 그 사실이 문제로 기록되었다. 결과는 앞과 같아 보이지만 **왜 `NA` 가
되었는지**를 아는 사람과 모르는 사람의 차이는 크다. 원래 빈칸이었는지, 휴관을 뜻하는 `-` 였는지, 오타였는지는
`problems()` 와 원문으로만 구별된다.


::: {.callout-note}
설문 조사 원자료는 무응답을 `9`, `99`, `999` 같은 **숫자**로 적는 경우가 많다. 이런 값은 숫자 열에 그대로
섞여 들어와 평균을 끌어올린다. 무엇이 결측 코드인지는 자료와 함께 배포되는 **코드북(codebook)** 에 적혀
있다. @sec-haven 에서 실제 예를 본다.

:::


### 한글과 인코딩 {#sec-encoding}

OMR 답안지를 떠올려 보자. 답안지에 칠한 칸은 그대로인데, A형 시험의 답안을 B형 정답표로 채점하면 점수가
엉터리가 된다. 파일도 마찬가지다. 파일의 바이트는 칠한 칸이고, 바이트를 글자로 바꾸는 정답표가
**인코딩(encoding)** 이다. 같은 바이트도 어떤 정답표로 읽느냐에 따라 전혀 다른 글자가 된다.

한글 파일에서 흔히 만나는 인코딩은 두 가지다.

- **UTF-8**: 전 세계 문자를 담는 표준. 한글 한 글자를 3바이트로 적는다. macOS, Linux, 웹, 그리고 최근의
  Windows 용 R 이 기본으로 쓴다.
- **CP949**: 한국어 Windows 가 오래 써 온 방식. 한글 한 글자를 2바이트로 적는다. 한국어 Windows 의 Excel 에서
  CSV 로 저장하거나, 공공기관에서 내려받은 CSV 파일에서 자주 만난다.


```{r encoding-bytes}
charToRaw("한글")                                    # UTF-8
charToRaw(iconv("한글", from = "UTF-8", to = "CP949"))  # CP949

```


같은 두 글자가 UTF-8 로는 6바이트, CP949 로는 4바이트다. 이 장의 연습 파일 `library-loans.csv` 는 CP949 로
저장되어 있다.


::: {.callout-tip}
**예측해 보자**: CP949 파일을 인코딩을 알려 주지 않고 `read_csv()` 로 읽으면 어떻게 되겠는가?
(가) 오류로 멈춘다, (나) 읽기는 끝나지만 글자가 깨진다, (다) 알아서 제대로 읽는다.

:::


```{r encoding-broken}
f <- "dataset/ch11/library-loans.csv"
broken <- read_csv(f, skip = 2)      # 앞의 제목 두 줄은 건너뛴다
nrow(broken)
names(broken)

```


답은 (나)다. 읽기는 오류 없이 끝나고 행 수도 그럴듯하다. 그러나 열 이름이 `\xb5\xb5` 같은 바이트 기호로
보인다. UTF-8 정답표로 CP949 바이트를 읽은 결과다. 이 표를 쓰려고 하면 그제야 문제가 드러난다.


```{r encoding-broken-use, warning=TRUE, error=TRUE}
broken$도서관            # 그런 이름의 열이 없다
print(broken)            # 표를 출력하려다 멈춘다

```


콘솔에서 이 파일을 읽으면 열 유형 요약을 출력하는 단계에서 같은 오류(`invalid multibyte string`)가 난다.
**멈춘 곳이 파일을 읽는 줄이 아닐 수 있다**는 점을 기억해 두자. `read.csv()` 는 읽는 줄에서 멈춘다.


```{r encoding-base, error=TRUE}
read.csv(f, skip = 2)
read.csv(f, skip = 2, encoding = "CP949")      # 이름이 비슷하지만 변환하지 않는다

```


둘째 줄에 주목하자. `read.csv()` 의 `encoding` 인수는 글자를 **변환하지 않고** 표시만 붙인다. 파일을 CP949 로
해석해 읽으라는 인수는 `fileEncoding` 이다. 이름이 비슷해 인터넷 예제에서도 자주 헷갈린다.

파일의 인코딩을 모를 때는 readr 의 `guess_encoding()` 으로 짐작한다.


```{r encoding-guess}
guess_encoding(f)

```


`EUC-KR` 로 짐작했다. CP949 는 EUC-KR 에 한글 글자를 더 넣어 넓힌 방식이므로 한국어 파일에는 `CP949` 를
지정하는 편이 안전하다. EUC-KR 에는 `똠`, `펲` 같은 글자가 없다. 인코딩을 알려 주면 제대로 읽힌다.


```{r encoding-fixed}
loans_try <- read_csv(f, skip = 2, locale = locale(encoding = "CP949"))
names(loans_try)

read.csv(f, skip = 2, fileEncoding = "CP949") |> names()

```


::: {.callout-note}
**"Windows 에서는 그냥 읽힌다"는 옛이야기다.** R 4.1 까지 한국어 Windows 의 R 은 CP949 를 기본으로 써서
CP949 파일이 인코딩 지정 없이 읽혔다. R 4.2.0 부터는 최근 Windows(10 버전 1903 이상)에서도 UTF-8 이 기본이
되었다(R NEWS). 그래서 인코딩을 적지 않은 옛 예제가 이제는 Windows 에서도 깨진다. **운영체제와 관계없이
인코딩을 명시**하는 습관이 필요하다.

:::


::: {.callout-tip}
새로 만드는 파일은 UTF-8 로 저장한다. 다른 사람이 CP949 파일을 요구할 때만 변환해서 건넨다
(@sec-excel-csv).

:::


## 읽은 결과 검증하기 {#sec-verify-import}

8장의 `rbinary_search()` 는 오류 없이 틀린 답을 냈고, 9장의 편향된 분산 함수도 그랬다. 파일 읽기도 같다.
**오류 없이 읽혔다는 사실은 제대로 읽혔다는 증거가 아니다.** 앞 절에서 본 가정들이 하나라도 어긋나면 그럴듯한
표가 조용히 만들어진다. 파일 읽기의 참값은 **원문**이다. 이 절에서는 연습 파일 `library-loans.csv` 를 읽고 원문과
대조하는 절차를 세운다.


### 원문 먼저 보기 {#sec-look-raw}

읽기 함수에 넘기기 전에 파일을 줄 단위 글자로 먼저 본다. 인코딩은 앞 절에서 CP949 로 확인했다.


```{r raw-lines}
f <- "dataset/ch11/library-loans.csv"
raw_lines <- read_lines(f, locale = locale(encoding = "CP949"))
length(raw_lines)
head(raw_lines, 4)
tail(raw_lines, 3)

```


파일 앞부분만 보면 평범한 표다. **끝부분을 보면** 두 가지가 더 있다. 모든 도서관을 더한 `합계` 행과, 쉼표가
들어간 주석 행이다. 사람 눈에는 표의 요약과 설명이지만 읽기 함수에는 데이터 행과 똑같은 한 줄이다. 줄마다 칸
수를 세어 보면 파일의 구조가 한눈에 보인다.


```{r raw-fields}
table(count.fields(f, sep = ","))

```


1칸짜리 2줄은 제목과 설명, 7칸짜리 22줄은 머리글 1줄과 도서관 20줄과 합계 1줄, 2칸짜리 1줄은 주석이다.
원문 25줄 가운데 **도서관 행은 20줄**이어야 한다. 이 숫자가 뒤의 대조에서 참값이 된다.


### 다섯 가지 대조 {#sec-five-checks}

지금까지 배운 것을 모두 반영해 파일을 읽어 보자. 제목 두 줄을 건너뛰고, 인코딩과 결측 표기를 알려 주고,
우편번호는 문자로, 점으로 적힌 개관일은 날짜로 읽는다.


```{r loans-raw}
loans_raw <- read_csv(
  f,
  skip = 2,
  na = c("", "NA", "-"),
  locale = locale(encoding = "CP949"),
  col_types = cols(
    우편번호 = col_character(),
    개관일 = col_date(format = "%Y.%m.%d")
  )
)

```


오류 없이 끝났다. 이제 원문과 대조한다.


::: {.callout-important}
**읽은 결과를 원문과 대조하는 다섯 가지**

1. **행 수**: 원문에서 센 데이터 줄 수와 같은가
2. **열 이름과 개수**: 기대한 이름이 기대한 개수만큼 있는가
3. **열 유형**: 숫자여야 할 열이 숫자이고, 번호여야 할 열이 문자인가
4. **결측 수**: 열마다 `NA` 개수가 원문의 빈칸과 결측 표기 개수와 같은가
5. **처음과 끝 행**: 머리말이나 꼬리말, 합계 행이 섞이지 않았는가

:::


```{r check-1-2}
c(읽은_행 = nrow(loans_raw), 원문의_도서관_행 = length(raw_lines) - 5)
names(loans_raw)

```


```{r check-3}
spec(loans_raw)

```


```{r check-4}
colSums(is.na(loans_raw))

```


```{r check-5}
tail(loans_raw, 3)
problems(loans_raw)[, 1:4]

```


대조 결과는 다음과 같다.

- **행 수**: 22행을 읽었다. 원문의 도서관 행은 20줄이다. 두 줄이 더 들어왔다.
- **열 이름과 유형**: 일곱 열이 모두 있고, 우편번호는 문자, 개관일은 날짜, 수를 담은 열은 숫자다.
- **결측 수**: 원문의 `-` 는 휴관 중인 여울도서관의 두 칸뿐인데, 여러 열에 `NA` 가 흩어져 있다.
- **끝 행**: 끝의 두 행이 `합계` 와 주석이다. 주석 행은 쉼표에서 두 칸으로 나뉘어 도서관 이름과 시도 열에 들어갔고,
  나머지 칸은 `NA` 로 채워졌다. `problems()` 가 이 줄의 칸 수 문제를 기록해 두었다.

행 수와 끝 행만 확인했어도 문제를 찾았을 것이다. 반대로 `head()` 로 앞부분만 보았다면 아무 문제도 보이지 않는다.


### 합계 행은 참값이다 {#sec-total-row}

가계부를 정리하면 영수증의 합계와 내가 더한 금액을 맞춰 본다. 표 아래의 합계 행도 같은 역할을 한다. 합계 행은
데이터에서 **빼야 할 행**이지만 버릴 행은 아니다. 우리가 계산한 값과 **대조할 참값**이다.


::: {.callout-tip}
**예측해 보자**: 합계 행을 지우지 않은 채 대출권수를 모두 더하면, 원래 합계의 몇 배가 나오겠는가?

:::


```{r total-doubled}
sum(loans_raw$대출권수, na.rm = TRUE)

```


정확히 두 배다. 합계 행 자체가 20개 도서관의 합이기 때문이다. 도서관 행과 합계 행을 나눈다. 도서관 행을
고르는 규칙은 **우편번호가 다섯 자리 숫자인 행**으로 정한다. 합계 행과 주석 행에는 우편번호가 없다. 10장에서
배운 정규표현식을 쓴다.


```{r split-total}
is_library <- grepl("^[0-9]{5}$", loans_raw$우편번호)
loans <- loans_raw[is_library, ]
total <- loans_raw[loans_raw$도서관 == "합계", ]

nrow(loans)
c(계산 = sum(loans$대출권수, na.rm = TRUE), 합계_행 = total$대출권수)
c(계산 = sum(loans$이용자수, na.rm = TRUE), 합계_행 = total$이용자수)
c(계산 = sum(loans$열람석), 합계_행 = total$열람석)

```


세 열의 합이 모두 합계 행과 일치한다. 9장에서 참값을 정해 두고 시뮬레이션 결과를 대조했듯, 여기서는 파일이
스스로 참값을 들고 있다. 이제 결측 수도 다시 보자.


```{r loans-na}
colSums(is.na(loans))

```


대출권수와 이용자수에 하나씩, 휴관 중인 여울도서관의 `-` 두 칸과 정확히 맞는다.

그렇다면 **유형을 직접 지정하면** 검증을 덜 해도 될까? 결측 표기 `-` 는 알려 주지 않은 채, 대출권수는 쉼표가 섞인
숫자(`col_number()`)로, 이용자수는 정수(`col_integer()`)로 지정해 읽어 보자. 두 열 모두 여울도서관의 칸에 `-` 가 있다.


::: {.callout-tip}
**예측해 보자**: 숫자로 지정한 두 열에 `-` 가 들어오면 어떻게 되겠는가? 두 열 모두 `NA` 가 되고 문제가 기록되겠는가?

:::


```{r dash-integer}
loans_int <- read_csv(
  f,
  skip = 2,
  locale = locale(encoding = "CP949"),
  col_types = cols(
    우편번호 = col_character(),
    대출권수 = col_number(),
    이용자수 = col_integer()
  )
)
lib_int <- loans_int[grepl("^[0-9]{5}$", loans_int$우편번호), ]

lib_int[lib_int$도서관 == "여울도서관", c("도서관", "대출권수", "이용자수")]
problems(loans_int)[, 1:4]

```


같은 `-` 가 두 열에서 다르게 처리되었다. 대출권수(6번째 열)의 `-` 는 `NA` 가 되고 `problems()` 에 기록되었다. 이 강의노트를
렌더한 readr `r packageVersion("readr")` 에서 이용자수(7번째 열)의 `-` 는 **`r lib_int$이용자수[lib_int$도서관 == "여울도서관"]`**
이 되었고, 아무 기록도 남지 않았다. 휴관 중이라 알 수 없는 값이 '이용자 0명'이라는 그럴듯한 값으로 바뀐 것이다.
정수 해석기에서만 나타나는 동작이다. 다섯 가지 대조가 이 차이를 잡아내는지 확인한다.


```{r dash-checks}
sum(lib_int$이용자수) == total$이용자수    # 합계 대조
sum(is.na(lib_int$이용자수))               # 결측 수
sum(grepl(",-$", raw_lines))               # 원문에서 '-' 로 끝나는 줄
min(lib_int$이용자수)                      # 최솟값

```


**합계 대조는 통과한다.** 0 을 더해도 합은 변하지 않기 때문이다. 결측 수 대조는 실패한다. 원문에는 `-` 가 한 줄
있는데 `NA` 는 하나도 없다. 최솟값이 0 이라는 것도 수상하다. 평균은 `r round(mean(lib_int$이용자수), 1)` 로, 제대로
읽었을 때의 `r round(mean(loans$이용자수, na.rm = TRUE), 1)` 보다 작아진다.


::: {.callout-caution}
**대조는 여러 가지를 함께 한다.** 합계 대조는 행이 빠지거나 겹친 문제를 잡지만, 결측이 0 으로 바뀐 문제는 놓친다.
결측 수 대조는 그 반대다. 하나의 검증으로 모든 결함을 잡을 수 없다는 점은 8장의 전수 검사와 경계 사례를 함께 쓴
이유와 같다.

그리고 **도구도 틀릴 수 있다.** 여기서 본 동작은 readr 의 정수 해석기에서 나타난 것이며, 이후 버전에서 고쳐질 수
있다. 버전이 바뀌어도 원문과 대조하는 절차는 그대로 쓸 수 있다.

:::


### 검증을 코드로 남기기 {#sec-import-assert}

대조를 눈으로만 하면 다음 달 파일을 받았을 때 다시 해야 한다. 대조를 **코드로 적어 두면** 파일을 바꿔 넣고
다시 실행하기만 하면 된다. `stopifnot()` 은 조건이 하나라도 거짓이면 멈추고, 조건에 붙인 이름을 오류 메시지로
보여 준다.


```{r check-function}
check_loans <- function(d, raw_lines, total) {
  stopifnot(
    "도서관 행 수가 원문과 같다" = nrow(d) == length(raw_lines) - 5,
    "우편번호는 다섯 자리 문자다" = all(grepl("^[0-9]{5}$", d$우편번호)),
    "대출권수 합이 합계 행과 같다" = sum(d$대출권수, na.rm = TRUE) == total$대출권수,
    "이용자수 합이 합계 행과 같다" = sum(d$이용자수, na.rm = TRUE) == total$이용자수,
    "이용자수 결측 수가 원문의 '-' 줄 수와 같다" =
      sum(is.na(d$이용자수)) == sum(grepl(",-$", raw_lines))
  )
  invisible(TRUE)
}

check_loans(loans, raw_lines, total)        # 통과하면 아무것도 출력하지 않는다

```


```{r check-function-fail, error=TRUE}
check_loans(lib_int, raw_lines, total)      # '-' 가 0 이 된 결과

```


`length(raw_lines) - 5` 에는 "제목 2줄, 머리글 1줄, 합계 1줄, 주석 1줄" 이라는 **파일 형식에 대한 가정**이 들어 있다.
다음 달 파일에 주석이 한 줄 늘면 첫 조건에서 멈춘다. 조용히 틀린 결과를 내는 것보다 멈추는 편이 낫다(6장).
함수로 만든 검증은 6장에서 맛본 testthat 의 `expect_equal()` 로 옮겨 적을 수도 있다.


## 파일 쓰기와 왕복 검사 {#sec-write}

분석 결과를 파일로 남기는 일은 읽기의 반대 방향이다. 쓰기 함수도 가정을 세우고, 그 가정 때문에 **정보를 잃는다.**
무엇을 잃는지는 **써 놓은 파일을 다시 읽어** 원래 객체와 비교하면 알 수 있다.


### write.csv() 와 write_csv() {#sec-write-csv}

::: {.callout-tip}
**예측해 보자**: 세 열짜리 표를 `write.csv()` 로 저장한 뒤 `read_csv()` 로 다시 읽으면 열은 몇 개가 되겠는가?

:::


```{r write-two}
small <- loans[1:3, c("도서관", "우편번호", "대출권수")]

out_base <- file.path(tempdir(), "small-base.csv")
out_readr <- file.path(tempdir(), "small-readr.csv")
write.csv(small, out_base)
write_csv(small, out_readr)

readLines(out_base)
readLines(out_readr)

```


```{r write-base-reread, message=TRUE}
names(read_csv(out_base))

```


`write.csv()` 는 기본값으로 **행 이름**(`"1"`, `"2"`, `"3"`)을 첫 열로 함께 쓴다. 이 파일을 다시 읽으면 이름 없는
열이 하나 생기고, readr 는 그 열에 `...1` 이라는 이름을 붙였다는 메시지를 낸다. 파일을 주고받을 때마다 이 열이
하나씩 늘어나기도 한다. `write.csv(small, out_base, row.names = FALSE)` 로 끄거나 `write_csv()` 를 쓴다.


### 왕복 검사 {#sec-round-trip}

번역기로 한국어 문장을 영어로 옮겼다가 다시 한국어로 옮겨 본 적이 있을 것이다. 돌아온 문장이 처음과 다르면
어딘가에서 뜻이 빠졌다는 증거다. 파일도 같은 방법으로 시험한다. **객체를 파일로 쓰고, 다시 읽어, 처음 객체와
비교한다.** 이를 **왕복 검사(round-trip test)** 라 한다. 처음 객체를 우리가 알고 있으니, 9장처럼 참값을 아는
세계에서 저장 방법을 시험하는 셈이다.


```{r round-trip-data}
before <- data.frame(
  도서관 = c("누리도서관", "여울도서관"),
  비율 = c(1 / 3, 0.1 + 0.2),
  등급 = factor(c("중", "상"), levels = c("하", "중", "상")),
  개관일 = as.Date(c("2004-03-15", "1999-02-11")),
  우편번호 = c("04157", "54896")
)
str(before)

```


::: {.callout-tip}
**예측해 보자**: `1/3` 을 CSV 로 저장했다가 다시 읽으면 `== 1/3` 은 `TRUE` 이겠는가? `write.csv()` 와
`write_csv()` 의 답이 같겠는가?

:::


```{r round-trip-csv}
rt_base <- file.path(tempdir(), "rt-base.csv")
rt_readr <- file.path(tempdir(), "rt-readr.csv")
write.csv(before, rt_base, row.names = FALSE)
write_csv(before, rt_readr)

after_base <- read.csv(rt_base)
after_readr <- read_csv(rt_readr)

after_base$비율[1] == 1 / 3
after_readr$비율[1] == 1 / 3
readLines(rt_base, n = 2)
readLines(rt_readr, n = 2)

```


`write.csv()` 는 수를 **유효숫자 15자리**까지만 적는다. `0.333333333333333` 은 `1/3` 에 아주 가깝지만 같지 않다.
`write_csv()` 는 다시 읽었을 때 같은 수가 되도록 필요한 만큼(`0.3333333333333333`) 적는다. 2장에서 본
`0.1 + 0.2` 도 `0.30000000000000004` 로 적혀 정확히 되돌아온다. 다른 열은 어떨까? `all.equal()` 은 무엇이 다른지
목록으로 알려 준다.


```{r round-trip-compare}
all.equal(before, after_base)
all.equal(before, as.data.frame(after_readr), check.attributes = FALSE)

```


`all.equal()` 은 아주 작은 수의 차이는 같다고 본다(8장). 그래서 `비율` 은 목록에 없고, **유형이 바뀐 열**이 드러났다.
결과를 정리하면 다음과 같다. 오른쪽 두 열은 @sec-formats 에서 확인한다.

| 원래 객체의 정보 | `write.csv` → `read.csv` | `write_csv` → `read_csv` | RDS | Parquet |
|:--|:-:|:-:|:-:|:-:|
| `1/3` 의 모든 자릿수 | 잃음 | 유지 | 유지 | 유지 |
| 요인과 수준의 순서 | 문자로 바뀜 | 문자로 바뀜 | 유지 | 유지 |
| 날짜 유형 | 문자로 바뀜 | 유지 | 유지 | 유지 |
| 우편번호의 앞자리 0 | 잃음 | 추측에 따라 다름 | 유지 | 유지 |

: {tbl-colwidths="[28,18,18,18,18]"}

CSV 는 **글자만** 담는다. 등급 열이 '하, 중, 상' 순서를 가진 요인이었다는 사실, 개관일이 날짜였다는 사실은
글자로 적히지 않으므로 다시 읽을 때 추측에 맡겨진다. 누구나 열어 볼 수 있다는 장점의 대가다.


### 엑셀에서 열 CSV {#sec-excel-csv}

R 에서 UTF-8 로 저장한 CSV 를 한국어 Windows 의 Excel 에서 두 번 눌러 열면 한글이 깨지는 경우가 많다. 아무 표시가
없는 CSV 를 Excel 이 시스템의 기본 인코딩(CP949)으로 읽기 때문이다. readr 의 `write_excel_csv()` 는 파일 맨 앞에
**BOM(byte order mark)** 이라는 세 바이트를 붙인다. readr 도움말에 따르면 이 표시가 Excel 에 "이 CSV 는 UTF-8"
이라고 알려 준다.


```{r bom}
out_excel <- file.path(tempdir(), "small-excel.csv")
write_excel_csv(small, out_excel)

readBin(out_excel, what = "raw", n = 3)     # 맨 앞의 BOM: ef bb bf
readBin(out_readr, what = "raw", n = 3)     # write_csv() 는 BOM 없이 바로 글자

```


Excel 에서 열어 볼 사람에게 건넬 파일은 `write_excel_csv()` 로 쓴다. 옛 프로그램이 CP949 파일만 받는다면
`write.csv(small, "파일.csv", row.names = FALSE, fileEncoding = "CP949")` 로 변환해 쓴다. 어느 쪽이든 받은 사람이
열어 본 결과를 한 번은 확인한다.


## 스프레드시트와 통계 패키지 파일 {#sec-spreadsheet-stat}

텍스트 파일이 아닌 형식으로 받는 자료도 많다. 사람이 입력한 표는 Excel 파일로, 설문 조사 원자료는 SPSS 나 SAS
파일로 오는 경우가 흔하다. 이 절에서는 같은 설문 자료를 세 가지 형식으로 받아 읽는다.


### Excel 파일 읽기 {#sec-excel}

readxl 패키지의 `read_excel()` 로 읽는다. 한 파일에 시트가 여러 개일 수 있으므로 시트 이름부터 확인한다.


```{r excel-sheets}
library(readxl)
x <- "dataset/ch11/survey.xlsx"
excel_sheets(x)
read_excel(x)                          # 시트를 지정하지 않으면 첫 시트

```


첫 줄의 제목이 열 이름이 되고, 진짜 머리글은 데이터의 둘째 행으로 들어갔다. CSV 와 똑같은 머리말 문제다.


```{r excel-skip}
survey_x <- read_excel(x, skip = 2)
survey_x
read_excel(x, sheet = "안내")

```


`안내` 시트에 **만족도 9 는 무응답**이라고 적혀 있다. 이 사실은 응답 시트만 읽어서는 알 수 없다. 시트를 모두
확인해야 하는 이유다. 필요한 칸만 읽으려면 `range = "A3:E15"` 처럼 Excel 의 칸 주소를 준다.

R 의 표를 Excel 파일로 쓸 때는 writexl 패키지의 `write_xlsx()` 를 쓴다. 이름을 붙인 리스트를 주면 이름마다
시트가 하나씩 생긴다.


```{r excel-write}
out_xlsx <- file.path(tempdir(), "loans.xlsx")
writexl::write_xlsx(list(도서관 = loans, 합계 = total), out_xlsx)
excel_sheets(out_xlsx)

```


### 날짜가 숫자로 보일 때 {#sec-excel-dates}

수능 D-100 을 계산할 때는 두 날짜를 '기준일부터 센 날수'로 바꾸어 뺀다. Excel 은 날짜를 처음부터 이렇게 저장한다.
칸에 보이는 `2026-09-01` 은 표시 형식일 뿐이고, 안에 든 값은 **1899년 12월 30일부터 센 날수** `46266` 이다.


::: {.callout-tip}
**예측해 보자**: 위 `survey_x` 의 참가일 열은 날짜 대신 무엇으로 읽혔는가? 왜 그렇게 되었겠는가?

:::


```{r excel-serial}
survey_x$참가일
class(survey_x$참가일)

```


참가일 열에는 날짜 칸 사이에 `미정` 이라는 **글자 칸이 하나** 섞여 있다. `read_excel()` 은 열의 유형을 하나로
정해야 하므로 날짜와 글자를 모두 담을 수 있는 문자를 골랐고, 날짜 칸은 속에 든 날수가 글자로 나왔다. 날수를
날짜로 되돌린다.


```{r excel-serial-fix, warning=TRUE}
참가일 <- as.Date(as.numeric(survey_x$참가일), origin = "1899-12-30")
참가일

```


경고는 `미정` 을 수로 바꿀 수 없어 `NA` 로 만들었다는 뜻이다. 의도한 결과인지 대조한다.


```{r excel-serial-check}
sum(is.na(참가일))                    # 변환 후 결측 수
sum(survey_x$참가일 == "미정")        # 원래 '미정' 칸 수

```


열 유형을 처음부터 날짜로 지정해도 된다. 이때는 글자 칸마다 **어느 칸이 문제인지** 경고로 알려 준다.


```{r excel-coltypes, warning=TRUE}
survey_d <- read_excel(x, skip = 2,
                       col_types = c("numeric", "numeric", "numeric", "date", "numeric"))
class(survey_d$참가일)

```


`read_excel()` 은 날짜를 시간까지 담는 `POSIXct` 로 읽으므로, 날짜만 필요하면 `as.Date()` 로 바꾼다.


::: {.callout-note}
Excel 의 날수는 1900년 1월 1일을 1 로 센다. 그런데 초기 스프레드시트 프로그램과 호환하려고 1900년을 윤년으로
세어 있지도 않은 1900년 2월 29일에 번호 하나를 주었다. 그래서 1900년 3월 이후의 날짜는 **1899년 12월 30일**을 0 으로
놓고 계산해야 맞는다. `read_excel()` 은 이 사정을 반영해 날짜 칸을 읽으므로, 날수를 직접 변환할 때만
`origin = "1899-12-30"` 을 기억하면 된다.

:::


### SPSS, SAS, Stata 파일 {#sec-haven}

통계 조사의 원자료는 SPSS(`.sav`), SAS(`.sas7bdat`), Stata(`.dta`) 형식으로 배포되는 경우가 많다. 이런 파일은
값과 함께 **값 라벨**(1 = 남, 2 = 여)과 **결측값 정의**(9 = 무응답)를 담는다. haven 패키지가 이 형식을 읽는다.


```{r haven-read}
library(haven)
survey_sav <- read_sav("dataset/ch11/survey.sav")
survey_sav$성별
survey_sav$만족도[1:5]

```


`성별` 은 값 1, 2 에 라벨이 붙은 열이다. `as_factor()` 로 라벨을 수준으로 쓰는 요인으로 바꾼다.


```{r haven-factor}
table(as_factor(survey_sav$성별))

```


`만족도` 의 4번째 응답은 `NA` 로 읽혔다. 원자료에서는 9 였지만 파일에 **9 는 결측값**이라는 정의가 들어 있어
`read_sav()` 가 `NA` 로 바꾸었다.


::: {.callout-tip}
**예측해 보자**: 같은 설문을 CSV 로 내보낸 `survey.csv` 를 읽어 만족도의 평균을 구하면, SPSS 파일에서 구한 평균과
같겠는가?

:::


```{r haven-vs-csv}
mean(survey_sav$만족도, na.rm = TRUE)

survey_csv <- read_csv("dataset/ch11/survey.csv")
mean(survey_csv$만족도)

```


1~5점 척도의 평균이 `r mean(survey_csv$만족도)` 로 부풀었다. CSV 에는 라벨도 결측 정의도 없이 **숫자 9 만** 남기
때문이다. 코드북에서 9 가 무응답임을 확인했다면 결측으로 바꾼다. 이때 `na` 인수는 조심해야 한다.


```{r haven-na-trap}
wrong <- read_csv("dataset/ch11/survey.csv", na = c("", "NA", "9"))
wrong$응답번호

```


`na` 는 **모든 열**에 적용된다. 9번 응답자의 응답번호까지 `NA` 가 되었다. 결측 코드가 한 열에만 해당하면 그 열에서만
바꾼다.


```{r haven-na-fix}
survey_csv$만족도[survey_csv$만족도 == 9] <- NA
mean(survey_csv$만족도, na.rm = TRUE)

```


SAS 파일은 `read_sas()`, Stata 파일은 `read_dta()` 로 읽는다. 사용법은 같다.


## 저장 형식 고르기 {#sec-formats}

보고서를 보낼 때 한글(hwp) 파일로 보낼지 PDF 로 보낼지 고민해 본 적이 있을 것이다. 받는 사람이 고쳐 써야 하면
원본 파일을, 모양 그대로 보여 주기만 하면 되면 PDF 를 보낸다. 데이터 저장 형식도 **받는 사람과 목적**에 따라
고른다. 이 절에서는 R 전용 형식과 Parquet 을 살펴보고, 네 가지 방식의 비용을 잰다.


### R 전용 형식: RDS 와 RData {#sec-rds}

R 객체를 **그대로** 저장하는 형식이다. 요인의 수준, 날짜 유형, 모든 자릿수가 보존된다.


```{r rds}
rds_file <- file.path(tempdir(), "before.rds")
saveRDS(before, rds_file)
identical(before, readRDS(rds_file))

```


`identical()` 은 한 비트라도 다르면 `FALSE` 를 돌려주는 가장 엄격한 비교다. 왕복 검사를 완전히 통과했다.
`saveRDS()` 는 객체 **하나**를 저장하고, 읽을 때 이름을 새로 붙인다. 여러 객체를 한꺼번에 저장하는 `save()` 와
`load()` 도 있다.


::: {.callout-tip}
**예측해 보자**: 아래 코드를 실행한 뒤 `x` 에는 무엇이 들어 있겠는가?

```r
x <- "지난주 결과"
save(x, file = rdata_file)
x <- "오늘 다시 계산한 결과"
load(rdata_file)
```

:::


```{r rdata-overwrite}
rdata_file <- file.path(tempdir(), "old.RData")
x <- "지난주 결과"
save(x, file = rdata_file)

x <- "오늘 다시 계산한 결과"
load(rdata_file)
x

```


`load()` 는 저장할 때의 **이름 그대로** 객체를 되살리면서, 같은 이름의 객체를 **아무 경고 없이 덮어쓴다.** 오늘
계산한 결과가 지난주 결과로 바뀌었다. 무엇이 되살아나는지는 파일을 열어 보기 전에는 알 수 없다. 반면
`readRDS()` 는 `result <- readRDS(파일)` 처럼 이름을 내가 정한다. 이 강의에서는 RDS 를 쓴다.


### Parquet {#sec-parquet}

학생 명부를 보관하는 두 가지 방법을 생각해 보자. 한 사람당 카드 한 장에 이름, 학번, 키를 적는 방법(행 단위)과,
이름 목록, 학번 목록, 키 목록을 따로 적는 방법(열 단위)이다. "모든 학생의 키 평균"을 구할 때는 키 목록 한 장만
보면 되는 열 단위가 빠르다. 같은 종류의 값이 이어져 있어 **압축도 잘 된다.** 이렇게 열 단위로 저장하는 대표적인
형식이 **Parquet** 이다. R 뿐 아니라 Python, DuckDB, Spark 같은 여러 도구가 읽고 쓰므로, 다른 사람과 큰 데이터를
주고받을 때 쓴다.


```{r parquet}
library(arrow)
pq_file <- file.path(tempdir(), "before.parquet")
write_parquet(before, pq_file)
identical(before, as.data.frame(read_parquet(pq_file)))

```


Parquet 도 왕복 검사를 통과했다. 요인, 날짜, 앞자리 0 이 모두 보존된다. arrow 패키지는 기능이 많은 만큼 설치
파일이 크다. Parquet 파일을 읽고 쓰기만 하면 되는 경우에는 가벼운 nanoparquet 패키지로도 같은 일을 할 수 있다.


### 형식별 비용 비교 {#sec-format-choice}

8장에서 비용을 수행 시간과 메모리로 정의했다. 저장 형식의 비용은 **파일 크기**와 **읽고 쓰는 시간**이다. 50만 행의
가상 기상 관측 자료로 네 가지 방식을 비교한다.


::: {.callout-tip}
**예측해 보자**: 같은 자료를 네 방식으로 저장하면 어느 파일이 가장 작고, 어느 파일이 가장 크겠는가?
(`read.csv` 용 CSV, `read_csv` 용 CSV, RDS, Parquet)

:::

초 단위 시간은 컴퓨터마다 다르지만 **크기와 복원 여부**는 어느 컴퓨터에서나 같다. 텍스트 파일인 CSV 는 수 하나하나를
글자로 적으므로 크고, 다시 읽을 때 유형을 추측해야 하므로 그대로 복원되지 않는다. RDS 와 Parquet 은 압축된 이진
파일이라 작고 빠르며 그대로 복원된다. 그러나 메모장으로 열어 볼 수는 없다. 네 방식의 성격을 정리한다.

| 형식 | 사람이 열어 보기 | 다른 프로그램 | 유형 보존 | 크기와 속도 | 알맞은 쓰임 |
|:--|:-:|:-:|:-:|:-:|:--|
| CSV | 쉬움 | 거의 모두 | 안 됨 | 크고 느림 | 사람과 다른 프로그램에 건네기 |
| Excel | 쉬움 | 스프레드시트 | 일부 | 보통 | 사람이 보고 고칠 표 |
| RDS | 안 됨 | R 만 | 완전 | 작고 빠름 | 내 분석의 중간 결과 저장 |
| Parquet | 안 됨 | R, Python 등 | 거의 완전 | 작고 매우 빠름 | 큰 데이터를 여러 도구와 공유 |

: {tbl-colwidths="[12,14,16,12,16,30]"}


표의 '작고 매우 빠름'은 위와 같이 **행이 많은 긴 표**에서의 이야기다. 형식의 비용은 자료의 모양에 따라 달라진다.
열이 2만 개인 넓은 표로 같은 비교를 해 보자. `dataset/pulse.csv` 는 69행, 20,000열이다.



열마다 값은 69개뿐이니 그 정보가 차지하는 몫이 커진 것이다. **어떤 형식이 싸다는 말도 추측이다.** 중요한 파일이면
8장에서처럼 내 자료로 직접 재어 본다.

### 작업 요구사항 {#sec-ai-import-spec}

한 학생이 `library-loans.csv` 를 읽으려다 `read.csv()` 와 `read_csv()` 에서 모두 오류를 만났다. 학생은 두 오류
메시지와, 메모장으로 연 파일의 **앞부분 7줄**을 붙여 AI 에게 요청했다. 오류 메시지는 이 파일을 R 에서 실제로 읽어

- **열 유형**: 이용자수가 **문자**다. 휴관 도서관의 `-` 때문에 숫자로 추측되지 않았다. 평균을 구하면
  `NA` 와 경고만 나온다.
- **합계**: 대출권수의 합이 합계 행의 **정확히 두 배**다. 합계 행이 데이터에 섞였기 때문이다.

경고가 가리킨 문제를 `problems()` 로 보려 하면 이상한 일이 생긴다.


```{r ai-problems-lost}

```

기록이 **떨어져 나갔다.** 읽은 직후의 결과에서는 기록이 남아 있다.

### AI 가 보지 못한 부분 {#sec-ai-import-gaps}

검증에서 드러난 결함은 모두 **붙여 넣은 7줄 밖**에 있다.

**보지 못한 줄 1. 휴관 도서관의 `-`** (원문 15번째 줄). 앞의 7줄에는 결측 표기가 없었으므로 코드에도 `na` 인수가 없다.
그 결과 이용자수는 문자가 되고, 대출권수의 `-` 는 문제 기록과 함께 `NA` 가 되었다.

**보지 못한 줄 2. 합계 행** (24번째 줄). 앞부분만 보고는 알 수 없다. 합계 행이 섞이면 모든 합이 두 배가 된다.

**보지 못한 줄 3. 주석 행** (25번째 줄). 응답은 꼬리말이 **있을 수 있다**며 `tail()` 로 확인하라고 조언했다. 좋은
조언이지만 확인은 코드에 들어 있지 않고 **사람의 몫으로** 남았다.

응답의 설명 가운데 하나는 실제 동작과 달랐다. "그냥 두면 `04157` 이 `4157` 로 바뀐다", "대출권수는 그냥 읽으면 텍스트로
들어온다"는 설명은 `read.csv()` 에 맞는 이야기다. AI 가 본 7줄만으로 `read_csv()` 의 추측을 확인해 보자.


```{r ai-seen-guess}

```


readr `r packageVersion("readr")` 는 이 줄들만 보고도 우편번호를 문자로, 대출권수를 `col_number()` 로 추측한다. 그렇다고
유형을 적어 둔 코드가 틀린 것은 아니다. @sec-col-types 에서 보았듯 추측은 파일마다 달라지므로 **명시하는 편이
옳다.** 다만 설명을 사실로 받아들이기 전에 한 번 실행해 보면 이런 차이가 드러난다.

원문에서 확인한 사실을 코드에 더하면 검증을 통과한다.

::: {.callout-caution}
**파일 읽기 코드에서 자주 나타나는 오류 유형** (사람이 짠 코드와 AI 가 짠 코드 모두)

- **앞부분만 보고 전체를 가정한다**: 합계 행, 주석 행, 뒤쪽에만 나오는 결측 표기를 놓친다.
- **경로를 내 컴퓨터에 묶는다**: `setwd()` 나 절대 경로를 쓰거나, 작업 디렉터리를 확인하지 않는다.
- **인코딩을 기본값에 맡긴다**: `read.csv()` 의 `encoding` 과 `fileEncoding` 을 혼동하기도 한다.
- **확인을 사람에게 미룬다**: `tail()` 로 보라고만 하고, 대조를 코드로 남기지 않는다.
- **가공한 뒤에 `problems()` 를 본다**: 파이프로 이어 가공하면 문제 기록이 사라진 뒤다.

이번 응답의 코드는 첫째 유형에 해당했고, 파이프 때문에 다섯째 확인도 할 수 없게 되어 있었다. 모든 유형의 공통점은
**오류 메시지가 나오지 않는다**는 것이다.

:::
