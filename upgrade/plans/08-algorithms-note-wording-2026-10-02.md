## 12. 1.2 구현에 따른 비용 차이, 308–310줄 (→ 311–314줄), 기준 6, 1

메모: 등식 오류 1+…+n = n(n−1)/2 를 0+1+…+(n−1) 로. 10배 → 100배를 이 문단으로 옮김

전:

    $i$ 번째 반복에서 $i$ 개를 복사하므로 전체 복사량은
    $1 + 2 + \cdots + n = n(n-1)/2$ 에 비례한다.
    반면 사전 할당 방식은 이미 확보된 메모리에 값을 대입하므로 반복당 비용이 일정하다.

후:

    $i$ 번째 반복에서 기존 원소 $i-1$ 개를 복사하므로 전체 복사량은
    $0 + 1 + \cdots + (n-1) = n(n-1)/2$ 에 비례한다. 따라서 `n` 을 10배로 늘리면 이어 붙이기의 복사량은
    약 100배가 된다. 반면 사전 할당 방식은 이미 확보된 메모리에 값을 대입하므로 반복마다 대입 한 번으로
    연산 횟수가 일정하고, `n` 을 10배로 늘리면 연산 횟수도 10배가 된다.

후:

    뒤의 값은 관측 가능한 우주의 원자 수로 추정하는 약 $10^{80}$ 보다 크다.
    
    $n = 10^6$ 이고 컴퓨터가 초당 $10^9$ 번 연산한다고 하자. $\mathcal{O}(n \log n)$ 은 약 $2 \times 10^7$ 번으로
    0.02초, $\mathcal{O}(n^2)$ 은 $10^{12}$ 번으로 1,000초(약 17분)가 걸린다. 컴퓨터가 100배 빨라져도

## 강사 확인

1. 5.7 경사하강법 첫 문단의 수치(네 걸음, 47걸음, 5걸음, 1.81 과 2.46)와 경로 그림 설명의 9.5, 일곱 걸음은 이를 출력하는 청크가 없다. 값은 맞다. 숨긴 청크를 하나 두고 인라인 R 로 바꿀지 결정이 필요하다(청크 추가는 이번 범위 밖이라 하지 않았다).
2. 2.2 `recursive-sum-deep` 청크의 코드 주석 `# 정상적으로 동작한다` 를 `# 500500 을 반환한다` 처럼 바꿀지.
3. 1.4 하드웨어 문단에 슬라이드 17번과 같은 가정($n = 10^6$, 초당 $10^9$ 연산)으로 0.02초, 약 17분, 10초, 500배를 산술로 적었다. 실행 출력이 아니라 가정에서 계산한 값이다. 같은 방식으로 1.4 의 $3n^2 + 5n$ 예(0.2%)와 3.4 콜아웃의 손익분기 $k \approx \log_2 n$ (n = 1,000 이면 약 10)도 산술 값이다.
4. 4.2 팀정렬 서술을 "원소 수십 개 길이의 구간을 삽입 정렬로 정렬한 뒤 병합한다" 로 구체화했다(CPython `listsort` 의 minrun 32~64, 이진 삽입 정렬). 이 정도로 둘지.
5. 5.5 `lm()` 의 QR 노트에 "$\mathbf{X}^\top\mathbf{X}$ 의 조건수는 $\mathbf{X}$ 의 조건수의 제곱" 을 넣었다. 2학년 수준에서 조건수를 정의 없이 써도 되는지.
6. 4.4 퀵 정렬의 `node stack overflow` 는 "R 이 재귀 호출이 쌓이는 공간에 한계를 여러 개 두고, 어느 한계에 먼저 닿느냐에 따라 메시지가 다르다" 로만 적었다. 세부 기전(식 중첩 한계 `expressions` 와 바이트코드 노드 스택)은 적지 않았다. 확인 실행에서 `quick_sort(1:4000)` 은 정상, `1:5000` 은 `node stack overflow`, `recursive_sum(2500)` 은 정상, `recursive_sum(5000)` 은 `evaluation nested too deeply` 였다.
7. 4.5 실행 시간 문단은 인라인 R 로 렌더 때 값을 싣는다. "퀵 정렬은 병합 정렬보다 시간이 덜 걸렸다" 는 이번 렌더(0.004초 대 0.017초)에서 맞지만 측정값에 기대는 문장이다. 원문도 같은 주장을 하고 있어 유지했다.
